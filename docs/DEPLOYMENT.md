# Production deployment

**As of 2026-07-25 (ADR-32, Phase 11), the app has no local database of its own** — Supabase (PostgreSQL) is the only datastore, reached over the network via `database/supabase_client.py`. The SQLite-specific steps this doc used to describe (`DATABASE_PATH`, `database.init_db`, local file backups) no longer apply; see [DECISIONS.md](DECISIONS.md) for the full migration history.

**As of 2026-08-21 (pilot phase, ADR-53), each library gets its own fully independent app deployment *and* its own fully independent Supabase project** — there is no shared schema and no `firm_id`/`organization_id`/tenant column anywhere; isolation between libraries is a *deployment/configuration* concern, not an application-layer one. This means the note that used to appear at the bottom of this file ("multiple independent web workers or hosts can safely point at the same Supabase project concurrently") is true only *within* one library's own deployment — different libraries must **never** share a Supabase project or an `.env` file. See **[PROVISIONING.md](PROVISIONING.md)** for the full, step-by-step process for provisioning a new library's environment; this file covers the deployment steps themselves.

1. Create a Python **3.11+** virtual environment and install `requirements.txt` (includes `waitress`, the production WSGI server used in step 4). Verified 2026-08-21: a clean install fails on Python 3.10 (`contourpy==1.3.3`, a transitive `matplotlib`/`utils/charts.py` dependency, requires 3.11+) and succeeds on 3.11.
2. Set the variables shown in `.env.example` in a `.env` file that belongs to **this deployment only** — never copied from, or shared with, another library's deployment. This includes a unique `SUPABASE_URL`/`SUPABASE_SECRET_KEY` pointing at this library's own Supabase project (see `database/supabase_client.py`) and a freshly generated `SECRET_KEY` (a shared `SECRET_KEY` across deployments would let one deployment's session cookies be replayed against another's). Do not commit `.env`. Confirm no other `.env` exists in any parent directory of this deployment's own folder — `python-dotenv`'s `load_dotenv()` walks upward looking for one if this deployment's own is missing, and would silently pick up a sibling library's instead of failing (see PROVISIONING.md).
3. Confirm the target Supabase project's schema matches `database/supabase_migration.sql` (applied by hand, once, in that project's Supabase SQL Editor — there is no migrations framework/runner), then run `python scripts/verify_schema.py` against it to confirm every table this app needs actually exists before serving any traffic.
4. Serve with a production WSGI server: `waitress-serve --call wsgi:create_app`, behind HTTPS.
5. Check this deployment's log for the `Connected Supabase project: ...` startup line and visually confirm it matches the intended project before declaring go-live.
6. Run `python scripts/verify_tenant_isolation.py` (before, and again right after, the first admin registers) to confirm this project contains only this one library's data — see PROVISIONING.md.
7. Backups are Supabase's responsibility at the infrastructure level (point-in-time recovery / scheduled dumps, configured in the Supabase project itself) — the app's own Settings → Data & Backup → "Create Backup" is a manual, per-admin data export (JSON), not a substitute for a real database backup strategy.

Because there's no local file to share or lock, multiple independent web workers *of the same deployment* can safely point at that deployment's own Supabase project concurrently — the constraint SQLite had (no shared file over a network filesystem) no longer applies. This does not extend across libraries: each library's workers/hosts point at that library's project only.
