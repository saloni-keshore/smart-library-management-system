# Code Journey — How a Request Actually Flows

The general shape (see [DIAGRAMS.md](DIAGRAMS.md) diagram 3 for the visual): **Browser → Blueprint route function → (raw SQL or a `database/*_queries.py` module) → SQLite → Jinja template (extends a layout, includes components) → back to the browser.** Every step below is traced against real file/function names so you can jump straight to the code.

## Journey 1 — Collecting a membership payment (a write path)

This is the most important flow in the app: it touches three tables in one transaction and is the pattern every other "record some money" feature follows.

1. **Browser** submits the form on `templates/payments/collect.html` → `POST /payments/collect/<membership_id>`.
2. **Route** `routes/payment.py`'s `collect(membership_id)` receives it:
   - Checks `if "admin_id" not in session: return redirect("/")`.
   - Gets a Supabase client via `database.supabase_client.get_supabase_client()` and fetches the `memberships` row by `membership_id` — if none exists, flashes "Membership not found" and redirects to `student.index`.
   - Verifies the membership belongs to the current admin with a second Supabase read: the membership's `student_id` looked up in `students`, filtered `.eq("admin_id", admin_id)` — if no matching student, flashes the same "Membership not found" and redirects, reproducing the old single-`JOIN` query's combined outcome as two sequential reads.
   - Validates `amount_paid`: must parse as a number, be `> 0`, and be `<= pending_amount`. Any failure flashes a `danger` message and re-renders `payments/collect.html`.
3. **Write #1 (Supabase, only store)** — updates `memberships.paid_amount` / `memberships.pending_amount` in Supabase via `.update({...}).eq("membership_id", membership_id)`. This is the write `routes/membership.py`'s `index()` actually reads (closing TD-37, ADR-21) — everything downstream in this route happens only if this succeeds. As of 2026-07-24 (ADR-29), there is no SQLite mirror-write to follow this one — `memberships` is Supabase-only.
4. **Write #2 (Supabase, strict)** — calls `database/payment_queries.py`'s `record_payment(admin_id, ...)` (no `conn` argument, as of 2026-07-24 ADR-28). It generates a receipt number (`generate_receipt_number()`, reading/advancing Supabase `library_settings.next_receipt_number` as of 2026-07-24, ADR-24 — see TD-40 for the narrower transaction-boundary risk this introduced, unaffected by ADR-28) and `INSERT`s into Supabase `payments` — this insert is **strict**: a failure raises `postgrest.exceptions.APIError` past `record_payment()`, since there's no SQLite fallback left to quietly keep the payment in.
5. **Write #3** — inside `record_payment()`, calls `database/cashbook_queries.py`'s `insert_income_entry(admin_id, category="Membership Fee", ...)`. As of 2026-07-24 (ADR-27), this call takes no SQLite `conn`/cursor either.
   - Inside `insert_income_entry`: generates a `reference_id` via `_generate_reference_id` (Supabase `COUNT`, ADR-27), best-effort `INSERT`s into Supabase `cashbook` with `source="Payments"` (not `"Cashbook Manual Entry"` — see below), then best-effort `INSERT`s the Supabase `audit_log` row (`"Auto-Created"`) — **write #4**. Both inserts (plus ID generation) are wrapped in one `try/except: pass`; as of ADR-27, a failure here means neither row is written anywhere (no SQLite fallback left, TD-43) — unlike write #2, a failure here is deliberately swallowed, not raised — see ADR-28's "why strict instead of best-effort" reasoning in [DECISIONS.md](DECISIONS.md) for why the two writes diverge.
6. **Rollback path** — if write #2 raises `APIError`, `collect()`'s `except APIError:` block reverts the Supabase update from **write #1** back to its pre-payment values (`.update({"paid_amount": old_paid, "pending_amount": old_pending})`), so Supabase never advances ahead of a failed payment write. As of 2026-07-24 (ADR-29), this is the entire rollback story — there is no SQLite transaction left to roll back alongside it.
7. **Redirect** to `student.view` with a success flash — POST/Redirect/GET, so refreshing the result page doesn't resubmit the payment.
8. **Downstream read-side effects**, visible immediately on next page load without any extra code: `routes/membership.py`'s `index()` (Supabase-backed) now shows the updated balance immediately, closing the staleness TD-37 described; the new `cashbook` row now appears in `routes/cashbook.py`'s ledger (as a **non-editable** row, since its `source` isn't `"Cashbook Manual Entry"` — see ADR-4 in [DECISIONS.md](DECISIONS.md)); it also feeds every aggregate in `database/bi_queries.py` (health score, revenue growth, top revenue sources) the next time `routes/business_intelligence.py`'s `index()` runs.

**Files touched, in order:** `templates/payments/collect.html` → `routes/payment.py` → `database/supabase_client.py` (`memberships`/`students` reads, `memberships` update — the only store as of ADR-29) → `database/payment_queries.py` (`record_payment`, `generate_receipt_number` — both Supabase-only and strict as of ADR-28) → `database/cashbook_queries.py` (`insert_income_entry`, `_generate_reference_id`, both Supabase-only and best-effort as of ADR-27) → back to `routes/payment.py` → `templates/students/view.html` (via redirect).

**Note (as of 2026-07-23, ADR-21):** this journey now matches Journeys for Enquiries/Students/Membership — Supabase is the source of truth for the `memberships` balance, and as of 2026-07-24 (ADR-29) also the only store, no SQLite mirror left at all. `routes/payment.py`'s own `index()` (listing all payments) reads Supabase `payments`/`students` too (ADR-25) — no SQLite dependency left in this route at all as of ADR-29. As of 2026-07-24, `audit_log`'s (ADR-26), `cashbook`'s (ADR-27), `payments`' (ADR-28), and `memberships`'/`students`' (ADR-29) SQLite mirror-writes are all gone entirely.

## Journey 2 — Viewing the Dashboard (a read + side-effect path)

1. **Browser** navigates to `GET /dashboard`.
2. **Route** `routes/dashboard.py`'s `dashboard()`:
   - Session check, same pattern as above.
   - As of 2026-07-23 (ADR-23): total-students/total-enquiries counts, active/expired membership counts, upcoming expiries, and recent admissions all read Supabase `students`/`enquiries`/`memberships` via `database.supabase_client.get_supabase_client()` and `database.membership_queries`'s `get_membership_counts()`/`get_memberships_for_admin()`/`get_admin_students()`/`get_days_left()` — no raw SQL against SQLite for any of these. As of 2026-07-24 (ADR-25), "Total Revenue"/"Today's Collection"/"Pending Fees" all read Supabase `payments`/`students`/`memberships` via `database.cashbook_queries` too — this route has no SQLite dependency left at all.
   - **Side effect:** calls `utils.charts.generate_revenue_chart(admin_id)` (still SQLite, its own `database.db.get_connection()`) and `generate_membership_chart(admin_id)` (Supabase, via `database.membership_queries.get_memberships_for_admin()`, ADR-23). Each overwrites `static/charts/revenue.png` / `static/charts/membership.png` in place.
3. **Template** `templates/dashboard/index.html` extends `layouts/base.html`, includes `components/{dashboard_header, quick_actions, revenue_chart, membership_chart, expiry_table, recent_admissions}.html`. The chart components don't receive chart data through the render context at all — they just `<img>` the static PNG path that step 2's side effect already wrote to disk.
4. **Global context processor** — before the template even starts rendering, `app.py`'s `inject_notification_summary` has already run (registered via `@app.context_processor`, fires on every render call, not just this route) and called `routes/notification.py`'s `get_notification_summary(admin_id)` (Supabase, ADR-23), populating `nav_notifications` for `components/notification_dropdown.html` inside `navbar.html`.
5. **Browser** receives HTML referencing the just-regenerated PNGs — if two admins' dashboard loads interleave, there's a brief window where one admin could see the other's chart (see [11_FUTURE_WORK.md](11_FUTURE_WORK.md) TD-1).

**Files touched:** `routes/dashboard.py` → `database/supabase_client.py` + `database/membership_queries.py` + `database/cashbook_queries.py` (all Supabase, ADR-23/25) + `utils/charts.py` (Supabase, own DB queries + file write) → `templates/dashboard/index.html` + 6 component templates → (in parallel) `app.py`'s context processor → `routes/notification.py` (Supabase) → `components/notification_dropdown.html`.

## The general pattern to follow for a new feature

1. Add a route function in the right `routes/*.py` (or a new blueprint, registered in `app.py`).
2. Start the function with the standard session guard (`if "admin_id" not in session: return redirect("/")`) — there's no decorator for this yet, copy the exact snippet used elsewhere.
3. For data access: if a `database/*_queries.py` module already exists for this feature (cashbook, BI, settings, membership settings, membership_queries, payment_queries), add a function there instead of writing raw SQL in the route — that's the pattern the more recently built features (Cashbook, BI, Settings, Payments) follow. As of 2026-07-24 (ADR-29), the only raw SQL left anywhere is `routes/enquiries.py`'s own SQLite mirror-*write* (`add()`/`edit()`/`delete()`) and `routes/setting.py`'s whole-file backup copy — `routes/student.py`/`routes/membership.py`/`routes/payment.py`, and `database/cashbook_queries.py`/`payment_queries.py`, all have zero SQLite dependency as of ADR-27/28/29; see `docs/MIRROR_TRACKER.md` for exactly which mirror remains and why. `auth` was the first module to move off SQLite (ADR-16); `enquiries.py` is now the only route still keeping an ongoing SQLite mirror-write in sync, the same "call `get_supabase_client()` directly for the route's own table" shape every migrated route uses, minus the mirror. `dashboard`/`notification`/`membership_distribution` moved onto shared helpers in `database/membership_queries.py`/`database/payment_queries.py` instead (ADR-23/25) rather than writing their own inline Supabase calls — prefer that shared-helper shape for any new cross-table read, rather than duplicating a `.select()`/`.in_()`/merge pattern per route.
4. Always filter by `admin_id` (directly, or via a join to a table that has it) — there is no framework-level tenant isolation, it's a manual convention (see ADR-2 in [DECISIONS.md](DECISIONS.md)).
5. If the new write should show up in the financial ledger, call `database/cashbook_queries.py`'s `insert_income_entry(admin_id, ...)` (as of 2026-07-24, ADR-27, it takes no SQLite connection at all — it's Supabase-only, best-effort) and pick a `source` value other than `"Cashbook Manual Entry"` so it's correctly treated as auto-generated/read-only in the Cashbook UI.
6. Render a template that extends `layouts/base.html`, reusing `components/stat_card.html` / `chart_card.html` / `table_card.html` for common layout shapes before hand-rolling new markup.
7. Update the relevant doc(s) in `docs/` and add a [CHANGELOG.md](CHANGELOG.md) entry in the same session — see the maintenance policy in [README.md](README.md).
