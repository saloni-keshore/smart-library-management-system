## 2026-08-28 — Fix Dashboard 500 from the matplotlib leader-line crash in `utils/charts.py` (resolves the chart half of TD-68)

- **Feature:** Dashboard / Membership Distribution charts. The first real Render deployment (Pilot A, Supabase project `rkbunnkkeiwrnvexihap`) 500'd on `/dashboard` right after the first admin added test students/memberships. Render logs showed `ValueError: Given lines do not intersect. Please verify that the angles are not equal or differ by 180 degrees.` from `matplotlib/bezier.py`'s `get_intersection()`, reached via `generate_membership_chart()`'s per-label `ax.annotate(..., arrowprops={"connectionstyle": f"angle,angleA=0,angleB={np.degrees(np.arctan2(point['y'], point['x']))}"})`. This is the same bug as **TD-68** (logged 2026-08-21, found then via an exact 6/6 two-plan split in a long-lived test admin), now hit again in production. Root cause: matplotlib's `angle` connection style builds a corner by intersecting a ray at `angleA` (always `0` here) with one at `angleB`; when a pie/donut wedge's centroid lands on the horizontal axis its `angleB` is `0` or `180`, the two rays are parallel, and `get_intersection()` raises instead of drawing. Confirmed via wedge geometry that this happens for an **exact 50/50 two-plan split** (wedges centred at 180 deg and 0 deg with `startangle=90`) and for **any single plan that is exactly 50% of all memberships** (that wedge centred at 180 deg) — both completely ordinary states for a small or new library. Reproduced the raw matplotlib `ValueError` locally with `connectionstyle="angle,angleA=0,angleB=180"` (`angleB=181` → fine). Fixed by routing both chart functions' leader-line `connectionstyle` through a new `_leader_line_connectionstyle(dx, dy)` helper that computes `angleB` and nudges it 1 deg off any multiple of 180 (`m = angle_b % 180; if m < 1 or m > 179: angle_b += 1`) — visually imperceptible on a leader line this short, guarantees the rays are never parallel. The identical inline expression in `generate_membership_distribution_donut()` (Membership Distribution page) had the same latent bug; both now call the helper.
- **Files changed:** `utils/charts.py` (new module-level `_leader_line_connectionstyle(dx, dy)`; `generate_membership_chart()` and `generate_membership_distribution_donut()` each swap their inline `connectionstyle=f"angle,angleA=0,angleB=..."` for `connectionstyle=_leader_line_connectionstyle(point["x"], point["y"])` — no other logic touched); `docs/FILE_REFERENCE.md` (`utils/charts.py` card — Functions list + Future modification notes); `docs/TROUBLESHOOTING.md` (the existing "Dashboard/Membership Distribution 500s with `ValueError: Given lines do not intersect...`" entry updated — cause broadened beyond the 50/50 case, fix + workaround-no-longer-needed noted); `docs/11_FUTURE_WORK.md` (**TD-68** — chart-crash half flipped to Resolved, test-fixture-growth half kept Open).
- **Database changes:** None.
- **UI changes:** The Dashboard and Membership Distribution pages now render for a library whose membership split has a wedge on the horizontal axis (an exact 50/50 two-plan split, or a plan that is exactly half the roster), instead of returning the 500 error page. All other splits are pixel-unchanged — the 1 deg nudge only ever applies to a wedge centroid within 1 deg of horizontal.
- **Future impact:** Resolves the chart-crash half of **TD-68**; the other half (that `tests/test_08_cross_tenant_isolation.py`'s `_register_and_login()` uses hardcoded, un-randomized username suffixes, so its admin keeps accruing membership rows in the shared dev/test project) is unchanged and still Open. Unrelated to **TD-1** (shared non-admin-scoped chart filenames). Verified: exact 50/50 two-plan, three-plan with a 50% plan, and single-plan / multi-plan / zero-plan datasets all render for both `generate_membership_chart` and `generate_membership_distribution_donut`, plus `generate_revenue_chart` with no payments.

## 2026-08-25 — Render deployment-readiness audit for Pilot A: stdout logging fix, Python version pin, deployment-readiness package produced (no deployment performed)

- **Feature:** A read-only deployment-readiness review of the whole repository, ahead of the first Render deployment for the external pilot (Pilot A, Supabase project `rkbunnkkeiwrnvexihap`, confirmed clean/empty). No Render service was created, no Supabase project was modified, and Panda was not touched. Three genuine deployment blockers were found and fixed with the smallest possible change; everything else (env vars, build/start commands, manual dashboard steps, smoke tests, rollback) was compiled into a deployment-readiness package delivered directly to the user, not stored as a new doc file. **Blocker 1:** `app.py`'s `_configure_logging()` attached only a `RotatingFileHandler` — verified live that Python's logging module has no console fallback once any handler exists on a logger, so in production every `app.logger` call, including the `Connected Supabase project: ...` startup line `docs/DEPLOYMENT.md`/`docs/PROVISIONING.md` require an operator to read before declaring go-live, would be written only to a local file. Render (like most PaaS hosts) only captures stdout/stderr as "Logs" and gives a web service no readable/persistent local filesystem by default — that verification step would have been silently impossible to perform. Fixed by also attaching a `logging.StreamHandler` (stdout), unconditionally, alongside the existing file handler. **Blocker 2:** No Python version was pinned anywhere in the repository (no `.python-version`, no `runtime.txt`) despite `docs/PROVISIONING.md`/`docs/DEPLOYMENT.md`/**TD-67** already documenting that a clean `pip install -r requirements.txt` fails outright on Python <3.11 (`contourpy==1.3.3 Requires-Python >=3.11`, a transitive `matplotlib`/`utils/charts.py` dependency) — reproduced live again this session on this machine's Python 3.10 install. Without a pin, Render's default Python version for a fresh service is not guaranteed to be 3.11+. Fixed by adding `.python-version` (`3.11.9`), which Render's native Python runtime reads automatically. **Blocker 3:** neither `request.is_secure` nor `request.remote_addr` accounted for a reverse proxy — no `ProxyFix` (or equivalent) was applied anywhere. Render, like effectively every PaaS host, terminates TLS at an edge proxy and forwards requests to the app over plain HTTP internally, setting `X-Forwarded-Proto`/`X-Forwarded-For`. Without trusting those headers: (a) `request.is_secure` would always be `False` in production, so `set_security_headers()`'s HSTS header would never actually be set even over real HTTPS; (b) `utils/security.py`'s `rate_limited()` — applied to `/` (login) and `/forgot-password` — keys its per-client attempt counter off `request.remote_addr`, which would show the proxy's own internal IP for every visitor, collapsing what's meant to be a per-client login-attempt limit into one shared bucket for the whole deployment. Fixed by wrapping `app.wsgi_app` in Werkzeug's built-in `ProxyFix(x_for=1, x_proto=1)` (trusting exactly one hop) — no new dependency, already transitively available via Flask/Werkzeug.
- **Files changed:** `app.py` (`_configure_logging()` — added the `StreamHandler`, kept the existing `RotatingFileHandler` unchanged; `create_app()` — wraps `app.wsgi_app` in `ProxyFix` as its first step; new `werkzeug.middleware.proxy_fix` import); `.python-version` (new file, `3.11.9`); `docs/FILE_REFERENCE.md` (`app.py` card — documents both changes and removes a stale note claiming `config.py` was unused/no error handlers existed, both no longer true).
- **Why:** The user explicitly authorized fixing only genuine deployment blockers found during this audit, with the smallest possible change, and asked for everything else to be reported rather than acted on ("do not change application behavior unless a genuine deployment blocker is found"). All three fixes above meet that bar: one silently breaks a documented, safety-critical go-live verification step on the target platform; one causes a reproducible, deterministic install failure; one silently breaks both a security header and the login rate-limiter's per-client accounting the moment the app sits behind any reverse proxy, which a Render deployment always does. Every other finding from this audit (ephemeral local-disk uploads under `static/uploads/settings/`, ephemeral generated chart PNGs, the existing `backups/` export flow, exact Render build/start commands, the required environment variable names, Waitress-vs-Gunicorn, manual Render dashboard steps, post-deploy smoke tests, and rollback) was reported to the user as guidance, not implemented as a code change.
- **Database changes:** None. Pilot A's Supabase project was not touched — this session only confirmed (via the user's own report) that it is provisioned and empty, per `docs/PROVISIONING.md`.
- **UI changes:** None visible to an end user. Operationally, this deployment's logs are now also visible via stdout/stderr (e.g. a hosting platform's log dashboard), not only in the local `instance/smart-library.log` file.
- **Future impact:** Resolves **TD-72** (new, same-day — the logging gap) and **TD-74** (new, same-day — the missing `ProxyFix`). Unblocks a future Render deployment from three specific, reproducible failure modes; does not itself deploy anything. New **TD-73** (open): `static/uploads/settings/` (Library Profile logo/stamp/signature uploads) and `backups/` (manual export) both write to local disk with no durable-storage fallback — lost on every restart/redeploy on a host with no persistent disk attached, e.g. a default Render web service. Not fixed this session — it's a real operational limitation, not a blocker (the app still runs correctly without it), and fixing it would be a genuine behavior/architecture change (Supabase Storage migration, or a paid Render Disk) out of this session's explicit "report, don't implement" scope.

## 2026-08-17 — Discount box added to Create Membership (ADR-46)

The calculation, kept fully transparent per ADR-45's principle: **Total Payable = Plan Fee + Admission Fee**; **Discount** is its own separate line item (never folded silently into Total Payable); **Final Payable = Total Payable − Discount** (this is what's stored as `total_fee`); **Paid** = amount actually received; **Pending = Final Payable − Paid**. Discount is validated server-side (`routes/membership.py`'s `create()`): must be `>= 0` and strictly less than the pre-discount total, so Final Payable can never reach zero or go negative. Discount is Create-only, matching how Admission Fee already only applies to new admissions, not renewals.

- **Why:** requested directly by the admin, immediately after the Total Fee/admission-fee fix — a need to give discretionary discounts to students at admission time, with the same "never silently fold into one number" transparency the admission-fee fix just established.

## 2026-08-17 — Fixed Total Fee silently including the admission fee instead of the configured plan price (ADR-45, narrows TD-7)
