# Architecture Decisions

Record of deliberate architectural choices and the reasoning behind them, so future changes can be judged against the original intent rather than guessed at. Entries marked **(inferred)** are reconstructed from reading the code/git history, not from a first-hand statement — treat their "why" as a best-effort explanation, not a certainty.

Add a new entry whenever a change reflects a deliberate architectural choice (not just a bug fix) — see the maintenance policy in [README.md](README.md).

---

### ADR-1: Raw SQL via `sqlite3`, no ORM **(inferred)**

**Decision:** All persistence uses the stdlib `sqlite3` module directly (`database/db.py`'s `get_connection()`), with hand-written SQL in route functions and `database/*_queries.py` modules. No SQLAlchemy or other ORM.

**Why (inferred):** SQLite + raw SQL is the simplest thing that works for a single-file, single-server app at this scale, and avoids the setup overhead of an ORM for a project that started as a fast-moving single-developer build (see the "Day 1"/"Day 2" commit messages).

**Consequence:** `models/` and `services/` folders exist but are empty — there's no natural home for ORM model classes or a separate service layer under this architecture. See [08_UTILS_SERVICES_MODELS.md](08_UTILS_SERVICES_MODELS.md).

### ADR-2: `admin_id`-based multi-tenancy retrofitted, not designed in from day one

**Decision:** Tenant isolation is enforced by an `admin_id` column checked manually in each query, added via `database/migrate.py` (commit `90b65e3`, 2026-07-01) — after `enquiries`/`students` already existed without it.

**Why:** the git history shows this landed as a distinct retrofit commit after the initial buildout, not as part of the original schema design.

**Consequence:** isolation is inconsistent across tables — some (`enquiries`, `students`, `library_settings`, `membership_settings`) have a direct `admin_id` column with an FK; some (`cashbook`, `expenses`) have `admin_id` but no FK (added via `ALTER TABLE`, which SQLite can't constrain); `memberships` and `payments` have no `admin_id` at all and rely on a join back to `students`. There is no framework-level enforcement (e.g. row-level security) — a query that forgets the filter would leak cross-tenant data. See [04_DATABASE_SCHEMA.md](04_DATABASE_SCHEMA.md).

**How to apply:** any new admin-scoped table should follow the `enquiries`/`students` pattern (direct `admin_id` column + FK from table creation, not retrofitted later).

### ADR-3: Cashbook as the single source of truth for financial ledger, not `transactions`/`expenses`

**Decision:** All income/expense recording — both manual entries and automatic entries triggered by memberships/payments — flows through the `cashbook` table via `database/cashbook_queries.py`. The `expenses` and `transactions` tables defined in `schema.sql` are not used by any route.

**Why (inferred):** `cashbook` supports both manual and auto-generated entries with a `source` field distinguishing them, plus an audit trail (`audit_log`) — a more general design than the narrower `expenses`/`transactions` tables, which look like earlier or parallel attempts that were superseded once `cashbook` matured (commit `5b482dd`, 2026-07-05).

**Consequence:** `expenses` and `transactions` are dead schema — see [11_FUTURE_WORK.md](11_FUTURE_WORK.md) items 2–3 for the cleanup recommendation (reconcile or drop them so they don't confuse a future contributor into building against the wrong table).

### ADR-4: Auto-generated cashbook entries are read-only in the UI

**Decision:** `routes/cashbook.py`'s `edit_transaction()` explicitly refuses to edit any `cashbook` row whose `source != "Cashbook Manual Entry"`.

**Why (inferred):** rows created by `insert_income_entry()` (from membership/payment flows) are derived from — and must stay consistent with — their originating `payments`/`memberships` row. Allowing direct edits in the Cashbook UI would let the ledger drift out of sync with the record it was generated from.

**How to apply:** if you need to correct an auto-generated entry, fix it at the source (the membership/payment record), not in the Cashbook edit form. Any new auto-generating flow should set a `source` value other than `"Cashbook Manual Entry"` to get this protection automatically.

### ADR-5: Server-rendered matplotlib PNGs for Dashboard/Distribution charts, Chart.js for Cashbook/BI

**Decision:** Two different charting approaches coexist: `utils/charts.py` (matplotlib, server-side, writes a static PNG) for the Dashboard and Membership Distribution pages, versus client-side Chart.js fed by `window.cashbookChartData`/`window.biChartData` for Cashbook and Business Intelligence.

**Why (inferred):** the matplotlib charts (revenue line, membership pie/donut) predate the Chart.js-based pages chronologically (Dashboard/Distribution came earlier in the git history than Cashbook/BI), suggesting the project moved toward client-side interactive charts for newer features while leaving the original server-rendered ones in place rather than back-porting them.

**Consequence:** two genuinely different code paths to maintain, and the matplotlib path currently has the cross-tenant shared-filename issue described in [11_FUTURE_WORK.md](11_FUTURE_WORK.md) item 1 that the Chart.js path doesn't have (since Chart.js data is embedded per-request, not written to a shared file). If unifying charting approaches is ever on the table, Chart.js's per-request data model is the safer default to standardize on.

### ADR-6: No migrations framework — hand-written idempotent scripts instead

**Decision:** Schema changes are one-off Python scripts in `database/migrate_*.py`, each guarding itself with a `PRAGMA table_info` / `CREATE TABLE IF NOT EXISTS` check rather than using Alembic/Flask-Migrate with a version table.

**Why (inferred):** matches the project's overall lightweight, no-framework-beyond-Flask approach; for a single SQLite file with one active environment, a migrations framework's main benefit (coordinating schema state across many environments) doesn't yet apply.

**Consequence:** there's no single command to "bring the DB up to date" — someone has to know to run each new `migrate_*.py` script manually, in the right order, on the right machine. This has already produced one inconsistency (ADR-3's `transactions` table, defined differently in two places depending on which runs first). If the number of environments/deployments grows, revisit this.

### ADR-7: Receipt Settings extends the `library_settings` row instead of a new table, update-only

**Decision:** Receipt numbering/branding/printing preferences (`receipt_prefix`, `next_receipt_number`, `paper_size`, etc.) were added as columns on the existing `library_settings` table rather than a new `receipt_settings` table, and `database/receipt_settings_queries.py`'s `save_receipt_settings()` only supports `UPDATE` — there is no insert/upsert path. `routes/setting.py`'s `receipt_settings()` redirects to `library_profile` if no row exists yet.

**Why:** every receipt setting is inherently tied to one library profile (one row per `admin_id` already existed, one-to-one), and the page reuses that row's `logo_path`/`stamp_path`/`signature_path`/`receipt_footer` directly for its branding preview — splitting it into a second table would mean joining back to `library_settings` on every read for no isolation benefit. Requiring the profile to exist first (rather than allowing an insert with `NULL` `library_name`) avoids violating that column's `NOT NULL` constraint and keeps "receipt settings" from being independently creatable without a library profile behind it.

**Consequence:** an admin must save Library Profile at least once before Receipt Settings becomes usable — this is enforced by the redirect, not by a database constraint. If Receipt Settings is ever split out for reasons unrelated to Library Profile (e.g. a future multi-branch model with one library profile but several receipt configs), this decision would need to be revisited.

### ADR-8: Notification Settings is the single owner of reminder/channel/quiet-hour/dashboard-display preferences

**Decision:** All reminder-day, notification-channel, quiet-hours, and dashboard-display preferences live on the `library_settings` row and are read/written exclusively through `database/notification_settings_queries.py`, surfaced at Settings → Notification Settings. `membership_settings.reminder_days`/`send_reminders` — which previously held the reminder-day/send-reminders concept — are left in the table but `database/membership_settings_queries.py`'s `save_membership_settings()` no longer includes them in its INSERT/UPDATE, and `templates/settings/membership_settings.html` no longer exposes editable inputs for them. Instead, Membership Settings renders a read-only "Reminders & Notifications" summary sourced from `get_notification_settings(admin_id)`, with a link to Notification Settings.

**Why:** the same concept (which reminder days trigger a notification) had drifted into two places — `membership_settings.reminder_days`/`send_reminders` (a single day + on/off flag) and the richer `library_settings.reminder_7_days`/`reminder_3_days`/`reminder_1_day`/etc. added for Notification Settings. Keeping both editable would mean two forms writing to two different representations of the same behavior, with no clear rule for which one wins if they disagree. Notification Settings' representation is strictly more expressive (three independent day-toggles plus expiry-day/after-expiry, versus one day + one flag), so it was picked as the single source of truth; Membership Settings becomes a read-only consumer instead of a second writer.

**Consequence:** the old `membership_settings` columns are now dead weight (see TD-23 in [11_FUTURE_WORK.md](11_FUTURE_WORK.md)) — kept rather than dropped to avoid a destructive schema change for a save-only config table. Anyone extending reminder behavior should treat `library_settings`'s `reminder_*`/`notify_*` columns as the only place to add new reminder-related fields; do not resurrect `membership_settings.reminder_days`/`send_reminders` as a second writable path.

### ADR-9: Data & Backup and Security Settings use dedicated new tables, not `library_settings`

**Decision:** Unlike Receipt Settings and Notification Settings (both of which extend the existing `library_settings` row), Data & Backup uses a new `backup_log` table (one row per admin, tracking `last_backup_at`/`backup_filename`) and Security Settings uses a new `security_settings` table (one row per admin, `session_timeout_minutes`/`remember_me_enabled`/`login_notifications_enabled`), each created by their own `database/migrate_*.py` script and defined directly in `schema.sql` for fresh installs.

**Why:** Receipt Settings and Notification Settings are both legitimately tied to "does this admin have a Library Profile yet" — `receipt_settings()`/`notification_settings()` redirect to `library_profile` if the row doesn't exist, because `library_settings.library_name`/`phone` are `NOT NULL` and there's no sensible lazily-created bare row to insert. Backups and security preferences have no such dependency: an admin should be able to take a backup or set a session timeout before ever filling in a Library Profile. Extending `library_settings` for these would have imported that same "profile must exist first" restriction for no reason, or forced a workaround (allowing `NULL` on columns that are supposed to be required). Separate tables sidestep the coupling entirely — `database/backup_queries.py`'s `record_backup()` and `database/security_settings_queries.py`'s `save_security_settings()` are both plain upserts (`INSERT ... ON CONFLICT(admin_id) DO UPDATE`), no existence guard needed.

**Consequence:** two more single-purpose one-row-per-admin tables to maintain, but no artificial dependency on Library Profile being filled in first. `get_security_settings(admin_id)` returns an in-memory defaults dict (not `None`) when no row exists yet, since there's nothing to redirect to — contrast with `get_notification_settings`/`get_receipt_settings`, which return `None` and rely on the route's redirect-to-`library_profile` guard.

### ADR-10: Data & Backup exposes one backup/export action per distinct output, not one per code path

**Decision:** Data & Backup offers exactly two user-facing actions — `Export CSV` (`backup_export_csv`) and `Create Backup` (`backup_create`) — instead of separately exposing every route that can produce a `.db` file. The `backup_export_db` route (a bare `send_file(DATABASE_PATH)` passthrough with no server-side trace) was removed even though it was technically a distinct code path from `backup_create`, because both produced the same `library.db` content for the user.

**Why:** `backup_export_db` and `backup_create` differed only in bookkeeping — `backup_create` additionally copies the file into `backups/` and calls `record_backup()` to keep `backup_log`'s `last_backup_at` accurate. Exposing both as separate buttons meant a user could download an identical file via the untracked path and be left with a stale "Last Backup Date" stat, with no way to tell from the UI that one button "counts" and the other doesn't.

**How to apply:** if a future Data & Backup addition would produce output that's byte-identical (or near-identical) to an existing action, don't add a new button for it just because the underlying route differs — either fold it into the existing tracked action or make sure it does its own equivalent bookkeeping. A new route/button pair is only warranted when it produces a genuinely different artifact (as `Export CSV` does).

### ADR-11: Fee revenue (Payments) and Cashbook income are distinct metrics, never blended

**Decision:** "Total Revenue" (Dashboard), "Revenue Collected" (Membership Distribution), and the Business Health Score's fee-collection component all derive from `database/cashbook_queries.py`'s new `get_total_fee_revenue(admin_id)` — `SUM(payments.amount_paid)` — instead of `get_total_income(admin_id)` (`SUM(cashbook.amount) WHERE type = 'Income'`), even though both had been used interchangeably in different places before 2026-07-21. `get_pending_fees(admin_id)` was already fee-scoped and is unchanged; `dashboard.py` and `membership_distribution.py` now both call it instead of keeping their own copy of the same `SUM(memberships.pending_amount)` query.

**Why:** an audit of every financial calculation (2026-07-21) found that `get_total_income()` sums *all* Cashbook income, including manual, non-fee categories (`Donation`, `Library Fine`, `Book Sale`, `Membership Card Fee`, `Other Income` — see `database/cashbook_categories.py`'s `MANUAL_INCOME_CATEGORIES`), while "Pending Fees" is specifically `memberships.pending_amount` — money owed against a membership plan. The Business Health Score's collection component computed `1 - pending / (pending + total_income)`, which meant any large non-fee income entry (a real one in this DB: a single mistyped `₹100,000,567` "Library Fine" manual entry for one admin) could drag the ratio to ~100% collected regardless of the library's actual fee-collection performance, because `pending` is fee-only but the denominator wasn't. Dashboard, Membership Distribution, and Cashbook also each computed "how much has this admin been paid" via three different code paths (`SUM(payments.amount_paid)` via SQL, `SUM(memberships.paid_amount)` via SQL, and a Python `sum()` over an already-fetched row list) that happened to agree only because they were mathematically equivalent restatements of the same underlying fact — a maintenance trap, not a guarantee.

**Consequence:** "Total Revenue"/"Revenue Collected" (fee-only) will now read *lower* than Cashbook's "Total Income (All Time)" for any admin who has recorded non-fee manual income — this is correct and intentional, not a regression; the two cards mean different things and are labeled differently for that reason. Anyone adding a new financial KPI that means "money owed/collected against a membership" must call `get_pending_fees`/`get_total_fee_revenue`, not `get_total_income`/a fresh `SUM(payments.amount_paid)` copy — see the updated card for `database/cashbook_queries.py` in [FILE_REFERENCE.md](FILE_REFERENCE.md).

### ADR-12: `database/membership_queries.py` is the single owner of "effective status" and Membership Settings pricing

**Decision:** A new module, `database/membership_queries.py`, now owns: (1) the "effective status" definition — whether a membership row is *really* still active once `end_date` is compared against today, exposed as both a SQL fragment (`EFFECTIVE_STATUS_SQL`) and a Python function (`get_effective_status`); (2) the "days until expiry" expression (`DAYS_LEFT_SQL`); (3) the guard against a student ending up with two simultaneously-`Active` memberships (`get_active_membership`); (4) the active/expired count query shared by Dashboard and Membership Distribution (`get_membership_counts`); and (5) the bridge from `membership_settings` rows to a plan-name-keyed pricing dict for the Create/Renew templates (`get_plan_pricing`/`get_admission_fee`). `routes/membership.py`, `routes/dashboard.py`, `routes/student.py`, `routes/membership_distribution.py`, and `routes/notification.py` all now import from it instead of each carrying their own copy.

**Why:** TD-6 (logged 2026-07-20) predicted that "effective status," independently recomputed in 3 files, was a duplication risk that "could drift." The 2026-07-21 Membership Workflow audit found it already had: `routes/membership.py`'s `index()` (a 4th, previously-unaudited copy) showed a membership as "Active" that every other screen correctly showed as "Expired," because it selected the raw `membership_status` column with no `end_date` comparison at all. Separately, TD-7 (also logged 2026-07-20) had `membership_settings` configured via Settings but never read by Create/Renew — `create.html`/`renew.html` each hardcoded their own `{Monthly:30, Quarterly:90, ...}` JS object, so two templates already disagreed in *style* (one used `Monthly:30`, unquoted; the other `"Monthly":30`) even though their values happened to still match. Centralizing both concerns in one queries module (matching the established `cashbook_queries.py`/`bi_queries.py` pattern) closes both gaps the same way: one definition, multiple call sites, instead of N definitions that only agree by coincidence.

**Consequence:** `EFFECTIVE_STATUS_SQL` is a raw SQL fragment meant for f-string interpolation into a query that already has a `memberships m` alias in scope — it is never a bind parameter. When it's selected under an alias that collides with an existing `m.*` column (as in `routes/membership.py`'s `index()` and `routes/student.py`'s `index()`), it must be listed *before* `m.*` in the `SELECT` list, because `sqlite3.Row` resolves a duplicate column name to whichever occurrence came first (verified empirically, not documented behavior) — getting the order backwards would silently reintroduce the exact bug this ADR fixes. `create()` now redirects to `renew()` instead of inserting a second membership when `get_active_membership()` finds one already live — any future entry point that creates a membership must call this guard too. Plan pricing/duration are auto-filled from settings but remain admin-editable (not server-enforced) — a discount or a one-off custom fee is still possible, this only fixes the *default* no longer being a hardcoded, settings-oblivious number.

### ADR-13: `database/payment_queries.py` is the single owner of receipt numbering and payment recording

**Decision:** A new module, `database/payment_queries.py`, now owns every write to the `payments` table. `generate_receipt_number(conn, admin_id)` allocates the next receipt number from `library_settings.receipt_prefix`/`next_receipt_number`, advancing that counter in the same transaction as the payment. `record_payment(conn, admin_id, ...)` inserts the `payments` row and its matching automatic Cashbook Income entry — now passing `payment_id` through to `insert_income_entry()` so `cashbook.payment_id` (declared as a FK in `schema.sql` since before this ADR, but never populated) actually links back to the payment that produced it. `routes/payment.py`'s `collect()` and `routes/membership.py`'s `create()`/`renew()` all call `record_payment()` instead of each inlining their own `INSERT INTO payments` + receipt-number formula.

**Why:** the 2026-07-22 Payment Workflow Audit found the three payment-creating routes had already drifted into two incompatible receipt-number formats — `collect()` used `REC-YYYYMMDD-<membership_id>-<new_paid>`, while `create()`/`renew()` used `REC-YYYYMMDD-<membership_id>` with no amount suffix — neither of which read the `receipt_prefix`/`next_receipt_number`/`auto_increment_receipt` an admin configures on Settings → Receipt Settings (TD-22, logged 2026-07-20, still open a full audit cycle later). `collect()`'s format was also a real collision risk: truncating a running `float` total with `int()` for the suffix meant two partial payments made the same day on the same membership could land on the same integer (e.g. paid totals of `500.4` and `500.8` both truncate to `500`), producing a `UNIQUE` constraint violation on `payments.receipt_number` that no route caught — an unhandled `sqlite3.IntegrityError` on a payment. Separately, `database/migrate_backfill_cashbook_payments.py` (a real, already-shipped script) could only match a `payments` row to its Cashbook entry by `(admin_id, person, amount, entry_date)` — proof by construction that reconciling "did this payment produce exactly one ledger entry" was never actually verifiable via the FK the schema declares, only by a fuzzy heuristic that two payments with the same person/amount/date would defeat.

**Consequence:** Receipt numbers are now strictly sequential per admin and reflect their configured prefix/starting number — an admin who set `receipt_prefix="ABC"`, `next_receipt_number=3000` now actually gets `ABC-03000`, `ABC-03001`, ... instead of a `REC-...` string their settings never touched. `generate_receipt_number()` always advances the counter regardless of `auto_increment_receipt`, because no manual-receipt-number entry field exists anywhere in the UI — honoring "off" as "don't advance" would make every payment after the first fail on the `UNIQUE` constraint for that admin. That toggle remains inert until a manual-entry UI is built (still no worse than before this ADR, where it was inert for a different reason — nothing read it at all). `routes/payment.py`/`routes/membership.py` now wrap their payment-recording sequence in `try/except sqlite3.Error: conn.rollback()`, so the rare remaining collision case (or any other DB error mid-write) surfaces as a flashed error with nothing saved, not a 500 page with an already-updated `memberships` row and no matching `payments` row. Any future third payment-creating flow must call `record_payment()`, not reintroduce a fourth inline formula.

### ADR-14: Supabase (PostgreSQL) migration script hand-translated as a literal mirror of `schema.sql`, not a redesign

**Decision:** `database/supabase_migration.sql` is a line-for-line PostgreSQL translation of `database/schema.sql`, intended to be run once in the Supabase SQL Editor to stand up an equivalent schema there. Translation choices were kept mechanical: `INTEGER PRIMARY KEY AUTOINCREMENT` → `INTEGER PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY` (`BY DEFAULT`, not `ALWAYS`, so a future data-migration script can insert explicit legacy IDs); `REAL` → `DOUBLE PRECISION` (SQLite's `REAL` is an 8-byte IEEE float, PostgreSQL's own `REAL` is only 4-byte, so `DOUBLE PRECISION` is the precision-preserving translation, not `REAL`); `PRAGMA` statements dropped (no PostgreSQL equivalent); the `cashbook` table's six `ALTER TABLE ... ADD COLUMN` statements folded into its `CREATE TABLE`. No table was added, removed, renamed, or given new constraints/columns beyond what `schema.sql` already declares.

**Why:** `requirements.txt` already lists the `supabase` client library and a connectivity smoke test (`test_supabase.py`) exists, indicating a Supabase migration is underway. The ask was explicitly to translate, not redesign — so every type mapping above was chosen to be the *faithful* equivalent of the existing SQLite type/constraint, even where a "nicer" PostgreSQL-native choice exists (e.g. `NUMERIC` for money instead of `DOUBLE PRECISION`, or `BOOLEAN` instead of `INTEGER` for the many 0/1 flag columns) — those would be schema redesign decisions, deliberately left for a future ADR if the project decides to make them.

**Consequence:** The app itself (`database/db.py`, every `routes/*.py`, every `database/*_queries.py`) still talks to SQLite via `sqlite3` — this script only creates a parallel, currently-unused PostgreSQL schema. Until a connection-layer cutover happens, `schema.sql` and `supabase_migration.sql` are two hand-maintained copies of the same design that **will drift** if one is edited without the other — the same category of risk ADR-3/TD-2 already describes for `expenses`/`transactions`. See TD-34. The many `INTEGER` 0/1 "boolean" columns (`demo_done`, `auto_expiry`, `remember_me_enabled`, etc.) and financial `REAL`/`DOUBLE PRECISION` columns are prime candidates to reconsider (`BOOLEAN`, `NUMERIC`) at actual cutover time, once the app's queries are being rewritten anyway and a real redesign is in scope — not before.

### ADR-15: `migrate_to_supabase.py` uses the Supabase Python client only, with a print-SQL fallback for identity-sequence resets

**Decision:** `database/migrate_to_supabase.py` copies `library.db`'s rows into the Supabase tables created by ADR-14's `supabase_migration.sql` using only the `supabase`/`postgrest` Python client (REST over HTTP), matching the pattern `test_supabase.py` already established — no `psycopg2`/direct Postgres connection string was added. Since PostgREST has no endpoint for arbitrary SQL, resetting each table's identity sequence after preserving legacy primary keys (`setval(...)`) can't be done through the client alone. The script instead calls an *optional* RPC, `migrate_reset_identity_sequence(p_table, p_id_column, p_value)`, and if that function doesn't exist in the target project (it does not, by default — creating it would itself be a schema change, out of this script's scope), it prints the exact `setval(pg_get_serial_sequence(...), ...)` statements for the user to paste into the Supabase SQL Editor once, at the end of the migration report.

**Why:** the task that produced this script explicitly scoped it to "only create `database/migrate_to_supabase.py` and any minimal documentation," ruling out adding a new dependency (`psycopg2`) or touching the schema (creating the helper RPC server-side). The Supabase client's REST-only nature is a real, permanent constraint, not an oversight — better to surface it honestly (print exact, copy-pasteable SQL) than to silently leave sequences unreset or fabricate a connection method the project doesn't otherwise use.

**Consequence:** Data import and row-count verification never depend on the sequence-reset step succeeding — a table can be fully migrated and verified while still needing a manual one-line SQL statement afterward. If a project later adds a generic SQL-exec RPC (or `migrate_reset_identity_sequence` specifically) to Supabase for other tooling, this script will pick it up automatically and stop printing manual fallback SQL for that table, with no code change required.

### ADR-16: App connection-layer cutover to Supabase happens incrementally, module by module — `routes/auth.py` first

**Decision:** Rather than cutting every route over to Supabase in one change, the app's connection layer is being migrated one module at a time, starting with `routes/auth.py` (login/register/forgot-password). A new reusable client, `database/supabase_client.py`'s `get_supabase_client()` (cached with `functools.lru_cache`, mirroring `database/db.py`'s `get_connection()` role but for Supabase), replaces `database.db.get_connection()` in that one file only. Every other route/`database/*_queries.py` module is untouched and continues reading/writing SQLite exactly as before. Routes, templates, business logic, and validation in `routes/auth.py` are unchanged — only the persistence calls were swapped, `.eq()`-filtered against the `admins` table Supabase already has (via ADR-14/ADR-15's schema translation and one-time data copy).

**Why:** a single big-bang cutover of every module at once is high-risk (13 blueprints, ~30 templates, no query-module abstraction for several of them) and hard to verify incrementally. `routes/auth.py` is the smallest, most self-contained candidate — it touches exactly one table (`admins`), has its own dedicated test file (`tests/test_01_auth.py`), and its own `tests/conftest.py`'s `new_admin` fixture already isolates every other test suite from needing to know how admin accounts are created. Cutting it over first, verifying the full test suite still passes, and only then moving to the next module keeps each step independently reviewable and revertible.

**Consequence — a real, temporary split-brain on `admins.password` (see TD-35):** `routes/auth.py`'s `forgot_password()` updates `admins.password` in Supabase only. `routes/setting.py`'s `security_settings()` (Settings → Security Settings → Change Password) still updates it in SQLite only — that route wasn't touched, per this same incremental-scope decision. Until Settings is migrated too, a password changed via Settings has no effect on login (login checks Supabase's copy, which the SQLite-only write never reached), and a password reset via `forgot_password()` is likewise invisible to `security_settings()`'s "current password" check (still SQLite). This is a known, accepted cost of doing the migration incrementally rather than all at once — the alternative (migrating `routes/setting.py`'s password-change branch in the same change) was ruled out to keep this step scoped to the auth module only, matching the stated incremental-migration plan.

**Consequence — `register()` needed a SQLite mirror-write, not a pure Supabase swap, to keep the rest of the app from breaking for new admins:** unlike `login()`/`forgot_password()`, `register()` creates a brand-new `admin_id`. Seven other still-SQLite tables enforce a real SQLite foreign key back to `admins.admin_id` (confirmed directly in `database/schema.sql`, not inferred): `enquiries` (`routes/enquiries.py`), `students` (`routes/student.py`), `audit_log` (written transitively from three modules — `routes/cashbook.py`, `routes/membership.py`, and `routes/payment.py` all eventually call `database/audit_queries.py`'s `log_entry()` via `database/cashbook_queries.py`), and `library_settings`/`membership_settings`/`backup_log`/`security_settings` (all four owned by `routes/setting.py`). `cashbook`/`expenses` also carry an `admin_id` column but were added via `ALTER TABLE ADD COLUMN`, which SQLite can't attach a `FOREIGN KEY` to, so those two don't enforce anything. `database/db.py`'s `get_connection()` sets `PRAGMA foreign_keys = ON` on every connection, so all 7 are actively enforced, not latent. Running the full test suite against the initial pure-Supabase version of `register()` surfaced this immediately: 74 failures, all `sqlite3.IntegrityError: FOREIGN KEY constraint failed` or its downstream `database is locked` symptom, every one traced back to a newly-registered admin (via `tests/conftest.py`'s `new_admin` fixture) that existed in Supabase but not in SQLite. In production this specific path is rare — `register()` already flashes "available only during initial setup" once any admin exists — but it would still hit a fresh deployment's very first admin at the worst possible moment: signup succeeds, then every other feature they try immediately breaks. Given this session's explicit "ensure the app remains runnable after each step" requirement, `register()` was changed to insert into Supabase first (the new source of truth for login), then mirror the same row — same `admin_id`, `full_name`, `username`, `mobile`, `email`, hashed `password`, `role` — into SQLite's `admins` table, rolling back the Supabase insert if the SQLite mirror fails (`try/except sqlite3.Error`, `supabase.table("admins").delete().eq("admin_id", ...)`). `login()` and `forgot_password()` remain pure Supabase reads/writes — this mirror is specific to `register()`'s FK-creation problem, not a general both-databases policy.

**Also new in this change:** every Supabase call in `routes/auth.py` that carries user-controlled input is wrapped in `try/except postgrest.exceptions.APIError`. This isn't new business logic — it's error handling for a failure mode SQLite never had: PostgREST encodes `.eq()`/`.select()` filter values into the request's GET query string, and Supabase's Cloudflare-fronted edge network was observed, live, to return an HTTP 403 WAF block for adversarial-looking query strings (confirmed via `tests/test_01_auth.py`'s existing SQL-injection-payload tests, e.g. a username containing `DROP TABLE`) before the request reaches Postgres at all. Without the `try/except`, that 403 surfaces as an unhandled `APIError` → Flask's generic 500 handler — worse than SQLite's graceful "Invalid username" for the same input. The `except` blocks degrade to the same outcome the equivalent "no match" branch already produced (or a generic "Something went wrong" flash for `register()`'s existence-check/insert calls), so normal (non-adversarial) behavior is completely unchanged. Actual SQL-injection safety is unaffected either way — `.eq()` values are never string-interpolated into a query, so injection was never possible; this is purely about not crashing on input that happens to look like an injection attempt.

**How to apply:** the next module to migrate should follow the same shape — add/extend `database/supabase_client.py` usage in that module only, leave every other module on SQLite, run the full test suite (not just that module's own tests — the FK-mirror issue above was only caught by running everything), and update this table's status in [04_DATABASE_SCHEMA.md](04_DATABASE_SCHEMA.md) and [11_FUTURE_WORK.md](11_FUTURE_WORK.md)'s TD-34/TD-35 rows. If `routes/setting.py`'s `security_settings()` is the next slice (closing TD-35's password-sync half), it should reuse `database/supabase_client.py`'s `get_supabase_client()`, not roll its own client. Note that migrating all of `routes/setting.py` only closes 4 of the 7 FK dependencies (`library_settings`/`membership_settings`/`backup_log`/`security_settings`) — `enquiries`, `students`, and `audit_log` belong to three separate modules (Enquiries, Students, and Cashbook/Membership/Payment respectively) and must each migrate too before `register()`'s SQLite mirror-insert can be deleted. Re-check after each of those migrations whether any FK dependency remains before removing the mirror — removing it early would reintroduce the exact `sqlite3.IntegrityError: FOREIGN KEY constraint failed` this ADR fixed.

### ADR-17: Settings module's second Supabase slice is scoped to the password-change branch only — the rest of `routes/setting.py` stays on SQLite

**Decision:** Following ADR-16's incremental plan, `routes/setting.py`'s `security_settings()` password-change branch (`form_type == "password"`) now reads/writes `admins.password` via `database/supabase_client.py`'s `get_supabase_client()`, reusing the exact client `routes/auth.py` already uses — no new client code. Nothing else in `routes/setting.py` was touched: `library_profile()`, `membership_settings()`, `receipt_settings()`, `notification_settings()`, `staff_access()`, `data_backup()`/`backup_export_csv()`/`backup_create()`, and `security_settings()`'s own session-preferences half (`session_timeout_minutes`/`remember_me_enabled`/`login_notifications_enabled`, saved via `database/security_settings_queries.py`) all continue reading/writing SQLite exactly as before. Routes, templates, business logic, and validation are unchanged — the current-password check, new/confirm-password match check, and `routes.auth.validate_password` strength check all run identically; only the two `admins` table calls (`SELECT`/`UPDATE`) were swapped from `sqlite3` to Supabase `.eq()` filters, wrapped in `try/except postgrest.exceptions.APIError` matching `routes/auth.py`'s existing pattern for the same table.

**Why:** this is the natural second slice ADR-16's "How to apply" section named directly — same table (`admins`), same client, same shape as the auth cutover, and it closes TD-35's `admins.password` split-brain (a password changed via Settings previously had no effect on login, since login already reads Supabase). Scoping it to only the password branch (not all of `routes/setting.py`) keeps the change small and independently verifiable, consistent with ADR-16's "each step independently reviewable and revertible" rationale. The other four tables `routes/setting.py` owns (`library_settings`, `membership_settings`, `backup_log`, `security_settings` itself) have no `admins`-style split-brain risk — nothing else reads or writes them from a second location the way `login()`/`forgot_password()`/`security_settings()` all touched `admins.password` — so migrating them now would be scope creep against this session's explicit "Settings module... only" instruction, not a fix for anything broken.

**Consequence — `register()`'s SQLite mirror-insert bridge (TD-35) is unaffected and still fully required:** this slice changed `admins.password`'s writer, not `admins.admin_id`'s existence. The 7 tables with a real SQLite FK to `admins.admin_id` (`enquiries`, `students`, `audit_log`, and `routes/setting.py`'s own `library_settings`/`membership_settings`/`backup_log`/`security_settings`) are untouched by this change — `register()` must keep mirroring new admin rows into SQLite until all 7 (not just the password column) are migrated. Migrating Settings' password branch closes 0 of those 7 FK dependencies; it only closes the separate `admins.password` value-sync problem TD-35 also described.

**How to apply:** the next slice should pick one of the remaining SQLite-only tables/modules (e.g. `routes/setting.py`'s `library_settings`/`membership_settings`/`backup_log`, or `routes/enquiries.py`'s `enquiries`, or `routes/student.py`'s `students`) and repeat this same pattern — reuse `database/supabase_client.py`, touch only that table's read/write calls, leave everything else (routes, templates, validation, other tables) untouched, and run the full suite afterward. Only once all 7 FK-dependent tables are migrated can `register()`'s SQLite mirror-insert be safely deleted — check the remaining count in TD-35 before removing it.

### ADR-18: Enquiries is the third Supabase slice — and the first one that needed its own two-way SQLite mirror, not just a one-time bridge insert

**Decision:** `routes/enquiries.py` (`index()`, `add()`, `edit()`, `delete()`, `view()`) now reads/writes the `enquiries` table via `database/supabase_client.py`'s `get_supabase_client()`, the same client `routes/auth.py` (ADR-16) and `routes/setting.py` (ADR-17) use. Supabase is the source of truth for every read (`index()`'s list, `edit()`'s/`view()`'s single-row fetch). Unlike `register()`'s one-shot mirror-insert, this slice needed a mirror kept in sync across **three** write paths, not one: `add()` mirrors the new row (same `enquiry_id`) into SQLite; `edit()` updates Supabase then applies the identical update to the SQLite mirror; `delete()` deletes from Supabase (authoritative) then best-effort deletes the SQLite mirror row, swallowing `sqlite3.Error` rather than rolling back the Supabase delete. `index()` still needs a `students` lookup to attach `student_id` per enquiry the way the old `LEFT JOIN students s ON s.enquiry_id = e.enquiry_id` did — `students` stays in SQLite (out of scope this session), so `index()` fetches Supabase's enquiries, separately queries SQLite for this admin's `enquiry_id → student_id` pairs, and merges them in Python instead of a database-level join. Routes, templates, validation, and business logic are otherwise unchanged; `followup_date` gained a small new `_sanitize_date()` normalization step (see the "Why" below) but every other field is untouched.

**`add()`'s `enquiry_id` is computed explicitly, not taken from Supabase's auto-assigned identity value:** a first-draft version of this change let Supabase's `GENERATED BY DEFAULT AS IDENTITY` column assign `enquiry_id` (mirroring `register()`'s pattern for `admin_id`), then mirrored that value into SQLite. Running the full test suite immediately surfaced every single `add()` as a failure: Supabase's `enquiries` identity sequence was seeded once by the one-time data copy (ADR-15) and had advanced only via this session's own testing, while SQLite's `AUTOINCREMENT` counter had kept climbing across every prior QA/test session since that copy (`enquiries` was still SQLite-only until today) — live-verified at `enquiry_id` 599 on Supabase's side vs. 1012 already used in SQLite. Supabase therefore kept re-issuing ids SQLite had already claimed, the SQLite mirror-insert's `PRIMARY KEY` collided every time, and `add()`'s own rollback (delete the Supabase row, flash an error) fired on every attempt — cascading into 45 failures across `test_02`/`test_03`/`test_04`/`test_05`/`test_07`/`test_09` (anything that calls the `make_enquiry` test helper). No `migrate_reset_identity_sequence` RPC exists in this project (ADR-15 already documented this as optional, and it was never created), and this codebase deliberately has no direct-Postgres/`psycopg2` path to run a manual `setval(...)` — so `add()` was changed to compute `enquiry_id` itself, as `SELECT MAX(enquiry_id) FROM enquiries` (SQLite) `+ 1`, and pass that explicit value to the Supabase insert (legal specifically because the column is `GENERATED BY DEFAULT`, not `ALWAYS` — see `supabase_migration.sql`'s translation notes). SQLite's max is always the safe upper bound going forward too, since every future `add()` writes the identical id to both databases in the same request, keeping them in lockstep from here on — the one-time gap only needed bridging once, at the first synchronized insert.

**Why:** `students.enquiry_id` has a real SQLite foreign key to `enquiries.enquiry_id` (`database/db.py` sets `PRAGMA foreign_keys = ON` on every connection), exactly like `admins.admin_id`'s FK problem in ADR-16 — but here the dependency is deeper than `register()`'s one-shot insert. `routes/student.py`'s `admission()` (explicitly out of this session's scope — "Do not modify Students... in this step") does three things directly against SQLite: reads the full enquiry row (`full_name`/`mobile`/`purpose`/`preferred_shift`) to populate the new student, inserts the student row with a real FK to `enquiry_id`, and afterward runs `UPDATE enquiries SET status='Admitted' WHERE enquiry_id=?`. Since that route can't be touched, `add()` alone (a one-shot mirror like `register()`'s) wasn't enough — if an admin edited an enquiry's mobile number after creation and `edit()` only wrote to Supabase, `admission()` would silently admit the student with the stale pre-edit mobile number read from SQLite, a real correctness bug, not just a missing-row crash. Making `edit()` (and, for symmetry/cleanliness, `delete()`) dual-write closes that specific gap without touching `routes/student.py`. Postgres's `followup_date DATE` column is strictly typed (unlike SQLite's dynamic typing, which silently accepted `""`/`"not-a-date"` and stored it verbatim) — `_sanitize_date()` converts blank/unparsable input to `NULL` before the Supabase call instead of letting `postgrest.exceptions.APIError` (invalid date syntax) surface as an unhandled 500, the same category of new failure mode ADR-16 already documented for adversarial-looking query strings.

**Consequence — a new, real split-brain this slice could not close (TD-36):** `admission()`'s `UPDATE enquiries SET status='Admitted' ...` is SQLite-only and untouched by this change. After a student is admitted, the SQLite mirror's `status` becomes `"Admitted"`, but Supabase's copy — the one `index()`/`edit()`/`view()` now actually read — stays whatever it was before (`"Interested"` by default). The Enquiries list/detail pages will therefore keep showing the pre-admission status and the "Admission" action instead of flipping to the "Admitted" badge and "View Student" link, even though `student_id` (read from SQLite, unaffected) correctly shows the enquiry has in fact been admitted. No test in this session's suite exercises "view Enquiries after admission," so nothing regressed there, but this is a real, user-visible gap, not a theoretical one — see TD-36. This is structurally the same category of consequence as TD-35 (ADR-16/17), just surfacing on a `status` column instead of `password`.

**Consequence — `register()`'s SQLite mirror-insert bridge is now partially, not fully, redundant for `enquiries` specifically, but still required:** `enquiries` is one of the 7 tables `register()`'s bridge exists for. This slice doesn't let that bridge be deleted — a newly registered admin's SQLite row is still needed for `add()`'s own mirror-insert to satisfy `enquiries.admin_id`'s SQLite FK, and `students`/`audit_log`/the rest of `routes/setting.py`'s tables are still unmigrated. Track the remaining count in TD-35.

**How to apply:** the next slice should be `routes/student.py`'s `students` table — migrating it would let `admission()`'s three SQLite operations move to Supabase too, closing TD-36's status split-brain at the source (rather than by, say, having `routes/enquiries.py` poll for status changes, which would be a workaround, not a fix) and removing one more of `register()`'s 7 FK dependencies. Until then, anyone touching `admission()` for an unrelated reason should know it's reading a SQLite mirror that `routes/enquiries.py` keeps in sync only for `full_name`/`mobile`/`purpose`/`preferred_shift`/`followup_date`/`remarks` — not for `status`, which flows the other direction (SQLite → nowhere, since Supabase is never told).

### ADR-19: Students is the fourth Supabase slice — closes TD-36 at the source, but the widest fan-out of unmigrated dependents seen so far

**Decision:** `routes/student.py` (`index()`, `admission()`, `view()`, `edit()`) now reads/writes the `students` table via `database/supabase_client.py`'s `get_supabase_client()`, the same client `routes/auth.py` (ADR-16), `routes/setting.py` (ADR-17), and `routes/enquiries.py` (ADR-18) already use. Supabase is the source of truth for every read. Like `enquiries` (ADR-18) and unlike `register()`'s one-shot mirror-insert, this slice needed an ongoing, per-write SQLite mirror: `admission()` mirrors the new row (same explicit `student_id`, computed as `SELECT MAX(student_id) FROM students` (SQLite) `+ 1` for the identical reason ADR-18 needed this for `enquiry_id` — Supabase's identity sequence, seeded once by the one-time data copy, ADR-15, trails SQLite's ever-climbing counter); `edit()` updates both, not best-effort. `admission()` also now reads/writes the `enquiries` row it needs directly against Supabase (via the same client) instead of the SQLite mirror `routes/enquiries.py` maintained for it — its guard-check read (`SELECT * FROM enquiries WHERE enquiry_id=? AND admin_id=?`) and its `status='Admitted'` write both now target Supabase, the copy `routes/enquiries.py` itself reads for the Enquiries pages. `index()` no longer runs the old correlated-subquery `LEFT JOIN memberships` against `students` in one query — it fetches Supabase's students list, separately queries SQLite for this admin's latest-membership-per-student (`EFFECTIVE_STATUS_SQL`, unchanged), and merges the two in Python, the same shape ADR-18 used for `enquiries.index()`'s `student_id` merge. `edit()`'s duplicate-mobile handling changed from a post-write `sqlite3.IntegrityError` catch to a pre-write existence check against Supabase (mirroring `routes/auth.py`'s `register()` username/mobile check), since a Supabase unique-violation can't be told apart from any other `postgrest.exceptions.APIError` without parsing its error code — check-first is the more direct fit for the new backend, and preserves the exact same user-facing message. `join_date` gained a `_sanitize_date()` normalization step, identical in shape to `routes/enquiries.py`'s `followup_date` handling, for the same reason (Postgres's `DATE` column is strictly typed, unlike SQLite's).

**Why:** requested as the next incremental-migration slice, explicitly naming Students and asking for a determination of whether Enquiries' SQLite mirror was still needed afterward. This matches ADR-18's own "How to apply" recommendation: `students` closes TD-36 at the source (rather than a workaround on the Enquiries side), and is one of `register()`'s 7 FK-dependent tables. Investigating the dependency graph the same way ADR-16/ADR-18 did surfaced a materially wider fan-out than `enquiries` had: `memberships.student_id` is a real SQLite FK (`database/db.py` sets `PRAGMA foreign_keys = ON` on every connection), and **eight** other modules run raw `JOIN students`/`SELECT * FROM students` directly against SQLite — `routes/membership.py`, `routes/payment.py`, `routes/dashboard.py`, `routes/membership_distribution.py`, `routes/notification.py`, `routes/setting.py`'s `backup_export_csv()`/`backup_create()`, `database/bi_queries.py`, `database/cashbook_queries.py`, and `database/membership_queries.py` — none of which this session's scope permitted touching. This is why the SQLite mirror could not be a one-shot bridge (as `register()`'s is) or dropped once Supabase became the source of truth for `routes/student.py` itself: it is genuinely load-bearing for eight other files' correctness, not transitional scaffolding for `students` alone.

**Post-migration determination on the Enquiries SQLite mirror (explicitly requested):** the mirror `routes/enquiries.py` maintains (ADR-18) is **still required**, for two reasons unrelated to `students` migrating: (1) `routes/dashboard.py`'s `index()` runs a plain `SELECT COUNT(*) FROM enquiries` against SQLite for its "Total Enquiries" KPI — untouched, out of this session's scope, and it would silently under/over-count if the mirror stopped being written; (2) `routes/enquiries.py`'s own `index()`/`view()` still query SQLite's `students` table (not Supabase) to build the `enquiry_id → student_id` map — also untouched. What this slice *did* change is which write reaches Supabase: `admission()` now updates `enquiries.status` in Supabase directly, instead of the SQLite mirror only, closing TD-36's split-brain — but the mirror's row existence and its other columns (`full_name`/`mobile`/`purpose`/`preferred_shift`/`followup_date`/`remarks`, kept in sync by `routes/enquiries.py`'s own `add()`/`edit()`) remain exactly as necessary as ADR-18 left them, for exactly the reasons ADR-18 gave — this slice neither removed nor added a dependency on that data.

**Consequence — TD-36 is now `Resolved`:** `enquiries.status` has a single writer again (`admission()`, writing Supabase directly), the same shape as TD-35's `admins.password` resolution (ADR-17). The Enquiries list/detail pages now correctly reflect a just-completed admission's status and offer "View Student" instead of a stale "Admission" action.

**Consequence — `register()`'s SQLite mirror-insert bridge (TD-35) is unaffected and still fully required, and the `students`/`enquiries` SQLite mirrors themselves are not yet removable:** `students` is one of the 7 tables `register()`'s bridge exists for; this slice doesn't let that bridge be deleted, for the identical reason ADR-18's `enquiries` slice didn't — `admission()`'s own SQLite mirror-insert still needs `students.admin_id`'s SQLite FK to resolve, so a new admin's SQLite row is still required. `audit_log` and the rest of `routes/setting.py`'s tables (`library_settings`/`membership_settings`/`backup_log`/`security_settings`) remain unmigrated and still require it too. Separately — and distinctly from the `admins.admin_id` FK question — the `students`/`enquiries` SQLite *mirrors* (as opposed to the `admins` mirror-insert bridge) can only be deleted once every one of the modules named in the "Why" section above (for `students`) and Dashboard's enquiry count / Enquiries' own student lookup (for `enquiries`) are migrated too; that is a materially larger remaining slice than the `admins.admin_id` FK question alone.

**How to apply:** the next slice should pick one of the remaining SQLite-only tables (`audit_log`, `library_settings`, `membership_settings`, `backup_log`, `security_settings` — all four of the latter owned by `routes/setting.py`) to close more of `register()`'s 7 FK dependencies, or, if reducing the `students`/`enquiries` SQLite mirrors' footprint is the goal instead, migrate one of the eight modules named above (Membership and Payment are the natural pair, since they already share `database/payment_queries.py`/`database/membership_queries.py` and would let `memberships`/`payments` move to Supabase together) — check which of `students`'/`enquiries`' remaining SQLite consumers that would close before assuming either mirror can be trimmed.

### ADR-20: Membership is the fifth Supabase slice — Payment deliberately deferred despite ADR-19's pairing suggestion

**Decision:** `routes/membership.py` (`index()`, `create()`, `renew()`) now reads/writes the `memberships` table via `database/supabase_client.py`'s `get_supabase_client()`, the same client `routes/auth.py` (ADR-16), `routes/setting.py` (ADR-17), `routes/enquiries.py` (ADR-18), and `routes/student.py` (ADR-19) already use. Supabase is the source of truth for every read. Like `enquiries`/`students` and unlike `register()`'s one-shot mirror-insert, this slice needed an ongoing, per-write SQLite mirror: `create()`/`renew()` mirror the new/updated row (same explicit `membership_id`, computed as `SELECT MAX(membership_id) FROM memberships` (SQLite) `+ 1`, the same fix ADR-18/ADR-19 needed for `enquiry_id`/`student_id` since Supabase's identity sequence — seeded once by the one-time data copy, ADR-15 — trails SQLite's ever-climbing counter). `index()` no longer runs the old `EFFECTIVE_STATUS_SQL`-decorated `JOIN students` query directly against SQLite — it fetches this admin's students from Supabase (`routes/student.py`, ADR-19) to build a `student_id → {full_name, mobile}` map, fetches `memberships` scoped to those student ids from Supabase, and merges the two in Python, computing effective status per row with `database/membership_queries.py`'s existing `get_effective_status()` — the same cross-table-merge shape ADR-18/ADR-19 used for `enquiries.py`'s/`student.py`'s own merges in the other direction. `database/membership_queries.py`'s `get_active_membership()` — `create()`'s duplicate-active-membership guard, and (confirmed by grep) its only caller anywhere in the codebase — now reads Supabase directly too, instead of the SQLite mirror the rest of that module still serves; every other export in that module (`EFFECTIVE_STATUS_SQL`, `DAYS_LEFT_SQL`, `get_membership_counts`, `get_effective_status`) is untouched and stays SQL/SQLite-backed, since `routes/dashboard.py`, `routes/membership_distribution.py`, `routes/notification.py`, and `routes/student.py` all still call them directly against the SQLite mirror. `renew()` additionally now captures which row(s) it's about to flip from `Active` to `Expired` *before* doing so (on both databases), so a failure partway through the request — an `APIError` on the Supabase insert, or a `sqlite3.Error` on the mirror-write — can restore exactly those rows to `Active` and delete the half-inserted new row, rather than leaving a partial expire-without-replace state; the original SQLite-only version didn't need this because a single connection's transaction already made the expire-then-insert atomic, a guarantee that's gone once the two steps span two separate databases. Routes, templates, validation, pricing rules (Membership Settings auto-fill), and the renew workflow are otherwise unchanged. A new helper, `_sanitize_int()` (same shape as `routes/student.py`'s `_sanitize_date()`), converts `duration_days` to an int or `None` before any Supabase call, since Postgres's `duration_days` column is a strictly-typed `INTEGER` unlike SQLite's, which silently accepted the raw form string.

**Why:** requested as the next incremental-migration slice, explicitly scoped to Membership only (`routes/membership.py`/`database/membership_queries.py`), with Payments and Cashbook explicitly excluded from this step even though ADR-19's own "How to apply" section had named Membership+Payment as "the natural pair, since they already share `database/payment_queries.py`/`database/membership_queries.py`." Investigating the dependency graph the same way ADR-16/18/19 did confirmed `memberships.student_id` is a real SQLite FK and four modules — `routes/payment.py`'s `collect()`, `routes/dashboard.py`, `routes/membership_distribution.py`, and `routes/notification.py` — all run raw `JOIN memberships` directly against SQLite; none of those were touched, per this session's explicit scope, so (as with `students`/`enquiries` before it) the SQLite mirror could not be a one-shot bridge or dropped once Supabase became authoritative for `routes/membership.py` itself — it is genuinely load-bearing for those four files, not transitional scaffolding for `memberships` alone. `get_active_membership()`'s move to Supabase-only reads (rather than continuing to read the SQLite mirror, which stays perfectly in sync with every `create()`/`renew()` write in the same request) was a deliberate choice for architectural clarity: it is private to the module being migrated (confirmed by grep — no other file imports it), so there's no reason for the one function `routes/membership.py` uses to guard its own writes to read a mirror instead of the source of truth it just wrote.

**Consequence — a new, real split-brain this slice could not close (TD-37):** `routes/payment.py`'s `collect()` (explicitly out of scope this session, per "Do not migrate Payments or Cashbook in this step") updates `memberships.paid_amount`/`pending_amount` in **SQLite only**. After a payment is collected against an existing membership, the SQLite mirror's `paid_amount`/`pending_amount` are correct (and everything that reads SQLite — Dashboard, Membership Distribution, Notifications, the Student detail page — sees the update immediately), but Supabase's copy of those same two columns — the one `routes/membership.py`'s `index()` now reads — keeps the pre-payment values until the next time that row is written by `create()`/`renew()` (which a payment collection never triggers). This is structurally the same category of consequence as TD-35 (`admins.password`, ADR-16/17) and TD-36 (`enquiries.status`, ADR-18/19) — a column with two writers that don't agree — surfacing here on `memberships.paid_amount`/`pending_amount` instead. Unlike TD-35/TD-36, this one cannot be closed by making the *unmigrated* side write Supabase directly without that being a de facto Payment migration, which this session's explicit scope ruled out; it can only be closed by migrating `routes/payment.py` itself, the natural next slice.

**Consequence — `register()`'s SQLite mirror-insert bridge (TD-35) is unaffected and still fully required, and the `students`/`enquiries` SQLite mirrors are also unaffected:** `memberships` was never one of `register()`'s 7 FK-dependent tables (that FK runs through `students.admin_id`, not directly from `memberships`), so this slice doesn't touch that bridge at all. It also doesn't close any part of the `students`/`enquiries` SQLite mirrors' remaining consumer list from ADR-18/19 — `routes/membership.py`'s own student lookups moved off SQLite onto Supabase (one fewer consumer of the `students` mirror, noted in [09_DEPENDENCY_MAP.md](09_DEPENDENCY_MAP.md)), but the mirror itself is still required for the other modules ADR-19 listed.

**How to apply:** the next slice should be `routes/payment.py` — migrating it would close TD-37 at the source (the same way ADR-19's Students slice closed TD-36 at the source, by moving the *stale writer* onto Supabase rather than working around it from the other side) and would let the `memberships` SQLite mirror's remaining consumer list shrink to `routes/dashboard.py`/`routes/membership_distribution.py`/`routes/notification.py`. Alternatively, one of the remaining SQLite-only tables (`audit_log`, `library_settings`, `membership_settings`, `backup_log`, `security_settings`) could be picked instead to keep closing `register()`'s FK dependencies — that work is orthogonal to `memberships`/`payments` and can proceed independently.

### ADR-21: Payment is the sixth Supabase slice — closes TD-37 at the source, and corrects ADR-20's remaining-mirror-consumer list

**Decision:** `routes/payment.py`'s `collect()` now reads/writes the `memberships` table's `paid_amount`/`pending_amount` columns via `database/supabase_client.py`'s `get_supabase_client()`, the same client and the same `memberships` table `routes/membership.py` (ADR-20) already uses. Supabase is the source of truth: `collect()` fetches the target membership by `membership_id` from Supabase, then verifies it belongs to the logged-in admin with a `students` ownership check (`.eq("student_id", ...).eq("admin_id", ...)`, also Supabase, ADR-19) — reproducing the original SQLite query's combined "exists AND belongs to this admin" semantics as two sequential reads instead of one `JOIN`, with the identical "Membership not found" outcome either way. The pending-balance update writes Supabase **first** (`.update({"paid_amount": ..., "pending_amount": ...}).eq("membership_id", ...)`), then mirrors the identical update into the SQLite `memberships` row, inside the same `try/except sqlite3.Error` block that already wraps `database/payment_queries.py`'s `record_payment()` (the `payments`/`cashbook`/`audit_log` writes, all still SQLite-only and untouched by this slice). If the SQLite mirror-write or `record_payment()` fails, the Supabase update is explicitly reverted to its pre-payment `paid_amount`/`pending_amount` before flashing the error — the same "don't let the source of truth advance ahead of a rolled-back write" shape ADR-20's `renew()` established for its expire-then-insert sequence. Routes, templates, validation (numeric/positive/`<= pending_amount`/no-pending-balance-to-collect checks), and receipt generation are unchanged. `index()` is untouched — it still runs its own raw SQL `payments JOIN students` query directly against SQLite; neither table is part of this slice.

**Why:** requested as the next incremental-migration slice, explicitly naming TD-37 as the target. ADR-20's own "How to apply" section had already identified this as the natural next step: TD-37 exists because `collect()`'s pending-balance update was SQLite-only while `routes/membership.py`'s `index()` (the page an admin actually looks at) reads Supabase — the fix is moving the *stale writer* onto Supabase, the same shape ADR-19's Students slice used to close TD-36 (`enquiries.status`) at the source, rather than a workaround on the read side (e.g. having `index()` poll SQLite for staleness, which would just be a different, worse split-brain). Re-checking the dependency graph the same way ADR-16/18/19/20 did (grep every unmigrated module for a raw `JOIN memberships`/`memberships.pending_amount` reference) found ADR-20's own prediction of the mirror's remaining consumers — `routes/dashboard.py`/`routes/membership_distribution.py`/`routes/notification.py` — was incomplete: it missed `routes/student.py`'s `view()` (`SELECT * FROM memberships WHERE student_id=?`, the Student detail page's membership card), `database/cashbook_queries.py`'s `get_pending_fees()` (`SUM(memberships.pending_amount)`, which Dashboard/Membership Distribution/the Business Health Score's fee-collection component all depend on via ADR-11), and `database/bi_queries.py`'s `get_membership_retention()`/`get_upcoming_expiries()`. All are still unmigrated and still require the SQLite mirror to stay current, so `collect()` keeps writing it (via the same mirror `create()`/`renew()` maintain) rather than treating ADR-20's shorter list as authoritative.

**Consequence — TD-37 is now `Resolved`:** `memberships.paid_amount`/`pending_amount` have a single writer-of-record again (Supabase) across `routes/membership.py`'s `create()`/`renew()` and `routes/payment.py`'s `collect()`, the same shape as TD-35's `admins.password` (ADR-16/17) and TD-36's `enquiries.status` (ADR-18/19) resolutions. The Memberships page now reflects a payment collected via `/payments/collect/<id>` immediately — verified by a new test asserting the "Collect Payment" action (rendered only while `pending_amount > 0`) disappears from `/memberships/` right after a full-balance `collect()`, not just by re-reading the raw table.

**Consequence — `register()`'s SQLite mirror-insert bridge (TD-35) and the `students`/`enquiries` SQLite mirrors (ADR-18/19) are all unaffected:** this slice only changed which database `collect()`'s `memberships` write reaches first; it added no new table, touched no `admin_id`/`enquiry_id`/`student_id` FK dependency, and `payments` (which `collect()`'s `index()` sibling and `record_payment()` both still read/write) remains entirely SQLite-only, read directly by `routes/payment.py`'s own `index()`, `routes/membership_distribution.py`, `routes/student.py`'s `view()`, `utils/charts.py`, and `database/cashbook_queries.py`/`database/migrate_backfill_cashbook_payments.py`.

**How to apply:** the `memberships` SQLite mirror itself is not yet removable — the next slice that would shrink it further is migrating one of its remaining consumers (`routes/dashboard.py`, `routes/membership_distribution.py`, `routes/notification.py`, `routes/student.py`'s `view()`, or the shared `database/cashbook_queries.py`/`database/bi_queries.py` functions above). Separately, and orthogonally, one of the five remaining SQLite-only tables behind `register()`'s bridge (`audit_log`, `library_settings`, `membership_settings`, `backup_log`, `security_settings`) could be picked next instead to keep closing that bridge's FK dependencies — unaffected by anything in this slice. If `payments` itself is ever migrated to Supabase (a materially larger slice — it's read directly by at least five other unmigrated modules, and `record_payment()` is shared by both `routes/payment.py` and `routes/membership.py`, so migrating it would touch both), re-verify this ADR's "index() is untouched" claim first.

### ADR-22: Cashbook is the seventh Supabase slice — the first slice where the caller of a write function (not just a *reader*) stays out of scope, and the first to hit a live Postgres FK the migration can't satisfy

**Decision:** `routes/cashbook.py` (`index()`, `add_transaction()`, `edit_transaction()`), `database/cashbook_queries.py` (every function), and `database/audit_queries.py`'s `get_recent_audit_log()` now read/write `cashbook` and `audit_log` via `database/supabase_client.py`'s `get_supabase_client()`, the same client every prior slice uses. Supabase is the source of truth for every read. Unlike every prior slice, this one has **two different write shapes**, not one, because one of `cashbook_queries.py`'s two insert paths is called from files this slice does not touch:

- `insert_transaction()` (manual entries — the only path `routes/cashbook.py`'s own `add_transaction()` calls) writes Supabase first, computing `entry_id` explicitly as SQLite's current `MAX(entry_id) + 1` (the same reason ADR-18/19/20 needed this for `enquiry_id`/`student_id`/`membership_id` — Supabase's identity sequence, seeded once by the one-time data copy, ADR-15, trails SQLite's ever-climbing counter), then mirrors the identical row into SQLite, rolling the Supabase insert back if the SQLite mirror-write fails. This is the same strict shape every prior slice's in-scope caller uses.
- `insert_income_entry()` (automatic entries, triggered by `database/payment_queries.py`'s `record_payment()` — itself called from `routes/membership.py`'s `create()`/`renew()` and `routes/payment.py`'s `collect()`, none of which are part of this slice) keeps its **existing SQLite write as primary, unchanged**, and best-effort mirrors the identical row into Supabase afterward, swallowing any failure. `routes/membership.py`/`routes/payment.py` only catch `sqlite3.Error` around this call and manage their own SQLite commit/rollback (per ADR-20/21) — a `postgrest.exceptions.APIError` or network failure raising out of `insert_income_entry()` would surface as an unhandled error in a file this slice isn't touching, which every prior slice's file-scope discipline (ADR-16 §"How to apply", repeated at every slice since) rules out.

`database/audit_queries.py`'s `log_entry(cursor, ...)` keeps its exact pre-migration signature and behavior (SQLite-only mirror-write, same transaction as its cashbook row) — `cashbook_queries.py` now writes the matching Supabase `audit_log` row itself, next to its own Supabase `cashbook` write, rather than `log_entry()` doing both.

**Why the FK problem is new to this slice:** every prior slice's SQLite mirror existed because some *other, unmigrated table* still needed to read live field values or hold a real SQLite FK reference. This slice hit a different, sharper constraint: Supabase's own `cashbook` table has a **live PostgreSQL foreign key**, `cashbook_payment_id_fkey → payments(payment_id)` (declared in `supabase_migration.sql`, ADR-14, mirroring `schema.sql`'s SQLite FK) — and `payments` is not part of this slice (it's still fully SQLite-only, per the FK chain documented in `MIRROR_TRACKER.md`). Verified live against the actual Supabase project before writing any code: inserting a `cashbook` row with a real, currently-valid SQLite `payment_id` that has no Supabase counterpart fails with Postgres error `23503` ("insert or update on table \"cashbook\" violates foreign key constraint \"cashbook_payment_id_fkey\""). Every automatic entry `insert_income_entry()` creates carries a real `payment_id` (that's the entire point of `payment_id`, added by ADR-13 for reconciliation) — so sending it to Supabase as-is would make **every single automatic Cashbook entry fail to insert**, permanently, not as an edge case. `payment_id` is therefore omitted from the Supabase row entirely (left unset, defaulting to `NULL`) for automatic entries; the SQLite mirror keeps the real value, preserving today's reconciliation ability there (unaffected — see TD-38).

**Why `insert_income_entry()` couldn't just adopt the strict Supabase-first pattern:** every prior slice's "write Supabase first, roll back on mirror failure" shape was safe specifically because the function doing it was called from a route inside that same slice, which could be given (or already had) a matching `try/except`. `insert_income_entry()` is called mid-transaction, via a cursor on a connection `routes/membership.py`/`routes/payment.py` opened, own, and roll back themselves — this slice has no authority to add a new caught exception type to those two files without expanding scope into Payment/Membership again. Best-effort (try/except around the Supabase calls only, SQLite unchanged as the primary path) was the only shape available that doesn't touch those files at all, at the cost of a narrower, explicitly-documented staleness window (TD-39) instead of TD-35/36/37's full split-brain shape.

**Read-side implementation note:** PostgREST's query builder has no `SUM`/`GROUP BY` pushdown reachable from `supabase-py` without adding a database view or RPC (a schema change, out of scope, same restraint ADR-14 already established for this migration). Every KPI/analytics getter (`get_total_income`, `get_monthly_income`, `get_income_category_totals`, `get_cash_balance`, etc.) therefore fetches this admin's matching Supabase rows and aggregates in Python — the same "fetch, then finish the shape in Python" pattern ADR-18/19/20 already use for their own cross-table merges, just applied to aggregation instead of a join. `get_cashbook_ledger()`'s structured filters (date range, type, category, payment method, the "Manual" half of `source`) run server-side via the query builder (`.eq()`/`.gte()`/`.lte()`, all parameter-bound, verified live); free-text search and the "Automatic" half of `source` (`OR source IS NULL`) are applied in Python after the fetch, rather than hand-building a raw PostgREST `OR` filter string out of unsanitized user search input.

**Consequence — a new, narrower kind of gap this slice could not close (TD-38, TD-39):** `cashbook.payment_id` no longer round-trips through Supabase for automatic entries (TD-38) — every reconciliation query that joins `cashbook.payment_id` to `payments.payment_id` (the existing `tests/test_03_student_membership_payment.py`/`test_09_full_workflow_chain.py` assertions, and `database/migrate_backfill_cashbook_payments.py`) must keep querying the SQLite mirror, not Supabase, until `payments` itself migrates. Separately, `insert_income_entry()`'s best-effort Supabase mirror means an automatic entry could, in the rare case of a transient Supabase failure, exist correctly in SQLite (and the underlying payment still succeeds) while briefly missing from the Supabase-sourced Cashbook ledger/KPIs an admin actually looks at (TD-39) — a narrower failure window than TD-35/36/37's permanent split-brain, since the next successful write doesn't retroactively fix a missed one, but bounded to genuine Supabase outages rather than being structural.

**Consequence — `register()`'s SQLite mirror-insert bridge (TD-35) is unaffected, still fully required for all 7 tables — but only 4 of those 7 are still fully unmigrated:** `audit_log` was one of the 7 tables `register()`'s bridge exists for. Migrating its *reads* to Supabase here does **not** shrink that count — `database/audit_queries.py`'s `log_entry()` still enforces a real SQLite FK from `audit_log.admin_id → admins.admin_id` on every single write, unchanged by this slice, the same reason `enquiries`/`students` migrating didn't shrink the bridge's dependency count either (ADR-18/19). What *does* change is a separate count: of the 7 bridge-dependent tables, how many are still **fully SQLite-only** (no Supabase source of truth for reads at all) drops from 5 to 4 — `enquiries`/`students` already migrated at the route level (ADR-18/19), `audit_log` now joins them (this slice), leaving `library_settings`/`membership_settings`/`backup_log`/`security_settings` (all four owned by `routes/setting.py`) as the only fully-unmigrated tables among the 7. Don't conflate the two counts: the bridge itself still needs all 7, unconditionally.

**How to apply:** the `cashbook`/`audit_log` SQLite mirrors are not yet removable — see `MIRROR_TRACKER.md` for the exact reader/writer list this slice verified by re-grepping the codebase (not trusting any prior document's claimed list, per that file's own maintenance rule). The next slice that would close TD-38/TD-39 at the source is migrating `payments` itself — a materially larger slice, since `database/payment_queries.py`'s `record_payment()` is shared by both `routes/membership.py` and `routes/payment.py`, and at least five other unmigrated modules read `payments` directly (`routes/payment.py`'s own `index()`, `routes/membership_distribution.py`, `routes/student.py`'s `view()`, `utils/charts.py`, `database/cashbook_queries.py`'s fee-revenue functions). Once `payments` is on Supabase, `insert_income_entry()` can send a real `payment_id` to Supabase's `cashbook` (closing TD-38) and can adopt the same strict Supabase-first shape `insert_transaction()` already uses (closing TD-39), since `record_payment()`'s own callers would by then already need updating for `payments` itself.

### ADR-23: Analytics (Dashboard/Charts/Membership Distribution/Notifications/BI) is the eighth Supabase slice — the first slice with no write path of its own, and the first to need a Python-side JOIN shared across five call sites instead of one

**Decision:** `database/membership_queries.py` gains a new pair of shared read helpers — `get_admin_students(admin_id)` (this admin's `students` rows, `student_id`/`full_name`/`mobile`/`shift`/`purpose`/`join_date` only) and `get_memberships_for_admin(admin_id)` (this admin's `memberships`, each row enriched with those same student columns) — plus a Python equivalent of `DAYS_LEFT_SQL` (`get_days_left(end_date)`), alongside the existing `get_effective_status`/`EFFECTIVE_STATUS_SQL`. Every function elsewhere in the codebase that used to run `memberships m JOIN students s ON m.student_id = s.student_id WHERE s.admin_id = ?` directly against SQLite now calls `get_memberships_for_admin()` instead and finishes the shape (grouping, filtering, sorting) in Python — the same "fetch this admin's rows, finish the shape in Python" convention ADR-18/19/20/22 already established, just shared across multiple call sites this time instead of being written out per-route. Migrated: `database/membership_queries.py`'s `get_membership_counts()`, `database/cashbook_queries.py`'s `get_pending_fees()`, `utils/charts.py`'s `generate_membership_chart()`/`generate_membership_distribution_donut()`, `routes/dashboard.py`'s `dashboard()` (total students, total enquiries, upcoming expiries, recent admissions), `routes/membership_distribution.py`'s `index()` (total/plan-wise counts, the membership listing's non-payment columns), `routes/notification.py`'s `get_notification_summary()`, and `database/bi_queries.py`'s `get_monthly_new_memberships()`/`get_membership_retention()`/`get_upcoming_expiries()`. Supabase `students`/`memberships`/`enquiries` (already source of truth since ADR-18/19/20) are the source of truth for all of these; nothing here creates a new mirror or a new write path, since this slice is entirely read-side.

**Why one shared helper instead of five separate call-site queries:** `students`+`memberships` is the single most-repeated cross-table read in the codebase — 7 modules/functions needed the identical join shape (per `MIRROR_TRACKER.md`'s pre-slice audit). Writing the same `.select()` + `.in_()` + Python-merge pattern out five more times would have reproduced the exact "four independent copies of the same logic" problem `database/membership_queries.py` itself was created to close for `EFFECTIVE_STATUS_SQL`/`DAYS_LEFT_SQL` (TD-6, ADR — see that module's own history). `get_memberships_for_admin()` fetches this admin's students once (`.select("student_id, full_name, mobile, shift, purpose, join_date").eq("admin_id", admin_id)`), then this admin's memberships once (`.select("*").in_("student_id", <those ids>)`), and merges by `student_id` in Python — one extra network round-trip over a real server-side JOIN, but PostgREST (via `supabase-py`) has no cross-table JOIN in the client this codebase uses, the same constraint every prior slice's cross-table reads (ADR-18 §`routes/student.py`, ADR-20 §`routes/membership.py`) already accepted.

**What stayed on SQLite, and why (temporary, documented compatibility — not an oversight):** `payments` has no Supabase copy read/written by any route yet (see `MIRROR_TRACKER.md`'s "Non-mirror unmigrated tables" section) — every one of this slice's targets that needed `payments`, not just `students`/`memberships`, was left exactly as it was: `utils/charts.py`'s `generate_revenue_chart()` (payments JOIN students, monthly revenue line), `database/cashbook_queries.py`'s `get_today_fee_collection()`/`get_total_fee_revenue()` (both payments JOIN students), and `routes/membership_distribution.py`'s per-row `receipt_number`/`payment_mode`/`payment_date`/`last_amount_paid` columns (looked up from SQLite in one batched `WHERE membership_id IN (...)` query, keyed by the membership ids Supabase already returned, rather than N separate queries). Each of these is commented in place with why it's still SQLite. This mirrors ADR-22's own precedent (`get_pending_fees`/`get_today_fee_collection`/`get_total_fee_revenue` were explicitly left SQLite there too, for the same reason) rather than inventing a new exception.

**Consequence:** the `students`/`memberships` SQLite mirrors' remaining-reader counts (tracked in `MIRROR_TRACKER.md`) both shrink substantially — `students` from 11 tracked consumers down to the ones that still need `payments` or aren't part of this slice (`routes/payment.py`'s `index()`, `database/payment_queries.py`'s receipt-fallback branch, `routes/setting.py`'s backup functions, `routes/enquiries.py`'s read-only lookups, `routes/student.py`'s own `index()` self-join); `memberships` from 7 down to just `routes/student.py`'s `view()`. Neither mirror is deletable yet — both are still gated on `payments` migrating on the FK-side (`payments.membership_id`/`payments.student_id`), per `MIRROR_TRACKER.md`'s FK-chain analysis, independent of how many readers remain. `enquiries`' one remaining reader (`routes/dashboard.py`'s total-enquiries count) is now migrated too, dropping that mirror's reader count to zero — but its own removal is still gated on the `students` mirror's FK-side condition, same reasoning.

**How to apply:** migrating `payments` itself is the natural next slice — it closes the FK-side gate for both `students` and `memberships` simultaneously (shared via `database/payment_queries.py`'s `record_payment()`, called from both `routes/membership.py` and `routes/payment.py`), lets `generate_revenue_chart()`/`get_today_fee_collection()`/`get_total_fee_revenue()`/`routes/membership_distribution.py`'s payment columns/`routes/payment.py`'s `index()` all cut over, and — per ADR-22's own "How to apply" — finally lets `cashbook`'s Supabase mirror carry a real `payment_id` (closing TD-38) and `insert_income_entry()` adopt the strict Supabase-first write shape (closing TD-39).

### ADR-24: Settings (library_settings/membership_settings/backup_log/security_settings) is the ninth Supabase slice — the first slice where the SQLite mirror is dropped entirely instead of kept

**Decision:** `database/settings_queries.py`, `database/receipt_settings_queries.py`, `database/notification_settings_queries.py` (all three read/write the same `library_settings` row), `database/membership_settings_queries.py`, `database/backup_queries.py`, and `database/security_settings_queries.py` now read/write their tables via `database/supabase_client.py`'s `get_supabase_client()` instead of SQLite. Unlike every prior slice (ADR-16 through ADR-23), **no SQLite mirror is kept at all** — these four tables are leaf nodes in the FK graph (`docs/MIRROR_TRACKER.md`'s FK-chain diagram): nothing else in `schema.sql` declares a foreign key against `library_settings`/`membership_settings`/`backup_log`/`security_settings`, so there is no downstream SQLite insert that needs these rows to exist in SQLite the way `students`/`memberships`/etc. needed their own mirrors. `routes/setting.py` itself needed no code changes — every function it calls kept its exact signature and return shape, the same zero-route-change outcome ADR-22 found for `routes/cashbook.py`. While in this file, `routes/setting.py`'s `backup_export_csv()` also moved its `students` read to Supabase (a `students`-mirror reader from `docs/MIRROR_TRACKER.md`'s tracked list, not a Settings table, but trivial to close in the same session) and `database/payment_queries.py`'s `generate_receipt_number()` moved its `library_settings.next_receipt_number` read/advance to Supabase (the same table this slice migrated, so it had to move together, not because `payments`/`generate_receipt_number()`'s own SQLite `payments` uniqueness check is in scope — it isn't, and stays SQLite).

**Backfill:** unlike `enquiries`/`students`/`memberships`/`cashbook` (which needed the explicit-id/rollback machinery ADR-18 introduced because Supabase's identity sequence trailed SQLite's), these four tables are one-row-per-`admin_id` (`UNIQUE` constraint on both sides), so there is no ordering/identity-sequence concern — `database/migrate_backfill_settings_to_supabase.py` (new) does a plain upsert, `on_conflict="admin_id"`, SQLite wins on conflict (it was the more current copy, since every write since the one-time bulk copy, ADR-15, had gone to SQLite only). Run once before this slice's code changes; see that script's own docstring for exactly what it does and why it needs none of `migrate_to_supabase.py`'s sequence-reset/temporal-sanitization machinery.

**Why no SQLite mirror, when every prior slice kept one:** every prior slice's mirror existed because a *different, unmigrated table* still needed to read live field values or hold a real SQLite FK reference to the migrated table. `register()`'s bridge (`routes/auth.py`, TD-35) is the clearest example of this pattern working the other way — 7 tables held a real FK back to `admins.admin_id`, so `admins` needed a mirror until all 7 stopped needing it. These four Settings tables are the opposite case: they are referenced by nothing, and reference nothing except `admins` (a FK this slice does not change — `admins` itself is unaffected, since these four tables never insert new rows referencing a *new* `admin_id`, only their own admin's row). There is no SQLite reader left after this slice (every `database/*_queries.py` function that touched these four tables is migrated) and no SQLite writer either, so both of `docs/MIRROR_TRACKER.md`'s removal conditions are satisfied in the same commit that introduces the migration — there was nothing left to call "temporary".

**Timestamp handling:** `library_settings`/`membership_settings`/`security_settings` all have `updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP` columns the old SQLite `UPDATE ... SET updated_at = CURRENT_TIMESTAMP` refreshed on every write. Supabase has no `ON UPDATE` trigger for this (a schema change, out of scope, same restraint ADR-14 established) — `database/settings_queries.py`'s new `_now_iso()` helper computes the timestamp in Python and every migrated `UPDATE`/`upsert` call sets it explicitly instead. `database/settings_queries.py`'s `get_library_settings()` also normalizes Supabase's `T`-separated ISO timestamp string back to the space-separated shape the SQLite column produced (`"2026-07-23T15:15:09+00:00"` → `"2026-07-23 15:15:09+00:00"`), since `routes/setting.py`'s AJAX response slices `created_at`/`updated_at` to their first 16 characters for display and a `T` there would have silently changed what the Library Profile page shows as "Registered on"/"Last updated".

**Consequence — a narrower version of TD-38/TD-39's problem, TD-40:** `database/payment_queries.py`'s `generate_receipt_number()` advances the Supabase counter as its own write, no longer inside the same SQLite transaction as the `payments` row it's issued for (`payments` itself stays SQLite, unmigrated, out of scope). If that enclosing SQLite transaction later rolls back, the counter has already advanced and won't roll back with it — a skipped receipt number, not a collision (`_receipt_number_taken()`'s uniqueness loop is unaffected). See TD-40 in `docs/11_FUTURE_WORK.md`.

**Consequence — `register()`'s SQLite mirror-insert bridge (TD-35) shrinks from 7 dependents to 3:** `library_settings`/`membership_settings`/`backup_log`/`security_settings` no longer insert into SQLite at all, so their FK to `admins.admin_id` is never exercised by this app anymore — they drop out of the bridge's dependent list entirely (not just off the "still fully unmigrated" sub-count, the way `enquiries`/`students`/`audit_log` did at the route level). `enquiries`, `students`, and `audit_log` are the only 3 remaining tables requiring `register()`'s mirror-insert — see `docs/MIRROR_TRACKER.md`'s updated `admins` section.

**How to apply:** the next slice to shrink `students`/`memberships` further is migrating `payments` itself (per ADR-23's own "How to apply" — unchanged by this slice, since Settings and Payments are independent tables). Once `payments` migrates, `database/payment_queries.py`'s `generate_receipt_number()`/`record_payment()` can finally move into a single Supabase-first transaction shape, closing TD-38/TD-39/TD-40 together. Separately, `enquiries`/`students`/`audit_log` are now the *only* thing blocking `register()`'s bridge removal — closing all three (which itself requires `payments` migrating first, since `students`/`memberships`' own mirrors are gated on it) is what finally lets that bridge, `cashbook`'s mirror, and `audit_log`'s mirror all come down.

### ADR-25: Payments is the tenth Supabase slice — the first slice that discovered its backfill was blocked by a pre-existing, previously-undocumented gap in three *earlier* migrations

**Decision:** `database/payment_queries.py`'s `record_payment()` now writes Supabase `payments` as a best-effort mirror alongside its unchanged SQLite primary write (same shape ADR-22 established for `insert_income_entry()`, for the identical reason: it's called mid-transaction from `routes/membership.py`/`routes/payment.py`, both out of scope). `payment_id` is now computed explicitly (SQLite `MAX(payment_id) + 1`) instead of left to `AUTOINCREMENT`, so the same id is used on both sides — the same explicit-id pattern ADR-18/19/20/22 established. Supabase `payments` becomes the source of truth for every *read*: `routes/payment.py`'s `index()`, `routes/student.py`'s `view()` (the `memberships` mirror's last remaining reader, per ADR-23 — now fully migrated), `utils/charts.py`'s `generate_revenue_chart()`, `database/cashbook_queries.py`'s `get_today_fee_collection()`/`get_total_fee_revenue()`, `routes/membership_distribution.py`'s per-row receipt columns, and `database/payment_queries.py`'s own `generate_receipt_number()` fallback branch — all via a new shared helper, `get_payments_for_admin()` (same "fetch this admin's students, filter by student_id, merge in Python" shape as `database/membership_queries.py`'s `get_memberships_for_admin()`; kept in `payment_queries.py` rather than reused directly by `cashbook_queries.py`, which gets its own small local copy, `_fetch_payments_for_admin()`, to avoid a circular import — `payment_queries.py` already imports `cashbook_queries.py` for `insert_income_entry`). Since `payments` now has a Supabase row, `insert_income_entry()` also starts sending a real `payment_id` to Supabase `cashbook` (closing **TD-38**) — best-effort, so if the payments mirror-write moments earlier happened to fail, this insert falls back to the same best-effort miss the rest of that function already risks (new: **TD-41**, a narrower version of TD-39).

**Backfill blocked by a pre-existing gap in `enquiries`/`students`/`memberships` — the actual bulk of this slice's work:** attempting the straightforward `payments` backfill (insert every SQLite row Supabase is missing, preserving `payment_id`) failed immediately on a foreign-key violation — `memberships` referenced by SQLite `payments` rows didn't exist in Supabase. Investigating found Supabase `memberships` was missing 339 rows SQLite had, `students` was missing 433, and `enquiries` was missing 493 (`admins` had zero gap). None of ADR-18/19/20's route-level cutovers, nor any backfill script before this one, caught it, because every one of them only guarantees parity *going forward* from the moment a route started dual-writing — any row created before that moment, and never edited since (so no post-migration write ever re-synced it), was simply never copied. The original one-time bulk import (ADR-15, `database/migrate_to_supabase.py`) ran once, early, before these tables had accumulated their full history. This is a real, previously-undocumented data-integrity gap: any Supabase read of `students`/`memberships`/`enquiries` since ADR-18/19/20/23 cut over (Dashboard, Membership Distribution, Notifications, BI, Enquiries, Students — everything Supabase-backed) has been silently missing these rows the entire time, not just something blocking this slice's backfill.

**Fix:** `database/migrate_backfill_mirror_parity.py` (new) reconciles all four tables — `enquiries` → `students` → `memberships` → `payments`, the FK-safe order — inserting only the SQLite rows Supabase is missing, preserving each row's exact id, never touching a row that already exists on both sides. It also sanitizes DATE/TIMESTAMP columns the same way `migrate_to_supabase.py` does (SQLite's dynamic typing had let at least one literal `"not-a-date"` string into a date column, which Postgres rejected outright). Run once, before any of this slice's code changes; verified full parity afterward (`enquiries` 1996/1996, `students` 1376/1376, `memberships` 922/922, `payments` 1064/1064).

**Why `payments` itself still uses a narrower, standalone backfill script conceptually, folded into the combined one:** unlike the four Settings tables (ADR-24, one row per `admin_id`, no ordering concern), `payments` is an append-only ledger whose primary key is referenced by `cashbook.payment_id` (a live Postgres FK) — preserving the exact `payment_id` on backfilled rows isn't optional, it's what lets `insert_income_entry()`'s `payment_id` linkage (TD-38) mean anything.

**Consequence — `memberships` mirror's last reader closes:** per ADR-23's tracked list, `routes/student.py`'s `view()` was the sole remaining SQLite reader of the `memberships` mirror, and it also needed SQLite `payments` for that same student's payment history — migrating both together in this slice closes `view()`'s SQLite dependency entirely. `docs/MIRROR_TRACKER.md`'s `memberships` mirror is now at **zero** read-side consumers (its FK-side condition — `payments.membership_id`'s SQLite FK — is also satisfied now that `payments`' own SQLite write stops being the exclusive source of truth, though the SQLite write itself is unchanged, see "How to apply" below).

**Consequence — `students` mirror's remaining readers all close too:** `routes/payment.py`'s `index()`, `database/payment_queries.py`'s receipt-fallback branch, and `utils/charts.py`'s `generate_revenue_chart()` were the last 3 tracked `students`-mirror readers, all gated on `payments` migrating (ADR-23). All three are now migrated. `docs/MIRROR_TRACKER.md`'s `students` mirror is now also at zero read-side consumers, leaving only `routes/setting.py`'s `backup_create()` (a whole-file SQLite copy, not a query) as a non-query consumer.

**How to apply:** with `students`/`memberships` both at zero read-side consumers, the next step is auditing whether their FK-side conditions are now satisfied too (`routes/membership.py`'s `create()`/`renew()` and `routes/student.py`'s `admission()`/`edit()` still write the SQLite mirrors unconditionally — that write itself, not just a downstream reader, is what Phase 9/10's dependency audit needs to re-verify against source before any mirror-write can actually be deleted). See the Phase 8/9 re-grep and dependency audit that follows this slice.

### ADR-26: `audit_log`'s SQLite mirror-write removed — the first mirror actually deleted, not just migrated

**Decision:** `database/audit_queries.py`'s `log_entry(cursor, admin_id, entry_id, action, details)` — a pure SQLite `INSERT INTO audit_log` with zero application readers since ADR-22 — is deleted outright, along with its three call sites in `database/cashbook_queries.py` (`insert_transaction()`, `insert_income_entry()`, `update_manual_transaction()`) and the now-unused `from database.audit_queries import log_entry` import. `get_recent_audit_log()` (Supabase, unchanged) is the only function left in `audit_queries.py`.

**Why this one first:** the Phase 9 dependency audit (`docs/MIRROR_TRACKER.md`) confirmed every mirror in the app is at zero live read-side consumers as of ADR-25 — the only thing left keeping any of them alive is another mirror's own FK requirement, in one connected chain: `admins` ← `enquiries`/`students`/`audit_log` ← `memberships` ← `payments` ← `cashbook.payment_id` ← `audit_log.entry_id`. `audit_log` is the one table nothing in `schema.sql` declares a foreign key against — a genuine leaf, safe to stop writing without touching anything else in the chain. Every other mirror still requires at least one more table's SQLite write to stop first.

**Consequence:** SQLite `audit_log` rows stop being created from this point forward (the table itself, and every row already in it, still physically exists — Phase 11 removes the table). `cashbook`'s own SQLite mirror-write is now the next candidate: with `audit_log` no longer inserting rows that reference `cashbook.entry_id`, that FK is no longer being exercised by new writes, so `cashbook`'s SQLite mirror-write is next in line, per the same reasoning.

**How to apply:** repeat this exact pattern — verify a table is a genuine leaf (nothing left references it), delete its SQLite mirror-write function/call sites outright (not just stop calling it; remove the dead code, matching the "no half-finished implementations" standard the rest of this codebase holds writes to) — for `cashbook` next, then `payments`, then `memberships`/`students`, then `enquiries`, then finally `admins`' `register()` bridge. Re-run the dependency audit after each removal, per `docs/MIRROR_TRACKER.md`'s own maintenance rule.

### ADR-27: `cashbook`'s SQLite mirror-write removed — the second mirror deleted; ID generation moves from SQLite to Supabase

**Decision:** `database/cashbook_queries.py` stops writing SQLite entirely. `insert_transaction()` and `update_manual_transaction()` drop their SQLite `INSERT`/`UPDATE` and `get_connection()`/commit/close calls; `insert_income_entry()` drops its SQLite `INSERT` and its `conn` parameter (the SQLite connection/cursor callers used to pass it, no longer needed for anything). `_generate_reference_id()` and `_next_entry_id()` — the two helpers that compute this table's explicit IDs, following the ADR-18/19/20/22 pattern — switch from querying SQLite's `COUNT`/`MAX` to querying Supabase's, since Supabase is now the only copy of `cashbook` that receives new rows. `database/migrate_backfill_cashbook_payments.py`, the one dormant script `docs/MIRROR_TRACKER.md` flagged as this mirror's last "read-side" justification, is deleted outright rather than rewritten — its entire approach (raw SQLite `JOIN`s across `payments`/`students`/`memberships`, then reconciling into SQLite `cashbook` via `insert_income_entry(conn, ...)`) no longer has anything to reconcile into, and its purpose (backfilling historical pre-automatic-logging payments) is a one-off data fix already superseded by the ADR-25 mirror-parity backfill.

**Why this one next:** the Phase 9 audit's FK chain (`admins` ← `enquiries`/`students`/`audit_log` ← `memberships` ← `payments` ← `cashbook.payment_id` ← `audit_log.entry_id`) meant `cashbook` couldn't be touched until `audit_log` stopped inserting rows that reference `cashbook.entry_id` — ADR-26 cleared that. `cashbook`'s only other tracked condition (the dormant backfill script) is resolved by deleting the script, not by keeping the mirror alive for it.

**Consequence — a real behavior change, not just a deletion:** `insert_income_entry()`'s failure mode changes. Before ADR-27, this function's SQLite write was primary and guaranteed (part of the caller's own SQLite transaction); Supabase was a best-effort mirror, so a Supabase hiccup only left the *Supabase-side* copy stale (TD-39/TD-41) while a real row still existed in SQLite. As of ADR-27, Supabase is the only store, and the whole function (ID generation plus both inserts) is wrapped in one bare `except: pass` to preserve its existing contract with its callers (`routes/membership.py`/`routes/payment.py`, still out of this migration's scope, still only catching `sqlite3.Error`) — but now a Supabase failure means the automatic `cashbook` entry and its `audit_log` row are lost, not just stale. This is new technical debt, not a pre-existing risk carried forward — see **TD-43** in `docs/11_FUTURE_WORK.md`. `insert_transaction()`'s failure mode is unaffected (still strict: the `cashbook` insert is rolled back if `audit_log` then fails, now entirely within Supabase instead of Supabase-then-SQLite).

**Consequence — ID generation now depends on Supabase being reachable:** before ADR-27, `_generate_reference_id()`/`_next_entry_id()` queried local SQLite, so they never failed for network reasons. As of ADR-27, both query Supabase, adding a new failure mode (a transient Supabase outage during `insert_transaction()` now raises before any row is written, visible to the admin as an error rather than silently retried) — an accepted tradeoff of removing the SQLite mirror, not a separate bug.

**How to apply:** `payments` is next in the removal order (per ADR-26's list) — it has the same explicit-ID pattern (`payment_id` from SQLite `MAX`, in `database/payment_queries.py`'s `record_payment()`) and will need the identical ID-generation migration from SQLite to Supabase this ADR made for `cashbook`. `record_payment()`'s own best-effort mirror-write (TD-41) will collapse into the same "no fallback left" shape TD-43 describes here — expect a similar new TD row rather than assuming TD-41 simply closes.

### ADR-28: `payments`' SQLite mirror-write removed — the third mirror deleted; `record_payment()` becomes strict instead of best-effort (a deliberate divergence from ADR-27's prediction)

**Decision:** `database/payment_queries.py`'s `record_payment()` stops writing SQLite entirely, dropping its `conn` parameter (no longer needed). `payment_id` is now computed from Supabase's own `MAX(payment_id) + 1` (same pattern as `cashbook.entry_id`, ADR-27). `_receipt_number_taken()`/`generate_receipt_number()` switch their uniqueness check from SQLite to Supabase, for the same reason ADR-27 moved `cashbook`'s ID-generation helpers: Supabase is now the only copy, so checking anywhere else means checking stale data. **Unlike ADR-27's prediction above, `record_payment()`'s Supabase `payments` insert is made strict (raises `postgrest.exceptions.APIError` on failure), not best-effort** — its three callers (`routes/membership.py`'s `create()`/`renew()`, `routes/payment.py`'s `collect()`) now catch `(sqlite3.Error, APIError)` instead of just `sqlite3.Error`, so a payment failure still triggers the exact same rollback (SQLite `memberships` mirror reverted, Supabase `memberships` update reverted, error flashed) it always did.

**Why this one next:** `cashbook`'s SQLite mirror-write (ADR-27) was the last thing that would have required a `payments` row to exist in SQLite for any downstream write's FK to resolve. With that gone, the only remaining condition was `record_payment()`'s own SQLite insert stopping — a pure write-path decision, per the Phase 9 audit's removal order.

**Why strict instead of best-effort, diverging from what ADR-27 predicted:** ADR-22/ADR-27's best-effort shape exists specifically because `insert_income_entry()`/`insert_transaction()`'s automatic-entry caller chain is out of this migration's scope and can't be given a new caught exception type *without* touching `routes/membership.py`/`routes/payment.py`. But `record_payment()` is called directly inside those same two files' own `try/except sqlite3.Error` blocks — modifying that `except` clause to also catch `APIError` is a minimal, mechanical, one-line change per call site, not a scope expansion into new logic. Given that, making `payments` (the actual "money was recorded" write, not a downstream convenience entry) fail loudly and roll back cleanly is strictly better than the alternative of silently losing a payment - the same reasoning ADR-21 already established for `memberships.paid_amount`/`pending_amount`. `insert_income_entry()` (ADR-27) stayed best-effort because it's genuinely a secondary, downstream effect of a payment, not the payment itself, and its callers' `except` clause is one more level removed (inside `record_payment()`, not the route file directly).

**Consequence:** `routes/membership.py`'s `create()`/`renew()` and `routes/payment.py`'s `collect()` each gained one line (`except (sqlite3.Error, APIError):` in place of `except sqlite3.Error:`) — `postgrest.exceptions.APIError` was already imported in all three files (used elsewhere for the `memberships` Supabase writes), so no new import was needed anywhere. The three "Bridge:" comments explaining why those routes still mirror `memberships` into SQLite were updated: `payments` no longer needs `memberships`'/`students`' SQLite rows to exist for its own FK, so `memberships`' SQLite mirror-write is now itself a removal candidate (see `docs/MIRROR_TRACKER.md`'s `memberships`/`students` sections). TD-40 (the receipt-counter/payment-insert non-atomicity) is **not** closed by this ADR — the counter still advances as a separate Supabase write before the `payments` insert, so a failure on the insert still leaves the counter one ahead; the fix, if ever built, would need both writes issued as a single Postgres transaction (an RPC, most likely), out of this ADR's scope.

**How to apply:** `memberships`/`students` are next (per ADR-26/27's list) — unlike `cashbook`/`payments`, these two have *two* separate writers each (`routes/membership.py`'s `create()`/`renew()` plus `routes/payment.py`'s `collect()` for `memberships`; `routes/student.py`'s `admission()`/`edit()` for `students`), so removing them means touching more call sites than any prior slice, and deciding the same "strict vs. best-effort" question for each. Given ADR-28's reasoning above, prefer strict where the caller can absorb a widened `except` clause cheaply; best-effort only where doing so would mean rewriting business logic the migration shouldn't be touching.

**Verification finding — a critical, unrelated-looking bug this ADR's own test run surfaced and fixed in the same slice:** running the full suite after the above changes produced cascading, seemingly-random failures (`test_edit_automatic_entry_blocked` and others failing with an empty automatic Cashbook entry, some runs showing `sqlite3.OperationalError: database is locked`, some showing SQLite/Supabase `membership_id` PK collisions). Root-caused to `generate_receipt_number()`'s no-Library-Profile fallback branch: it always started counting from `1001 + <this admin's own payment count>` and called `_receipt_number_taken()` in a loop to skip forward past every already-claimed `"LIB-NNNNN"` number (every admin defaults to the shared `"LIB"` prefix). Before this ADR, that loop queried local SQLite — fast enough that walking past hundreds of claimed numbers was invisible. As of this ADR, it queries Supabase — a real network round trip per iteration. Live reproduction: 1281 already-claimed `"LIB-"` receipts made a single fresh admin's first receipt-number allocation take **161 seconds**, long enough to trigger httpx timeouts mid-`record_payment()`, leaving `APIError`s that the caller's rollback sometimes couldn't fully clean up (the SQLite lock and ID-collision symptoms were real secondary effects of that timeout window, not separate bugs — later confirmed by re-testing clean after the real fix). Fixed by adding `_max_claimed_sequence()` — one `ORDER BY receipt_number DESC LIMIT 1` query (the zero-padded `%05d` format sorts lexicographically identical to numeric order, so no need to fetch/parse every row) — and seeding both branches' starting point from its result instead of a fixed floor. Verified: the same case dropped from 161s to 0.72s; the full targeted suite (test_03/04/09, 83 tests) that previously took 30+ minutes with failures now passes cleanly in 9m20s. Logged as **TD-44** (`Resolved`) in `docs/11_FUTURE_WORK.md` rather than folded silently into this ADR's diff, since it's a genuine standalone defect (would also degrade a real production library that never customizes its receipt prefix) discovered *by* this ADR's verification step, not an inherent part of the mirror-removal design itself.

### ADR-29: `memberships`/`students` SQLite mirror-writes removed — the fourth and fifth mirrors deleted, in one slice

**Decision:** `routes/membership.py`'s `create()`/`renew()` and `routes/payment.py`'s `collect()` stop writing SQLite `memberships` entirely; `routes/student.py`'s `admission()`/`edit()` stop writing SQLite `students` entirely. `membership_id`/`student_id` are now computed from Supabase's own `MAX(...)` (same `ORDER BY ... DESC LIMIT 1` pattern ADR-27/28 established for `cashbook.entry_id`/`payments.payment_id`), not SQLite's. Both tables are removed in the **same** slice, unlike the prior three mirrors removed one at a time — `students` and `memberships` are tightly coupled (a `memberships` row's own SQLite insert needed a `students` SQLite row to exist for its FK, and that FK dependency only clears once *both* stop writing SQLite together, not one at a time), so splitting them into separate commits would leave an intermediate state where one mirror is half-orphaned relative to the other.

**Why these two, and why together:** per the Phase 9 audit's removal order and ADR-28's own "How to apply" note, `payments`' SQLite mirror-write being gone (ADR-28) cleared the last FK dependent for both `memberships` (via `payments.membership_id`) and, transitively, `students` (via `payments.student_id`, and via `memberships.student_id`) — see `docs/MIRROR_TRACKER.md`'s `students`/`memberships` sections for the exact FK-graph reasoning.

**Consequence — four call sites, all made strict:** unlike `insert_income_entry()` (ADR-27, deliberately best-effort), every one of these four call sites now propagates a Supabase failure as a normal Python exception (`postgrest.exceptions.APIError`) with an explicit `except APIError:` block that rolls back whatever it already wrote (deleting the just-inserted `memberships`/`students` row, reverting `previously_active_ids` back to `Active` for `renew()`, reverting `paid_amount`/`pending_amount` for `collect()`) and flashes the same "Nothing was saved" message these routes always showed. This follows ADR-28's "strict is fine, and preferred, when the caller can absorb it" reasoning — every one of these four call sites already had its own `try`/`except` structure built around the *previous* SQLite mirror-write, so replacing "roll back the SQLite half + delete the Supabase half" with "just delete the Supabase half" is a subtraction, not new logic. `sqlite3`/`database.db.get_connection` imports were removed from all three route files (`routes/membership.py`, `routes/payment.py`, `routes/student.py`) — none of them touch SQLite for anything anymore.

**Consequence — test infrastructure had its own dependency on the mirror:** `tests/conftest.py`'s `get_last_student_id()`/`get_last_membership_id()` helpers, used by nearly every test that creates a student or membership, read the *SQLite* mirror on the assumption it would always hold the just-created row. With the mirror gone, both were rewritten to query Supabase directly (`ORDER BY ... DESC LIMIT 1`, same shape as the route-level ID computation above). Four cross-tenant isolation tests (`tests/test_08_cross_tenant_isolation.py`) and one workflow-chain assertion (`tests/test_09_full_workflow_chain.py`) also read/wrote SQLite `memberships`/`students` directly to seed test state or assert on the outcome — all rewritten to Supabase, since checking the now-frozen SQLite copy would either always trivially pass (a blocked cross-tenant edit can never touch "HACKED" into a table nothing writes to anymore, whether or not the isolation check actually worked) or never observe a real effect (seeding an `end_date` into SQLite `memberships` no longer affects the Supabase-backed Notifications page at all). This is the same category of test-suite fragility every prior mirror removal in this phase has had to fix in its own tests — expected, not a surprise, but worth calling out explicitly since missing even one of these would have silently reduced test coverage to a tautology instead of failing loudly.

**How to apply:** `enquiries` is next (per ADR-26's removal order) — `routes/enquiries.py`'s `add()`/`edit()`/`delete()`. Unlike `memberships`/`students`, `enquiries` has exactly one writer file, so it should be a smaller slice than this one. After `enquiries`, only the `admins` bridge (`routes/auth.py`'s `register()`) remains, and it can only be removed once `enquiries`/`students`/`audit_log` — its three FK dependents — have all stopped writing SQLite (`audit_log` already has, ADR-26; `students` now has, this ADR; `enquiries` will after the next slice).

### ADR-30: `enquiries`' SQLite mirror-write removed — the sixth mirror deleted, and the only bridge left is `admins`

**Decision:** `routes/enquiries.py`'s `add()`/`edit()`/`delete()` stop writing SQLite `enquiries` entirely. `enquiry_id` is now computed from Supabase's own `MAX(enquiry_id)` (`ORDER BY enquiry_id DESC LIMIT 1`), the same pattern ADR-27/28/29 established. `sqlite3`/`database.db.get_connection` imports removed from `routes/enquiries.py` — it has zero SQLite dependency of any kind now.

**Why this one next:** `students`' own SQLite mirror-write (ADR-29) was the last thing exercising `students.enquiry_id`'s SQLite FK. With that gone, nothing in the SQLite FK graph required an `enquiries` row to exist for a write to succeed — the Phase 9 audit's removal order (`audit_log` ← `cashbook` ← `payments` ← `memberships`/`students` ← `enquiries` ← `admins`) reaches `enquiries` here, one step before the `admins` bridge itself.

**Consequence — three call sites, three different shapes:** `add()` is made strict (`except APIError:` rolls back nothing extra — there's no SQLite write left to roll back, `add()` never had anything to revert on the Supabase side either, since it's the first write in its own flow). `edit()` drops its `try`/`except sqlite3.Error` wrapper entirely — its Supabase `.update()` is already independently wrapped in its own `except APIError:`, and there is nothing left for the old SQLite block to do. `delete()`'s old comment described a "best-effort mirror delete, not wrapped to roll back" specifically because `students.enquiry_id`'s SQLite FK (no `ON DELETE` clause) could block the SQLite delete for an already-admitted student — with no SQLite write left at all, that entire code path (and its documented TD-36 leftover-row edge case) disappears; `delete()` is now a single Supabase call with no follow-up.

**Consequence — a stale comment caught along the way:** `edit()`'s removed SQLite-sync block had a comment claiming `routes/student.py`'s `admission()` "reads full_name/mobile/purpose/preferred_shift for this enquiry_id straight from SQLite" — this was already wrong before this ADR (`admission()` has read enquiry fields from Supabase directly since ADR-19) and predates this migration entirely. Corrected while removing the block it was attached to, not left to rot further.

**Consequence — test infrastructure:** `tests/conftest.py`'s `get_last_enquiry_id()`, used by nearly every test that creates an enquiry, read the SQLite mirror; rewritten to query Supabase directly. Two cross-tenant isolation tests (`tests/test_08_cross_tenant_isolation.py`) that asserted on SQLite `enquiries` state after a blocked edit/delete attempt were rewritten to Supabase for the same reason ADR-29's test fixes were needed — checking the frozen SQLite copy would make the isolation check tautological rather than a real test.

**How to apply:** the `admins` bridge (`routes/auth.py`'s `register()`) is the **only** mirror/bridge left in the entire app — `enquiries`, its last FK dependent, is now gone. Removing it means deleting `register()`'s SQLite mirror-insert of the new admin row and its compensating rollback-on-`sqlite3.Error` — the exact same "delete the mirror-write, catch nothing new since there's no SQLite left to fail" pattern every mirror in this phase has followed. Once that's done, Phase 11 (full SQLite removal — connections, `database/db.py`, `schema.sql`, obsolete `migrate_*.py` scripts, `sqlite3`/`get_connection` imports project-wide) can begin; nothing in the live request path will read or write SQLite at all.

### ADR-31: `admins` bridge removed — the seventh and final mirror/bridge deleted; Phase 10 is complete

**Decision:** `routes/auth.py`'s `register()` stops mirror-inserting the new admin row into SQLite entirely. Its old `try` block — insert into SQLite `admins`, commit, and on `sqlite3.Error` delete the just-created Supabase row and flash an error — is deleted outright, along with the `insert_response`/`new_admin_id` variables that only existed to feed it. The Supabase `.insert(...)` call is simplified from capturing `insert_response` to a bare statement, since nothing downstream needs the new row's id anymore. `import sqlite3` and `from database.db import get_connection` are removed from the file — it has zero SQLite dependency of any kind now.

**Why this one, and why last:** `admins` was never a real "mirror" in the same sense as the other six tables (nothing reads it back out of SQLite) — it was an existence-only **bridge**, kept solely so that `audit_log.admin_id`, `students.admin_id`, and `enquiries.admin_id`'s SQLite foreign keys had a valid parent row to reference. TD-35 (`Resolved` via ADR-17) had already split the *password* off to Supabase-only years earlier; this bridge only ever mirrored the row's existence. Per the Phase 9 audit's removal order (`audit_log` ← `cashbook` ← `payments` ← `memberships`/`students` ← `enquiries` ← `admins`), `admins` could only be removed once all three FK dependents stopped writing SQLite: `audit_log` (ADR-26), `students` (ADR-29), and `enquiries` (ADR-30) — the last of the three cleared in the immediately preceding slice, making this the final removal in Phase 10.

**Consequence:** `login()` and `forgot_password()` were already Supabase-only before this ADR (per TD-35's resolution) and are untouched here. Only `register()` changes. This is the smallest of the seven mirror-removal slices — one function, one deleted block, two deleted imports — precisely because `admins` never had a reader or an ID-generation dependency the way `cashbook`/`payments`/`memberships`/`students`/`enquiries` did (Supabase's own identity column has always assigned `admin_id`; nothing computed it via `MAX(...)`).

**Consequence — test infrastructure:** `tests/test_08_cross_tenant_isolation.py`'s `_register_and_login()` and `tests/test_09_full_workflow_chain.py`'s `_reg()` helper both read the new admin's `admin_id` back out of SQLite after registering; both rewritten to use `tests/conftest.py`'s existing `get_admin_by_username()` (already Supabase-based, already used elsewhere in the suite). `tests/conftest.py`'s now-fully-unused `from database.db import get_connection` import was removed — no remaining call site in the file references it.

**Consequence — this is the last mirror/bridge in the entire app:** every table the migration touched (Phase 6 through Phase 10) is now Supabase-only. Grepping `routes/`, `database/`, and `tests/*.py` for `FROM admins`/`INTO admins`/`UPDATE admins` turns up only two out-of-scope hits: `database/migrate.py` (the historical one-time bulk-copy script, ADR-15) and `tests/test_07_settings.py`'s TD-32 backup-leak test (which reads a raw downloaded SQLite *file copy* produced by `backup_create()`'s whole-file copy feature — not a live query against a mirror).

**How to apply:** Phase 10 (mirror removal) is complete. Phase 11 (full SQLite removal) can now begin: delete `database/db.py`, `database/schema.sql`, and any obsolete `database/migrate_*.py` scripts; remove `sqlite3`/`get_connection` imports project-wide. The one known exception requiring a decision before Phase 11 can finish cleanly is `routes/setting.py`'s `backup_create()`/`data_backup()`, which still use `get_connection()` for a whole-file copy and `db_size` display — these read the SQLite *file* itself (a backup/diagnostic feature), not any table data, so removing `database/db.py` requires either repurposing or retiring that feature explicitly rather than leaving it silently broken.

### ADR-32: SQLite removed entirely (Phase 11) — `backup_create()` rebuilt as a per-admin Supabase export, fixing TD-32 as a side effect

**Decision:** every file that existed solely to create, connect to, or migrate the SQLite database is deleted outright: `database/db.py` (`get_connection()`/`initialize_database()`), `database/schema.sql`, `database/seed.py`, `database/init_db.py`, and all fourteen `database/migrate_*.py` one-time historical scripts (`migrate.py`, `migrate_audit_log.py`, `migrate_backfill_mirror_parity.py`, `migrate_backfill_settings_to_supabase.py`, `migrate_backup_log.py`, `migrate_cashbook_ledger.py`, `migrate_library_settings.py`, `migrate_membership_setting.py`, `migrate_notification_settings.py`, `migrate_receipt_settings.py`, `migrate_security_settings.py`, `migrate_settings_receipt_footer.py`, `migrate_to_supabase.py`, `migrate_transactions.py`). `app.py`'s `initialize_database()` startup call and its import are removed. `config.py`'s unused `DATABASE_PATH` setting is removed. The on-disk `database/library.db` file itself is left in place, untouched — it's already `.gitignore`d (never part of the repo), receives no further writes from any code path as of ADR-31, and deleting a real data file is a needless irreversible action when simply not referencing it achieves the same "SQLite is gone from the app" outcome; an operator can delete it by hand whenever they're satisfied Supabase has everything they need.

**Why now:** Phase 10 (ADR-26 through ADR-31) removed every mirror/bridge that wrote to SQLite. Once `routes/auth.py`'s `register()` bridge was gone (ADR-31), the only remaining SQLite touchpoint anywhere in live application code was `routes/setting.py`'s `backup_create()`/`data_backup()` — see below. With that resolved in the same slice, nothing in the app opens a SQLite connection, and the infrastructure that created/migrated that database has no remaining caller.

**Consequence — `backup_create()` rebuilt, not just deleted:** the old implementation used SQLite's `backup()` API to snapshot the *entire shared* `database/library.db` file and served it as a raw `.db` download — this was **TD-32**, a critical, previously undiscovered cross-tenant data leak (every admin could download every other admin's students, payments, and password hashes on demand; deliberately left unfixed during the 2026-07-22 QA sprint because "a correct fix means... a real per-admin data export across every admin-scoped table... new development, not a bug fix"). Removing SQLite entirely forces exactly that fix: the new `backup_create()` calls a new helper, `_collect_admin_backup_data(admin_id)`, which queries every admin-scoped Supabase table filtered to this admin only — directly via `.eq("admin_id", ...)` for `enquiries`/`students`/`cashbook`/`audit_log`/`library_settings`/`membership_settings`/`security_settings`, and via `.in_("student_id", ...)` (this admin's own student ids) for `memberships`/`payments`, which have no `admin_id` column of their own (see `docs/04_DATABASE_SCHEMA.md`) — plus this admin's own `admins` profile row with `password` explicitly excluded from the selected columns. The result is serialized to indented JSON and written to `backups/<admin>_<timestamp>.json` (previously a `.db` file), recorded via the existing `record_backup()`, and served as a download exactly as before. **This resolves TD-32** — see its updated `Resolved` status in `docs/11_FUTURE_WORK.md`.

**Consequence — `data_backup()`'s "Current Database Size" card removed:** that stat read `os.path.getsize(DATABASE_PATH)`, a SQLite-only concept with no single-file equivalent once every admin's data lives in one shared Supabase project — there's no "this admin's database size" to report without a materially bigger reporting feature than this phase's scope. The card (and `_format_file_size()`, now unused) is removed from both `routes/setting.py` and `templates/settings/data_backup.html`; "Last Backup Date" and "Backup Location" are unaffected and remain accurate (backups still land in the local `backups/` folder before being streamed to the client).

**Consequence — test infrastructure:** `tests/test_07_settings.py`'s `test_backup_create_leaks_entire_multi_tenant_database` (the test that documented TD-32 as an intentional, known-bad finding) is replaced with `test_backup_create_scoped_to_own_admin_only`, which seeds two admins, has one create a private student, and asserts the *other* admin's backup export contains none of that data and no password hash anywhere — proving the fix rather than documenting the defect. `test_backup_create_downloads_file_and_records_log`'s mimetype assertion updated from a SQLite-shaped guess to `"json" in resp.mimetype`.

**Consequence — stale comments corrected while editing nearby code:** `database/cashbook_queries.py`'s `insert_income_entry()` docstring and module docstring, and `database/payment_queries.py`'s module docstring, previously said `routes/membership.py`/`routes/payment.py` "only catch `sqlite3.Error`" around `record_payment()` — stale since ADR-29 widened those routes' `except` clauses to `APIError` alone (no SQLite write left to catch `sqlite3.Error` for). Corrected in place to describe the current, `APIError`-only shape; the underlying best-effort-vs-strict reasoning these comments explain is unchanged. `database/supabase_client.py`'s module docstring, which described itself relative to "`database.db.get_connection()`" (a file that no longer exists), rewritten to describe itself as the app's only remaining database access layer.

**Verification finding — an unrelated, pre-existing test bug this ADR's own full-suite run surfaced and fixed in the same slice:** `tests/test_09_full_workflow_chain.py::test_receipt_numbers_globally_unique_across_two_fresh_admins` failed intermittently during Phase 11 verification with spurious "duplicate" `receipt_number` values (e.g. `REC-5-2000`, `REC-3-5000`) that, checked directly against Supabase (`.eq("receipt_number", ...).select(count="exact")`), each had an exact count of **1** — not a real duplicate. Root-caused to the test's own pagination: it paged through the `payments` table via `.range(start, start + page_size - 1)` with no `.order()` clause, and PostgREST/Postgres does not guarantee stable row order across separate paginated queries without one — once the table grew past `page_size` (1000) rows (a natural side effect of this session's own extensive test runs), the same row could reappear across two pages, or rows could shift between them, producing a false-positive duplicate. This was a latent bug in the test itself, unrelated to any Phase 11 code change (confirmed: the immediately-prior full-suite run, before any Phase 11 change, passed this same test cleanly) — it simply hadn't been triggered before the table crossed the one-page threshold. Fixed by adding `.order("payment_id")` before `.range()`, making the pagination deterministic. Not logged as a new TD-N, since it was found and fixed in the same verification step rather than left open.

**How to apply:** Phase 11 is complete — no `sqlite3`, `get_connection`, `DATABASE_PATH`, or `database.db`/`database.seed`/`database.init_db`/`database.migrate_*` reference remains anywhere in the app's Python code (verified via a project-wide grep). Phase 12 (dead code / stale comment cleanup) is next — a lighter pass than any prior phase, since most of the obvious dead weight (mirror-write code, bridge code, migration scripts) was already removed as part of Phases 10-11 rather than left for a separate cleanup pass.

### ADR-33: One shared partial (`components/receipt_document.html`) for every receipt render, unrelated to the SQLite→Supabase migration (ADR-1 through ADR-32)

**Decision:** the professional receipt-document markup — logo, library name, receipt no./date/payment mode/student/plan/amount, footer, stamp/signature — lives in exactly one file, `templates/components/receipt_document.html`, parameterized by `{% set %}` variables the including template supplies. Both real render sites include it rather than each keeping their own copy: `templates/settings/receipt_settings.html`'s "Receipt Preview" card (mock data — unchanged visual output) and the new `templates/payments/receipt.html` (real payment data, rendered by `routes/payment.py`'s new `receipt(payment_id)`). `static/css/settings.css`'s `.receipt-preview-doc`/`.receipt-preview-logo`/`.receipt-preview-mark` rules were widened from `.settings-page`-scoped to global so the partial looks identical regardless of which page includes it.

**Why:** an audit of the payment/receipt flow (2026-07-25) found the receipt shown immediately after a successful payment didn't match the Receipt Preview's design — not because two templates disagreed, but because **no receipt was rendered after payment at all**. `routes/payment.py`'s `collect()` and `routes/membership.py`'s `create()`/`renew()` only ever `flash()`ed the receipt number and redirected to `student.view` (a payment-history table). The one template shaped like a post-payment receipt, `templates/payments/success.html`, was never wired to any route (TD-11) and, even if it had been, used a plain Bootstrap card+table design that didn't match the Preview's design at all. Building the missing real receipt page as a second, independent copy of the receipt markup would have "fixed" the immediate complaint while leaving the same drift-prone duplication that let the two designs diverge in the first place — one shared, parameterized partial makes that class of drift structurally impossible instead of relying on remembering to update both copies in lockstep.

**Consequence — `templates/payments/success.html` deleted, not kept as a second copy:** it was fully superseded by `templates/payments/receipt.html`, which serves the same purpose (a post-payment confirmation with real student/membership/amount data) using the shared partial instead of its own markup, plus a "Print / Save as PDF" button and a "Back to Student" link `success.html` never had. This also resolves the `payments/success.html` half of **TD-11** (its `create.html` and the unrelated `cashbook`/`reports` entries in the same TD-11 row remain open).

**Consequence — `record_payment()`'s return contract is untouched:** the new post-payment redirect needs the just-created payment's `payment_id`, but `record_payment()` (`database/payment_queries.py`) has returned only `receipt_number` since ADR-13 and is called from three call sites (`routes/payment.py`'s `collect()`, `routes/membership.py`'s `create()`/`renew()`). Rather than widen that return shape (a tuple, a dict, an optional kwarg — any of which is a breaking change for every existing caller), a small new lookup, `get_payment_id_by_receipt_number()`, resolves the `payment_id` from the `receipt_number` `record_payment()` already returns. This is safe because `payments.receipt_number` is enforced globally unique (`generate_receipt_number()`'s uniqueness loop, ADR-13) — the lookup can never be ambiguous.

**Consequence — no PDF library added; print and "download as PDF" are the same page:** `routes/payment.py`'s `receipt()` is the only new route. Printing and saving as PDF both use the browser's native `window.print()` on that same rendered page (a `@media print` rule hides the nav/sidebar/buttons), rather than adding a server-side PDF pipeline (e.g. WeasyPrint) — no such dependency existed anywhere in this codebase before this change, and TD-22 already documents `library_settings`' `auto_print`/`auto_email`/`open_pdf_after_save`/`duplicate_copy` columns as configured-but-unconsumed. Building that pipeline is a materially larger feature than "the same receipt everywhere" and is left as a distinct, larger follow-up rather than folded into this fix.

### ADR-34: Business Intelligence becomes a tabbed module via shared macros + a route-built placeholder-dict contract, not four independent pages

**Decision:** Business Intelligence is now four pages under one sidebar entry — the existing Overview (`index()`, visually untouched) plus three new UI-only pages, `purpose_analytics()`, `revenue_analytics()`, `occupancy_analytics()` — tied together by a single shared component file, `templates/components/bi_components.html`, and a single shared stylesheet, `static/css/business_intelligence.css` (extended, not forked per page). Two sub-decisions worth recording on their own:

1. **Macros, not `{% with %}{% include %}`, for the six shared components.** Every other component folder in this app (`stat_card.html`, `cashbook_summary_cards.html`, etc.) is included via `{% with title=..., value=... %}{% include "components/x.html" %}{% endwith %}`. `bi_components.html` uses real Jinja `{% macro %}`/`{% call %}` definitions instead (`tabs`, `analytics_header`, `kpi_card`, `chart_card`, `insight_card`, `analytics_table`), imported once per page as `{% import "components/bi_components.html" as bi %}`. The `{% with %}` pattern reads fine when a component appears once per page; these six appear repeatedly per page with different arguments each time (five `kpi_card()` calls in a KPI row, four `insight_card()` calls in an insights row) — five or six stacked `{% with %}...{% include %}...{% endwith %}` blocks per row is harder to scan than five `{{ bi.kpi_card(...) }}` calls, and `chart_card`/`analytics_table` need an arbitrary inner body (a `<canvas>`, a `<thead>`/`<tbody>`) that only `{% call %}` expresses cleanly. This is a deliberate, scoped exception to the codebase's dominant pattern, not a silent drift — see `templates/components/bi_components.html`'s card in [FILE_REFERENCE.md](FILE_REFERENCE.md) for the reasoning restated next to the code.
2. **Placeholder data is built server-side, in the same dict shape a future real query would return, not embedded in the template or left for client-side JS to invent.** Each new route calls a `_*_placeholder()` function (`_purpose_analytics_placeholder()` etc.) that returns a plain dict — KPIs, one Chart.js-ready `{labels, datasets}` block per chart, and a list of table rows — which the route passes to `render_template()`, which the template dumps into a `window.bi*ChartData` JS global via `{{ data | tojson }}`, which a page-specific JS file (`static/js/bi_purpose_analytics.js` etc.) reads to build Chart.js instances. This is the exact same shape `index()`/`business_intelligence.js` already used for the Overview page's real data (`window.biChartData`) — reusing it here means a future phase closing **TD-46** only has to replace a `_*_placeholder()` function body with a real `database/bi_queries.py` (or new) query returning the same shape; the template, macros, CSS, and JS files need no changes at all.

**Why now:** the task was explicitly scoped to "UI structure and navigation" only — no analytics calculations, no backend queries, no chart data from real sources, and no redesign of the existing Dashboard or BI Overview page. A tab bar shared across four pages, plus reusable card/table primitives, plus a data contract that already matches what real data will eventually look like, is what makes "future backend implementation only requires replacing placeholder data" (the task's explicit requirement) actually true rather than aspirational.

**Consequence — Overview page has exactly one line changed:** `templates/business_intelligence/index.html` gained `{% import "components/bi_components.html" as bi %}` and `{{ bi.tabs('overview') }}`, placed after its flashed-messages block and before its pre-existing `.bi-section` header. Every `bi_*` component it already included, and every value `index()` computes, is untouched — verified by running the existing test suite (`tests/test_05_dashboard_bi_analytics.py` and the full suite) unmodified and green after this change.

**Consequence — three new Technical Debt/Planned-Feature entries, deliberately, not accidentally:** **TD-46** (the three new pages show identical, fabricated figures to every admin until wired to real data) and **PF-6** (no filters/export/drill-down on any of the three yet) in [11_FUTURE_WORK.md](11_FUTURE_WORK.md) exist so nobody mistakes "Sample data"-badged charts for real per-admin analytics, or mistakes the deliberately narrow scope of this phase for an oversight.

**How to apply:** when a future phase wires real data into Purpose/Revenue/Occupancy Analytics, replace only the three `_*_placeholder()` function bodies in `routes/business_intelligence.py`, scoping each query to `session["admin_id"]` the way every other `database/bi_queries.py` function already does — do not touch `templates/business_intelligence/{purpose,revenue,occupancy}_analytics.html`, `components/bi_components.html`, or the three `static/js/bi_*.js` files unless the *shape* of the returned dict needs to change (e.g. a new KPI), in which case update the placeholder builder, the real builder, and the consuming template/JS together in the same change.

**How to apply:** any future third render site for a receipt (an emailed copy, a bulk-print view, etc.) should `{% set %}` its variables and `{% include "components/receipt_document.html" %}`, the same as the two sites above — never recreate the receipt markup inline. If the receipt's visual design itself needs to change, `receipt_document.html` is the only file to edit; every render site picks up the change automatically.

### ADR-35: Purpose Analytics wired to real data by merging two existing admin-isolated queries in Python, not a new Supabase view/RPC

**Decision:** `routes/business_intelligence.py`'s `purpose_analytics()` now calls `_purpose_analytics_data(admin_id)`, which calls a new `database/bi_queries.py` function, `get_purpose_breakdown(admin_id)`. That function reuses `database.membership_queries.get_admin_students()` (source of each student's `purpose`) and `database.payment_queries.get_payments_for_admin()` (source of `amount_paid`) unmodified, and merges the two lists on `student_id` in plain Python — no new Supabase table, view, or RPC was added, and neither existing query function was changed.

**Why:** this closes the Purpose Analytics slice of **TD-46** exactly the way ADR-34 already committed to: replace only the `_*_placeholder()` function body, keep the same returned dict shape, touch no template/JS. PostgREST (the Supabase client this codebase uses) has no server-side JOIN, so every other cross-table read in this app (`get_memberships_for_admin()`, `get_payments_for_admin()`, `_fetch_payments_for_admin()`) already fetches each table separately and merges in Python — `get_purpose_breakdown()` follows that same established shape rather than introducing a new one (e.g. a `students_purpose_revenue` database view), which would be the first schema change this module has ever needed and a bigger blast radius than the task called for.

**Consequence — counts every student regardless of `students.status`:** `get_admin_students()` doesn't filter by `status`, so Purpose Analytics' "Total Students" includes both Active and Inactive students, matching the Students list page's total — **not** `routes/dashboard.py`'s "Total Students" KPI, which filters `status = 'Active'`. These two "Total Students" figures can legitimately differ; that's a scope difference (all students ever admitted vs. currently-active only), not a bug. Documented on `get_purpose_breakdown()`'s own docstring and its [FILE_REFERENCE.md](FILE_REFERENCE.md) card so it isn't "fixed" into agreement by a future change without noticing the two are answering different questions.

**Consequence — a student with no `purpose` (blank/whitespace) or a payment whose student isn't found in the students fetch both fall under `NO_PURPOSE_LABEL` ("Not Specified"), never silently dropped:** this keeps `sum(students across rows)` and `sum(revenue across rows)` always equal to the admin's true totals — the KPI cards and the summary table's percentage columns would otherwise quietly undercount if either case were filtered out instead.

**Consequence — the "Sample data" badge on `purpose_analytics.html`'s chart/table cards is now inaccurate, left as a known gap (TD-47):** the task this shipped under was scoped to "no template/CSS changes beyond placeholder *values*", and the badge is a static macro parameter in `components/bi_components.html`, not a `data` field — fixing it requires a template change the task explicitly excluded, so it's tracked rather than silently patched.

**How to apply:** when Revenue Analytics / Occupancy Analytics (the remaining two pages in TD-46) get their own real-data pass, follow the same shape: one new `database/bi_queries.py` function per page, built by merging existing admin-isolated query functions (`get_admin_students`, `get_memberships_for_admin`, `get_payments_for_admin`, Cashbook's monthly/category getters) in Python rather than adding new Supabase views/RPCs, unless a future performance problem specifically justifies that larger change.

### ADR-36: Centralized input normalization — one shared `utils/normalization.py`, four field families, Cashbook's own category/payment-method fields deliberately excluded

**Decision:** Added `utils/normalization.py`, a single module of five pure string functions, and routed every route that inserts/updates a Category (Purpose, Shift, Membership Plan, Payment Mode), person-Name (Student/Owner Name), Location (City, State), free-text (Address, Remarks, Receipt Footer), or phone-number field through it, instead of each route writing its own `.upper()`/`.title()`/`.strip()`. Category fields are stored UPPERCASE, name/location fields Title Case, free text and phone numbers only whitespace-trimmed/collapsed (casing untouched). A one-time script, `database/migrate_normalize_input_data.py`, applied the same rules to every pre-existing row (4,760 rows updated across `enquiries`/`students`/`memberships`/`payments`/`library_settings` on the run that shipped this change).

**Why:** the same real-world value ("upsc" / "Upsc" / "UPSC") entered through different admins/sessions was being stored as distinct strings, which silently fragmented `database/bi_queries.py`'s `get_purpose_breakdown()`, `routes/membership_distribution.py`'s plan-wise counts, and any future category-grouped report into multiple rows for what should be one bucket — the exact failure mode Purpose Analytics (ADR-35) needs *not* to have. A single shared module (rather than one `.upper()` call added per route) is what makes "every module uses the same helper" actually true instead of aspirational, matching the precedent `database/membership_queries.py`'s `get_effective_status()` already set for "one definition, not N copies of the same rule" (TD-6).

**Consequence — three call sites needed a matching fix, not just a routes/*.py change, because they compare a normalized DB value against a hardcoded Title-Case literal:**
1. `templates/students/edit.html`'s Purpose/Shift `<select>`s compare `student.purpose`/`student.shift` against `"Study"`/`"Morning"`/etc. to decide which `<option>` is pre-selected — updated to compare against the UPPERCASE equivalents (`"STUDY"`/`"MORNING"`/etc.) so editing a student still shows their actual saved value selected, instead of always defaulting to the first option.
2. `routes/membership_distribution.py`'s `plan_counts`/`plan_percentages` are keyed by the Title-Case labels `templates/components/membership_summary_cards.html`/`membership_progress.html` index directly (`plan_counts["Monthly"]`, hardcoded in the template) — rather than edit those templates, `PLAN_ORDER`'s labels were left as Title Case and a `_PLAN_LOOKUP = {normalize_category(plan): plan for plan in PLAN_ORDER}` dict maps a normalized DB value back to its display label before counting. Zero templates changed; the plan-wise cards on Membership Distribution are pixel-identical.
3. `utils/charts.py`'s `PLAN_CHART_COLORS` dict (donut/pie slice colors) is keyed directly by `m["plan_name"]` — its keys were updated to the UPPERCASE labels to match, and both chart functions now normalize `plan_name` before using it as a dict key, so a pre-migration row with a different case still merges into the same slice instead of splitting it.

**Consequence — Cashbook's own `category`/`payment_method` fields (`database/cashbook_categories.py`) are deliberately excluded from this entire pass:** they're a separate concept from the four Category fields this task named (Purpose/Shift/Membership Plan/Payment Mode), already validated against a fixed, already-consistent list (`MANUAL_INCOME_CATEGORIES`/`MANUAL_EXPENSE_CATEGORIES`/`PAYMENT_METHODS`, all Title Case), and `database/cashbook_queries.py`'s `get_cash_balance()` has a hardcoded `row["payment_method"] != "Cash"` comparison. Because `database/payment_queries.py`'s `record_payment()` is the one place a Category field (`payment_mode`, chosen on the Membership/Payment forms) feeds into a Cashbook automatic entry (via `insert_income_entry(..., payment_method=payment_mode, ...)`), normalizing `payment_mode` for the `payments` table write and then also passing the *normalized* value into that Cashbook call would have written `"CASH"` into `cashbook.payment_method` for automatic entries while manual entries kept writing `"Cash"` — splitting that one column by capitalization, exactly the bug this task exists to fix, just relocated into Cashbook. `record_payment()` therefore normalizes only the `payments.payment_mode` copy and passes the caller's original value to `insert_income_entry()` unchanged.

**How to apply:** any new form field that's a fixed-vocabulary category, a person's name, a city/state, free text, or a phone number should call the matching `utils/normalization.py` function, not a local `.upper()`/`.title()`/`.strip()`. If Cashbook's `category`/`payment_method` are ever normalized too, it must happen for **both** manual (`routes/cashbook.py`) and automatic (`database/payment_queries.py` → `insert_income_entry()`) entries in the same change, plus updating `PAYMENT_METHODS`/`get_cash_balance()`'s `"Cash"` comparison/the Cashbook filter dropdown together — normalizing only one write path would recreate this exact split. See TD-48 in [11_FUTURE_WORK.md](11_FUTURE_WORK.md).

**Update (2026-07-26, Normalization Audit — same day):** a full audit of every `.insert()`/`.update()`/`.upsert()` call site found three more write paths still bypassing `utils/normalization.py`: `routes/auth.py`'s `register()` (`admins.full_name`/`mobile`, raw `.strip()` only), `routes/setting.py`'s `receipt_settings()` (`receipt_prefix` via its own local `.strip().upper()` instead of `normalize_category()`; `receipt_footer` — a second write path to the column `library_profile()` already normalized — via raw `.strip()`), and `routes/cashbook.py`'s `add_transaction()`/`edit_transaction()` (`person`/`description`, written completely raw, not even trimmed). All three fixed the same way as every other write path — `category`/`payment_method` on the Cashbook forms remain untouched, per the exclusion above. `database/migrate_normalize_input_data.py`'s `TABLE_RULES` was extended to `admins`/`cashbook` accordingly.

That same extension surfaced two bugs in the migration script itself, both reproduced and fixed live: an unranged `supabase.table(t).select("*").execute()` is silently capped at PostgREST's max-rows (1000 on this project), so the first two runs only ever normalized each table's first 1000 rows (every table here now holds several thousand); and a bulk-`.upsert()` rewrite meant to reduce network round trips was reverted after it nulled out a `NOT NULL` column on a live row — Postgres validates every `NOT NULL` column against an upsert's tentative INSERT row before `ON CONFLICT DO UPDATE` resolves, so any column absent from a `field_rules`-derived payload fails that constraint even on an existing row. See `database/migrate_normalize_input_data.py`'s own "Fixed" note in [FILE_REFERENCE.md](FILE_REFERENCE.md) and the same-day [CHANGELOG.md](CHANGELOG.md) entry for the corrected run's actual row counts (7,652 rows, superseding the first run's undercounted 4,760).

### ADR-37: Revenue Analytics wired to real data — Payments/Memberships-scoped throughout, New-vs-Renewal classified by membership order rather than the best-effort Cashbook `source` label

**Decision:** `routes/business_intelligence.py`'s `revenue_analytics()` now calls `_revenue_analytics_data(admin_id)`, which calls eight new `database/bi_queries.py` functions (`get_revenue_time_windows`, `get_monthly_fee_revenue`, `get_revenue_by_plan`, `get_revenue_by_payment_mode`, `get_payment_mode_usage_counts`, `get_new_vs_renewal_revenue`, `get_revenue_collection_summary`, `get_avg_revenue_per_student`) plus the existing `get_purpose_breakdown()`. `_revenue_analytics_placeholder()` is deleted outright (not kept, unlike Purpose Analytics' own placeholder). Every KPI/chart is deliberately **Payments/Memberships**-scoped, never `cashbook_queries.get_monthly_income()`'s broader all-Cashbook-income total (donations, library fines, book sales) — the same fee-revenue-vs-total-income distinction ADR-11 already drew for the Business Health Score and Purpose Analytics (ADR-35).

**Why:** same reasoning as ADR-35 — PostgREST has no server-side JOIN, so every new helper fetches `get_payments_for_admin()`/`get_memberships_for_admin()` (both already admin-isolated) and merges/aggregates in Python rather than adding a Supabase view or RPC. Task scope named 15 explicit metrics (time-window revenue, plan/purpose/payment-mode breakdowns, new-vs-renewal split, expected/collected/pending/collection %) that the placeholder never had cards for, so unlike Purpose Analytics' drop-in replacement, `revenue_analytics.html`/`bi_revenue_analytics.js` gained new KPI cards and two new chart canvases (`paymentModeChart`, `newVsRenewalChart`) and a new Business Insights row (same macro-based shape `purpose_analytics.html` already established) — every pre-existing chart/KPI kept its original id and shape, so this was additive, not a redesign.

**Consequence — "New Admissions vs Renewal Revenue" is classified from `memberships.membership_id` ordering, not Cashbook's `source` column:** `routes/membership.py`'s `create()`/`renew()` already tag their automatic Cashbook entries `source="Admission"`/`"Renewal"`, which looks like the obvious classification source. It was deliberately **not** used: `database/cashbook_queries.py`'s `insert_income_entry()` is best-effort (bare `try/except: pass`, TD-43) with no SQLite fallback left since ADR-27 — a dropped write means that Cashbook row (and its `source` tag) never existed at all, which would silently misclassify or drop that payment's revenue from both buckets. `get_new_vs_renewal_revenue()` instead compares each payment's `membership_id` against that student's own lowest `membership_id` (their first membership), reading only `payments`/`memberships` — both strict, ADR-28/29 — so the split stays correct even after a Cashbook mirror-write failure.

**Consequence — Expected/Collected/Pending read `memberships.total_fee`/`paid_amount`/`pending_amount` directly, not `SUM(payments.amount_paid)`:** these three columns hold the invariant `total_fee == paid_amount + pending_amount` for every row (enforced by `routes/membership.py`'s `create()`/`renew()` at insert time and `routes/payment.py`'s `collect()` on every collection), so `get_revenue_collection_summary()` sums them directly across every membership regardless of status (Active or Expired) — the same "count everything, not just currently-Active" scope `get_pending_fees()` already uses. `Collected` (sum of `paid_amount`) and the page's separate `Total Revenue` KPI (sum of `payments.amount_paid`, via `get_revenue_time_windows()`) are two different queries that land on the same number by construction, not a coincidence — if a future change ever lets a payment adjust `amount_paid` without a matching `memberships.paid_amount` update (or vice versa), these two KPIs would silently diverge and that's the first place to look.

**Consequence — the "Sample data" badge gap TD-47 documented for Purpose Analytics does not recur here:** `revenue_analytics.html`'s five `chart_card()`/`analytics_table()` macro calls all pass `sample=False` in this same change, rendering the "Live Data" badge immediately rather than leaving a stale "Sample data" label to fix in a follow-up.

**How to apply:** when Occupancy Analytics (the last page in TD-46) gets its own real-data pass, follow the same shape: new `database/bi_queries.py` functions built by merging existing admin-isolated queries in Python, additive template/JS changes only where a metric has no existing chart/KPI slot to reuse, and `sample=False` passed on every macro call in the same commit that wires up real data — not as a follow-up fix.

### ADR-38: Occupancy Analytics wired to real data — seat capacity is a new, genuinely-configurable `library_settings` field, not a fabricated number; "occupied" means a currently effectively-active membership, not every student ever admitted

**Decision:** `routes/business_intelligence.py`'s `occupancy_analytics()` now calls `_occupancy_analytics_data(admin_id)`, which calls seven new `database/bi_queries.py` functions (`get_shift_capacities`, `get_active_memberships`, `get_shift_occupancy`, `get_occupancy_summary`, `get_occupancy_by_purpose`, `get_occupancy_by_plan`, `get_purpose_shift_matrix`, `get_monthly_occupancy_trend`, `get_occupancy_insights`). `_occupancy_analytics_placeholder()` is deleted outright, closing the last placeholder page from TD-46/PF-6.

Unlike Purpose/Revenue Analytics (ADR-35/37), this page's KPIs (Total/Occupied/Available Seats, Occupancy %) fundamentally need a *capacity* — and no seat/capacity concept existed anywhere in the schema before this change (confirmed by reading the full schema, not assumed). Rather than fabricate a number (the old placeholder's hardcoded 80/80/60), three new nullable columns were added to `library_settings`: `morning_capacity`/`afternoon_capacity`/`evening_capacity` (`INTEGER DEFAULT 50` each), editable from a new "Seating Capacity" section on Settings > Library Profile (`routes/setting.py`'s `library_profile()`, `templates/settings/library_profile.html`). This was an explicit user decision among three options (add a real setting / derive capacity from peak historical occupancy / drop the seat-limit framing entirely) — the real-setting option was chosen specifically so "Available Seats" answers "how many physical chairs are free," not a proxy.

**Why the schema change couldn't be applied directly, and what was done instead:** this codebase has no direct-Postgres/`psycopg2` path (ADR-14) — only the `supabase-py` REST client, which cannot execute DDL. Verified live before writing any code: `select("admin_id, morning_capacity")` against the real `library_settings` table returns Postgres error `42703` ("column does not exist"), and no `exec_sql`/`run_sql`/generic DDL RPC exists in this project either (probed `exec_sql`, `execute_sql`, `run_sql`, `pg_execute`, `migrate_reset_identity_sequence` — all `PGRST202`, not found). The three columns are documented in `database/supabase_migration.sql` (merged into `library_settings`'s `CREATE TABLE`, per that file's own convention) with the exact `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...` statement an existing Supabase project's owner must run once, by hand, in the SQL Editor — the same "print the copy-pasteable SQL, since this app can't run it itself" precedent ADR-14 already set for the identity-sequence RPC.

Because that manual step may not have happened yet on any given deployment, `database/settings_queries.py`'s `create_library_settings()`/`update_library_settings()` attempt the full payload (including the three capacity fields) first, and — only on a `42703` error specifically — retry once with those three keys stripped out. This is a deliberate, verified-necessary fallback (not a defensive-programming reflex for something that "can't happen" — it was reproduced live moments before this code was written), and it means Library Profile saving never breaks for any admin regardless of whether the ALTER TABLE has been run yet; the capacity fields simply don't persist until it has. `database/bi_queries.py`'s `get_shift_capacities()` reads with `.get(..., DEFAULT_SHIFT_CAPACITY)` for the same reason — `get_library_settings()`'s `select("*")` never errors on a missing column, it just won't be a key in the returned dict.

**Consequence — "occupied" means a currently effectively-active membership, not every student ever admitted:** unlike `get_purpose_breakdown()` (ADR-35), which deliberately counts every student regardless of `status` to match the Students list page, occupancy is about who is physically using a seat *right now* — `get_active_memberships()` filters through `database.membership_queries.get_effective_status()` (the same shared status logic TD-6 centralized) and dedupes to one row per student (the highest `membership_id`, for the rare case of an overlapping duplicate). A student whose membership expired no longer holds a seat in this page's numbers, even though they remain a permanent row in `students` and in Purpose Analytics' totals — these two pages are deliberately answering different questions, the same documented divergence ADR-35 already established for "Total Students."

**Consequence — a shift value outside Morning/Afternoon/Evening is bucketed as "Other," never dropped or mis-tallied:** `students.shift` is free text upstream of `students/edit.html`'s 3-option dropdown (an enquiry's `preferred_shift` placeholder text explicitly suggests "Full Day" as a valid answer, and normalization only uppercases whatever was typed — it doesn't constrain the vocabulary). `_canonical_shift()` maps anything not exactly `MORNING`/`AFTERNOON`/`EVENING` to `OTHER_SHIFT_LABEL`, which the Shift Distribution chart and Purpose Shift Matrix table both surface when non-empty (`get_purpose_shift_matrix()`'s `columns` only grows a 4th "Other" entry when at least one active membership actually falls into it) — no seat capacity is defined for "Other" (it isn't one of the three configurable shifts), so it counts toward `total_occupied`/`total_available` but never toward any single shift's own utilization %.

**Consequence — Monthly Occupancy Trend is reconstructed from `memberships.joining_date`/`end_date` ranges, not a real historical snapshot:** there is no attendance/seat log anywhere, so a past month's occupancy is approximated as "how many distinct students had a membership whose `[joining_date, end_date]` range overlapped that month," measured against **today's** configured capacity (there's no historical capacity snapshot either — a capacity change retroactively reshapes every past month's percentage too). This is a real, data-derived reconstruction, not a fabricated trend line, but it is an approximation — documented on `get_monthly_occupancy_trend()`'s own docstring and tracked as **TD-49** rather than presented as more precise than it is.

### ADR-39: AI Center is a rule-based retention-risk score, not a trained model — Phase 1 ships Student Risk Analysis only, purpose is deliberately unscored

**Decision:** A new module, `database/ai_center_queries.py` + `routes/ai_center.py` (`/ai-center/`), adds a per-student retention-risk score (0-100, bucketed High `<40`/Medium/Low `>70`) computed as a weighted blend of three rule-based signals — unpaid-balance age (45%), renewal/expiry timing (35%), membership plan length (20%) — with every "why is this student at risk" reason being the literal rule that fired, not a separate explanation layer. This is Phase 1 of a larger, explicitly phased AI Center build: it ships **only** the Student Risk Analysis page. An aggregate Prediction Dashboard (Phase 2) and admin-configurable thresholds/weights (Phase 3, AI Center Settings) are deliberately deferred — each phase is a complete, independently useful vertical slice, not a partially-wired feature. A planned AI Chat Assistant (natural-language business Q&A) is a separate, later initiative, not part of this module at all.

**Why rule-based, not machine learning:** there is no labeled "did this student churn" outcome anywhere in the schema, and no attendance/visit log to draw a real predictive signal from (confirmed by reading the full schema, not assumed — see TD-49's occupancy note for the same gap in a different module). Training a classifier against noise would produce a number that looks precise but isn't grounded in anything verifiable. A rule-based score, by contrast, is exactly as trustworthy as the rules themselves, which are visible and auditable — the same reasoning `database/bi_queries.py`'s `get_business_health_score()`/`get_action_items()`/`get_occupancy_insights()` already established for "AI Insights" elsewhere in this app (all rule-based, none ML). `requirements.txt` has no `scikit-learn`/`pandas` and none were added for this — a future phase that has real labeled outcomes to train against should reconsider, not this one.

**Why `purpose` (free text — UPSC/NEET/JEE/etc.) is not a scoring signal:** unlike the other three signals, there is no verified evidence in this data that any purpose category correlates with churn — adding a weight for it would be a guess dressed up as insight, the exact failure mode this ADR's first paragraph is trying to avoid. Tracked as **TD-52** so it isn't silently forgotten if outcome data ever accumulates to check this against.

**Why the payment-delay signal is a proxy:** `payments` has no due-date column, so "delay" is measured from the last actual payment made on the membership (or from `joining_date` if none has been made yet), not true days-overdue. Documented on `_payment_delay_signal()`'s own docstring and tracked as **TD-51**.

**Consequence — reasons and actions are generated 1:1 from the same signal, in the same weighted order:** `compute_student_risk()` returns a single ranked list where each entry's `reason` and `action` come from the same signal function call — there is no separate "recommendation engine" to keep in sync with the scoring engine, matching this codebase's existing "AI Insights" pattern of computing insight text directly alongside the numbers that justify it.

### ADR-40: AI Center Settings — weights/thresholds are a new admin-scoped table, not hardcoded module constants, and Phase 3 (Settings UI) was pulled forward ahead of Phase 2 (aggregate dashboard)

**Decision:** The three signal weights and two risk-level thresholds ADR-39 introduced as `database/ai_center_queries.py` module constants (`DEFAULT_WEIGHTS`, `HIGH_RISK_MAX`, `LOW_RISK_MIN`) are removed from that module entirely and replaced with a new admin-scoped table, `ai_center_settings` (one row per `admin_id`, same shape as `membership_settings`/`security_settings`), read through a new `database/ai_center_settings_queries.py`. `compute_student_risk()` now calls `get_effective_settings(admin_id)` once per request and threads the result through every signal function — changing a weight in Settings changes scoring on the very next request, with no code change and no redeploy. A new page, `routes/ai_center.py`'s `settings()` (`/ai-center/settings`), lets an admin actually edit these values — pulling forward what the original phased plan called "Phase 3," ahead of Phase 2's aggregate Prediction Dashboard, because a config layer with no way to edit it isn't actually configurable. The two AI Center pages (Student Risk Analysis, Settings) now share an in-page tab bar (`templates/components/ai_center_components.html`'s `tabs()` macro, mirroring `bi_components.html`'s precedent) rather than a second sidebar entry, matching the reasoning already recorded in `templates/ai_center/`'s `FILE_REFERENCE.md` card.

**Why a new table, not `library_settings`:** same reasoning as ADR-9's Membership/Security Settings split — AI Center's weights/thresholds are a distinct concern from library-profile data, and a dedicated table keeps `library_settings` from accumulating unrelated columns.

**Why validation lives in the route, not a DB constraint:** the three weights must sum to 100, and `high_risk_max` must be less than `low_risk_min` — both are cross-column invariants Postgres could enforce with a `CHECK` constraint in principle, but this app has no path to add one to a live Supabase project without the same manual-application problem described below, and `routes/ai_center.py`'s `_parse_settings_form()` already has to parse and range-check the submitted values regardless. Enforcing it once, in the route, before any write is attempted, was chosen over a DB constraint that would just convert a bad request into an unhandled `APIError` instead of a clear flashed message.

**Why this table needs manual, one-time application, same as ADR-38's capacity columns:** this app has no DDL path of its own — no `exec_sql`/`run_sql` RPC, no direct-Postgres/`psycopg2` connection (ADR-14). Unlike ADR-38 (three new *columns* on an existing table), this is a brand-new *table*, which makes the gap sharper: there are no existing rows to fall back to, only "the table doesn't exist yet." Verified live against the project this app's own test suite runs against: `.select()`/`.upsert()` against `ai_center_settings` both raise `postgrest.exceptions.APIError` with code `PGRST205` ("Could not find the table … in the schema cache") until the `CREATE TABLE` in `database/supabase_migration.sql` is run by hand in the Supabase SQL Editor. `get_ai_center_settings()` catches this the same way `get_membership_settings()` catches any read failure — returning `None`, which `get_effective_settings()` overlays with `DEFAULTS` — so a project that hasn't applied the migration yet scores exactly as it did before this change (45/35/20, 40/70), just via the DEFAULTS fallback path instead of a hardcoded constant. `save_ai_center_settings()`'s write has no such fallback (there's nothing to fall back to without a table) — it raises, and `routes/ai_center.py`'s `settings()` catches that specific failure to flash "this Supabase project is missing the `ai_center_settings` table" instead of a 500. Tracked as **TD-53** until the table is confirmed applied.

**Consequence — `get_risk_level()`'s signature changed:** it now takes `high_risk_max`/`low_risk_min` as parameters instead of reading module constants, since those constants no longer exist. Its only caller, `compute_student_risk()`, was updated in the same change; there was no other call site.

### ADR-41: Student Risk Analysis search is a JSON-backed autocomplete with explicit selection, not a full-page-reload search

**Decision:** The old `?q=`-driven search (`routes/ai_center.py`'s `index()` rendering a server-side matches list, `templates/ai_center/student_risk.html`'s now-deleted `.ai-match-list`) is replaced by a live autocomplete: a new JSON endpoint, `GET /ai-center/student-suggestions`, backed by `database/ai_center_queries.py`'s `search_students()` (unchanged matching logic — case-insensitive, partial, on name or mobile), and a new `static/js/ai_center_search.js` that debounces keystrokes (250ms), fetches suggestions, and renders them in a dropdown (`templates/components` gained no new file — the markup lives directly in `student_risk.html`, since nothing else needs it). `index()` no longer reads or renders a `q` parameter at all — the only way to load a student's risk breakdown is `?student_id=`, set by the JS only when the admin explicitly clicks or arrow-keys-then-Enters a suggestion. Typing alone never selects, computes, or renders anything past the dropdown itself.

**Why explicit selection, not auto-select-first-match:** the request was specific that ambiguous names (multiple students sharing a name) must all be shown, not silently resolved to one. A dropdown the admin picks from is the only version of "search" that can't guess wrong on their behalf — auto-selecting the first/best match on Enter would reintroduce exactly the ambiguity risk this was meant to remove.

**Why each suggestion carries `plan_name` from a single extra query, not N+1 lookups:** `search_students()` now also fetches `database.membership_queries.get_memberships_for_admin()` once (only when there's at least one match) and indexes each student's latest membership's `plan_name` in Python — the same fetch-all-then-merge shape every other cross-table read in this codebase already uses (there's no server-side JOIN available), not a new pattern invented for this feature.

**Why "Library ID" is `LIB` + the zero-padded `student_id`, not a new field:** this exact format (`LIB{{ "%04d"|format(student.student_id) }}`) is already how every other student-facing page in the app (`students/index.html`, `students/view.html`, `memberships/*.html`, `payments/create.html`, `notification/index.html`) displays a student's ID — the autocomplete dropdown reuses it (client-side, in `ai_center_search.js`, since suggestions are JS-rendered) rather than inventing a second ID format for one page.

**Addendum (2026-07-27) — `ai_center_settings` was created with RLS enabled; no policies are needed.** This app's `database/supabase_client.py` connects with `SUPABASE_SECRET_KEY` — Supabase's service-role-equivalent key, which bypasses Row Level Security unconditionally, independent of whether any policy exists. Verified live immediately after the table was created: `.select()` returned real rows and `.upsert()` persisted a real save with RLS already on, with zero policies defined. This is consistent with every other table in the schema — ADR-2 already established that this app's *only* tenant-isolation mechanism is manual `admin_id` filtering in application code, not RLS ("there is no framework-level enforcement... a query that forgets the filter would leak cross-tenant data"). Adding RLS policies here would be redundant with that existing model, not a second layer of real defense, since the app never connects with a key RLS would actually constrain — the same reasoning would apply to enabling RLS on any other table in this schema. TD-53 is `Resolved` as of this verification.

**How to apply:** if a future change adds a real seat/attendance log (e.g. a check-in table), `get_shift_occupancy()`/`get_monthly_occupancy_trend()` are the two functions to replace — everything downstream (`get_occupancy_summary()`, the KPIs, all four charts, both tables, `get_occupancy_insights()`) already consumes their output shape and wouldn't need to change. If another Settings field ever needs the same "documented in `supabase_migration.sql`, but the live database might not have it yet" shape, reuse this ADR's fallback pattern (`_is_undefined_column_error()`/`_insert_with_capacity_fallback()`/`_update_with_capacity_fallback()` in `database/settings_queries.py`) rather than inventing a new one.

### ADR-42: AI Center Settings' inline help is a small hand-rolled popover component, not Bootstrap's native Tooltip/Popover JS

**Decision:** The "ⓘ" contextual help added to every Settings field (`aic.info_tip()` in `templates/components/ai_center_components.html`, styled/scripted by `static/css/ai_center.css` and `static/js/ai_center_settings.js`) is a small self-contained show/hide component — a `<span>` toggled via a CSS class on hover, tap/click, or keyboard focus — rather than Bootstrap 5.3.7's built-in `Tooltip`/`Popover` component, even though `bootstrap.bundle.min.js` (which includes both) is already loaded globally in `templates/layouts/base.html`.

**Why not Bootstrap's native component:** grepping the codebase (`docs/07_STATIC_ASSETS.md`) turned up zero existing uses of `data-bs-toggle="tooltip"`/`"popover"` anywhere in this app — Bootstrap's JS bundle is loaded for its other components (modals, dropdowns) but its Tooltip/Popover constructors are never manually instantiated (`new bootstrap.Tooltip(...)`), which Bootstrap 5 requires per-element since it doesn't auto-init them. Introducing that initialization pattern for one page would add a first-of-its-kind dependency wiring (opt-in JS init, `data-bs-*` attribute contract, Popper.js positioning under the hood) for a need a ~40-line vanilla-JS toggle already covers, and it would need to work identically on hover (desktop) and tap (mobile) — Bootstrap's default tooltip trigger is hover/focus only, tap support needs the same kind of custom click-handling this component already does, so adopting Bootstrap's version wouldn't actually remove the custom JS, just add a second layer under it.

**Why hand-rolled instead of a shared cross-page component:** unlike `bi_components.html`'s macros (reused across four Business Intelligence pages), `info_tip()` only has one caller today (`settings.html`) — it was added to `ai_center_components.html` (already imported by both AI Center pages) rather than a new shared file, following the same "extract only what's actually shared, when a second real use exists" reasoning ADR-40's `ai_center_components.html` note already documents.

**How to apply:** if inline help is ever needed on a page outside AI Center, don't copy `ai_center.css`'s `.ai-info-tip`/`.ai-info-popover` rules verbatim — they're intentionally scoped under `.ai-center-page` (same isolation pattern as every other AI Center style). Either lift the macro + CSS into a shared, unscoped component at that point (two real call sites justifies extraction, per the precedent above), or reconsider Bootstrap's native Tooltip/Popover if by then more than one page wants the same hover/tap-help pattern — at that point the initialization boilerplate is amortized across more call sites and may be worth it.

### ADR-43: Panda AI Assistant — a self-contained `panda/` package, dummy responses only, insights computed on the fly

**Decision:** The floating "Panda" assistant widget (visible on every authenticated page) is built as its own top-level package — `panda/routes.py`, `services.py`, `prompts.py`, `notifications.py`, `insights.py`, `forecasting.py` — instead of splitting across the existing flat `routes/`/`database/` folders every other feature uses. It ships with no real language model: `panda/prompts.py`'s `generate_placeholder_reply()` returns one fixed, honest "not connected to a real AI yet" string for every message, and `panda/forecasting.py` is entirely `NotImplementedError` stubs wired into nothing. Chat history (`panda_conversations`/`panda_messages`, admin-scoped, multi-conversation) is real and persisted via `database/panda_queries.py`, following the same Supabase-native, admin_id-isolated pattern as every other query module. "Today's AI Insights" (revenue trend, expiring memberships, seat under-utilization) are computed fresh on every request by `panda/insights.py`/`notifications.py` — reusing `database/bi_queries.get_revenue_growth`/`get_occupancy_summary` and `routes/notification.get_notification_summary` — with no new table and no read/dismiss state.

**Why a separate package instead of `routes/panda.py` + `database/panda_*.py`:** Panda is designed to be independently swappable — the explicit goal of this phase is that wiring in a real LLM later only touches `panda/prompts.py` and `panda/services.py`'s reply generation, never `routes.py`, the frontend, or any other feature's code. Keeping the whole subsystem in one folder makes that boundary visible in the file tree, not just in code review discipline. This is a deliberate, isolated exception to this codebase's usual flat `routes/`/`database/` convention — it does not signal any App-wide reorganization to Django-style per-feature packages.

**Why insights are computed, not stored:** the three example insights (revenue lower, memberships expiring, seats underutilized) are all simple threshold checks over data this app already computes elsewhere for other pages — persisting a snapshot would just be a second, staler copy of numbers Dashboard/BI/Notifications already own live. No dismiss/read-state was requested for this phase; adding one later means a new `panda_notifications` table (same manual-Supabase-creation pattern as `panda_conversations`), not a change to how the checks themselves work.

**Why chat storage is a new Supabase table applied manually, not auto-created:** this app has no DDL path at all (ADR-14/38) — `panda_conversations`/`panda_messages` follow the exact same shape as `ai_center_settings` (ADR-40): defined in `database/supabase_migration.sql`, and every read/write in `database/panda_queries.py` raises `ChatStorageUnavailable` (caught by `panda/routes.py` as an HTTP 503) until a project owner runs the `CREATE TABLE` statements by hand. Unlike `ai_center_settings`, a missing table here doesn't just fall back to a default — chat history genuinely doesn't work — but the floating button, insights, and suggested questions are unaffected, since none of them read these tables.

**Why the app-wide security boundary (read-only, no SQL/exec/filesystem/secret access) is enforced by construction, not a runtime filter:** Phase 1 has no tool-calling layer at all — every function Panda's routes call is either a read from an existing query module or a write to Panda's own chat-log tables, so there is no code path capable of violating those rules yet. `panda/prompts.py`'s `READ_ONLY_RULES` records the constraints a future LLM/tool-calling layer must be given verbatim once one exists; it is documentation for that future layer, not an enforcement mechanism today.

**Consequence:** No forecasting exists yet (`panda/forecasting.py` is unreachable from any route) — see the matching `TD` row in [11_FUTURE_WORK.md](11_FUTURE_WORK.md). Every chat reply is identical regardless of what's asked; a future contributor should not mistake `generate_placeholder_reply()` for even a rule-based heuristic — it deliberately does not try to pattern-match the question.

**How to apply:** a new insight check belongs in `panda/notifications.py` as one more `_check_*` function reusing an existing read-only query module wherever possible (see `insights.py`'s docstring on why). Wiring in a real model means replacing `generate_placeholder_reply()`'s body and giving it `SYSTEM_PERSONA`/`READ_ONLY_RULES` from `prompts.py` — `panda/routes.py`, `database/panda_queries.py`, and the frontend widget should not need to change at all for that swap.

### ADR-44: Global navbar search — multi-entity JSON autocomplete extending ADR-41's pattern

**Decision:** The navbar's search box (`templates/layouts/navbar.html`), previously a decorative `<input>` with no `name`/`id`/JS/backend at all, is now a live, grouped-by-type autocomplete searching four entities at once — Students, Payments, Enquiries, Cashbook — behind **one** JSON endpoint, `GET /search/suggestions` (`routes/search.py`, new `search_bp`), backed by one new module, `database/search_queries.py`. `global_search(admin_id, query)` runs `search_students()`/`search_payments()`/`search_enquiries()`/`search_cashbook()` and returns `{"students": [...], "payments": [...], "enquiries": [...], "cashbook": [...]}`, each capped at `RESULTS_PER_TYPE=5`. A new `static/js/navbar_search.js` — a structural extension of `static/js/ai_center_search.js`'s debounce/staleness-guard/keyboard-nav/click-outside pattern — renders the four groups under headers in one dropdown and flattens them for keyboard navigation. Exactly like ADR-41, this is explicit-selection-only: typing alone never navigates anywhere, only clicking or arrow-key-then-Enter on a result does.

**Why one endpoint, not four:** every one of the four per-module reads is already a single "fetch this admin's rows" round trip with no PostgREST `ilike`/JOIN to offload filtering to (the same constraint every cross-table read in this codebase already works around) — the cost is dominated by Supabase round trips, not Python-side filtering of a few thousand rows. Four separate `fetch()` calls from the browser would mean four independent HTTP round trips to Flask for the exact same total DB work, plus four separate debounce timers and four independent race conditions to guard against per keystroke, instead of the one `latestRequestId` staleness guard `ai_center_search.js` already established. Per-admin data volume keeps this cheap in practice: every read here is `admin_id`-scoped first, so "fetch this admin's four tables on every keystroke" is the same shape `database/ai_center_queries.py`'s `search_students()` already does for one table today (proven fine at this app's scale), not a new order of magnitude for four.

**Why `database/search_queries.py` is a new file, not four extensions to existing query modules:** Students/Payments/Cashbook each already have zero, one, or a differently-shaped search function living in another module (`database.ai_center_queries.search_students()`'s `plan_name`-enriched version, `get_payments_for_admin()`, `get_cashbook_ledger()`'s own `search=` param) — bolting a *second*, differently-capped, differently-shaped search function into those same files would sit oddly next to a function with a similar name solving an adjacent problem for a different page. `search_students()` here deliberately does **not** call `database.ai_center_queries.search_students()` — it calls `get_admin_students()` directly and skips the `plan_name` enrichment (an extra `get_memberships_for_admin()` round trip AI Center's dropdown needs but this one doesn't), so global search's shape stays uncoupled from AI Center's enrichment contract.

**Why Cashbook results are shown but not clickable:** `routes/cashbook.py` has no single-entry `GET` view route — confirmed by reading the file: `edit/<int:entry_id>` is `POST`-only, no GET branch, no view template. Linking a Cashbook result to `/cashbook/edit/<id>` would 405; linking to `/cashbook/` with no anchor would look like a working "view" link while actually just landing on the general ledger. Rendering the row (so an admin can at least confirm a matching entry exists) but making it inert was the only option that didn't invent new UI surface for a UI-only search feature — building a real single-entry Cashbook view page is a separate feature, tracked as **TD-56**, not folded into this one.

**How to apply:** a fifth entity type added to global search needs its own `search_*()` function in `search_queries.py` (reusing an existing admin-scoped fetcher if one exists, following `search_enquiries()`'s direct-`.eq("admin_id", ...)` shape if not), a branch in `routes/search.py`'s `suggestions()` reshaping its rows into the JSON fields the frontend needs, a `GROUPS` entry in `navbar_search.js` (with `clickable: false` if no single-record view page exists for it yet, same as Cashbook), and a `renderRow()`/`selectItem()` branch for its display/navigation shape.

### ADR-45: Total Fee is server-computed from `membership_settings` for standard plans, client-editable only for Custom; Pending is always derived

**Decision:** A membership's `total_fee` is no longer trusted from client input for a standard plan (Monthly/Quarterly/Half-Yearly/Yearly). `routes/membership.py`'s `create()`/`renew()` now derive it authoritatively, server-side, from that admin's `membership_settings` row via `database/membership_queries.py`'s `get_plan_pricing()`/`get_admission_fee()`: `total_fee = plan_pricing[plan]["fee"]` for `renew()`, and `plan_pricing[plan]["fee"] + admission_fee` for `create()` (admission fee is a one-time new-admission charge, deliberately never applied on renewal). Only the `"Custom"` plan — which has no admin-configured price to derive from — accepts a manually-typed `total_fee` from the form. `pending_amount` is always computed as `total_fee - paid_amount` server-side; there is no `due_amount` form field anymore, and a new guard rejects `paid_amount > total_fee`. The templates surface this as three distinct concepts — Plan Fee, Admission Fee (Create only, shown when nonzero), and Total Payable — rather than one opaque number, with Paid and Pending kept visually and functionally separate from Total Payable.

**Why:** the previous shape (`total_fee = paid_amount + due_amount`, both raw form fields, no "Total Fee" field on the form at all) let the admission fee get silently folded into the stored total: `templates/memberships/create.html`'s plan-select JS pre-filled the *Paid* input with `plan_fee + admission_fee`, and an operator correcting Paid down to the amount actually collected (typing the perceived remainder into Due) produced a `total_fee` that no longer matched the plan price the admin configured in Settings — with nothing anywhere to catch the drift, since there was no independent source of truth for what the total *should* be. Deriving `total_fee` from `membership_settings` at the point of write closes that gap the same way ADR-20/21/29 established Supabase as the single source of truth for other membership fields — one authoritative computation, not a value trusted from whatever the UI happened to compute client-side.

**Why Custom is the one exception:** there is no admin-configured price for an arbitrary/negotiated arrangement, so it's the only case where a manually-entered `total_fee` is legitimate — and even then, `paid_amount > total_fee` is still enforced, and `pending_amount` is still always derived, never typed.

**How to apply:** a future field that should factor into Total Payable (e.g. a discount, a proration) belongs in this same server-side derivation in `create()`/`renew()`, not as a new client-editable form field — keep the pattern of "the server computes the authoritative total for every plan except Custom" rather than reintroducing a total assembled from independently-typed pieces.

### ADR-46: Discount is a staff-entered, per-transaction line item on Create only, with a hard failure (not ADR-38's silent strip) if its columns don't exist yet

**Decision:** Admins can give a flat-₹ discount when creating a new membership (`templates/memberships/create.html`, `routes/membership.py`'s `create()` only — not `renew()`). Discount is its own transparent line item, matching ADR-45's principle that Plan Fee/Admission Fee/Discount must never be silently folded into one opaque number: **Total Payable = Plan Fee + Admission Fee**, **Discount** is entered separately (optionally with a free-text reason, not required), **Final Payable = Total Payable − Discount** (this is what's actually stored as `total_fee`), **Paid** = amount actually received, **Pending = Final Payable − Paid**. `discount_amount`/`discount_reason` are new nullable columns on `memberships`, always written alongside `total_fee` so a discounted membership's history still shows the undiscounted price and why it was reduced — never just a smaller `total_fee` with no trace, which is exactly the shape of bug ADR-45 fixed.

**Validation:** `discount_amount` must be `>= 0` and strictly less than the pre-discount total (Total Payable, or the Custom plan's manually-entered total) — a discount that equals or exceeds the total is rejected, keeping the existing `total_fee > 0` invariant intact after the discount is applied. `paid_amount > total_fee` (i.e. > Final Payable) is still rejected, same as ADR-45.

**Why Create only, not Renew:** matches the user's explicit scope — a discount at first admission is the common case, and Renew's Total Payable already deliberately excludes Admission Fee (ADR-45) for the same "only applies to new admissions" reasoning.

**Why this does NOT follow ADR-38's silent-strip-and-retry precedent for missing columns:** ADR-38's `library_settings.morning_capacity`/etc. degrade silently (retry insert without the new columns) because losing a seating-capacity number is a cosmetic/analytics gap, not a financial one. A discount is money: `total_fee` is computed *net of the discount* before the insert is even attempted, so silently stripping `discount_amount`/`discount_reason` and retrying would still charge the student the discounted price while permanently erasing the only record of why — worse than the columns not existing at all. Per explicit direction, `database/membership_queries.py`'s `insert_membership()` instead only degrades silently when there's nothing to lose (`discount_amount == 0` and no `discount_reason` — the common case for any admin not using the discount box), and otherwise raises `DiscountColumnsUnavailable`, caught by `create()` to flash a clear, specific message and create nothing at all. This is a deliberate departure from ADR-38's pattern, driven by the nature of the data (financial vs. cosmetic), not a rejection of that pattern generally.

**Schema:** same "no direct-Postgres/DDL path" constraint as ADR-14/ADR-38 — `discount_amount DOUBLE PRECISION DEFAULT 0`/`discount_reason TEXT` are merged into `memberships`' `CREATE TABLE` in `database/supabase_migration.sql` for fresh installs, with the exact `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...` documented in a comment block for an admin to run by hand on an existing Supabase project.

**How to apply:** a future per-transaction financial adjustment (e.g. a late fee applied at renewal) should follow this same shape — its own column(s), its own line item in the UI never folded into `total_fee` silently, and a hard failure (not a silent strip) if its columns aren't live yet on a given project.
