# File Reference

Per-file cards for every important source file: **Purpose**, **Responsibilities**, **Functions/Classes**, **Files it depends on**, **Files that depend on it**, **Future modification notes**.

"Depends on" / "depended on by" are drawn from a grep of every `import`/`from` statement in the project (verified 2026-07-20, see [DIAGRAMS.md](DIAGRAMS.md) for the same data as a graph) — cross-blueprint `url_for` couplings (runtime-only, not imports) are noted separately where relevant. If you add or remove an import, update the two matching cards (both sides of the edge) in the same change.

## Root

### `app.py`
- **Purpose:** Flask application factory and process entry point.
- **Responsibilities:** Create the Flask app, set `SECRET_KEY`, register all 15 blueprints, register the `branding_src` Jinja global (**added 2026-08-28, ADR-57** — `utils/branding.py`; templates resolve a stored branding-image reference through it), define the one global context processor that feeds both the navbar notification bell and the navbar's notification-display preferences on every page. `_configure_logging(app)` attaches a rotating local-file handler (**best-effort as of 2026-08-28** — wrapped in `try/except OSError` so a read-only filesystem like Vercel's doesn't 500 the app at cold start) plus a `logging.StreamHandler` (as of 2026-08-25) — see that function's own note below. **Also as of 2026-08-25:** `app.wsgi_app` is wrapped in `werkzeug.middleware.proxy_fix.ProxyFix(x_for=1, x_proto=1)` before any request is served, so `request.is_secure`/`request.remote_addr` reflect the real client behind exactly one trusted reverse-proxy hop (Render, or any similar PaaS host that terminates TLS at an edge proxy) instead of the proxy's own internal connection.
- **Functions/Classes:** `create_app()`; module-level `app = create_app()`; module constant `DEFAULT_NAV_NOTIFICATION_PREFS` (all four flags `True`); no classes. Inline `inject_notification_summary()` registered via `@app.context_processor` — now also computes `nav_notification_prefs` (a dict of `dash_show_badge_count`/`dash_show_expiry_today`/`dash_show_expiry_tomorrow`/`dash_show_overdue`, read via `get_notification_settings_cached(admin_id)` and defaulting to `DEFAULT_NAV_NOTIFICATION_PREFS` when there's no session or no `library_settings` row yet) alongside the existing `nav_notifications`. **Added 2026-08-21 (one-deployment-per-library provisioning, ADR-53):** `_log_connected_supabase_project(app)` — logs one line at startup (skipped when `app.testing`) showing the last ~24 characters of `SUPABASE_URL`, so an operator can visually confirm this deployment is connected to the intended library's own Supabase project (never logs the secret key). Called from `create_app()` right after `_configure_logging(app)`. **Changed 2026-08-25 (pre-Render-deployment readiness audit):** `_configure_logging(app)` now also attaches a `logging.StreamHandler` (stdout) alongside the `RotatingFileHandler` — verified live that Python's logging module has no automatic console fallback once any handler is attached to a logger, so without this, every `app.logger` call (including the `Connected Supabase project: ...` line above, which `docs/DEPLOYMENT.md`/`docs/PROVISIONING.md` require an operator to read before declaring go-live) would be written only to a local file, invisible on a host like Render that only captures stdout/stderr as "Logs" and has no readable/persistent filesystem for its web service by default. **Changed 2026-08-28 (ADR-56, Vercel deploy):** the `instance/` mkdir + `RotatingFileHandler` setup is now inside `try/except OSError` — on a read-only-filesystem host that raised while `create_app()` was still building, 500ing every cold start; it now silently falls back to the stdout `StreamHandler` alone, which is all a serverless host needs anyway.
- **Depends on:** `routes.auth`, `routes.dashboard`, `routes.enquiries`, `routes.student`, `routes.membership`, `routes.payment`, `routes.cashbook`, `routes.report`, `routes.setting`, `routes.notification` (also imports `get_notification_summary`), `routes.membership_analytics`, `routes.membership_distribution`, `routes.business_intelligence`, `routes.ai_center`, `panda.routes` (added 2026-07-27, ADR-43 — the only cross-package import `app.py` makes into `panda/`), `database.notification_settings_queries.get_notification_settings_cached`, `utils.branding.branding_src` (added 2026-08-28), `werkzeug.middleware.proxy_fix.ProxyFix` (added 2026-08-25 — already a transitive dependency via Flask/Werkzeug itself, no new package).
- **Depended on by:** nothing imports `app.py` — it's the process entry point (`python app.py`); `templates/components/notification_dropdown.html` consumes both `nav_notifications` and `nav_notification_prefs` from this context processor.
- **Future modification notes:** This is the right place to add a centralized auth-check decorator/`before_request` hook (currently duplicated in nearly every route — see [Known Technical Debt](11_FUTURE_WORK.md)). `config.py` is wired in (`DevelopmentConfig`/`ProductionConfig`, selected by `APP_ENV`) and 404/405/413/500 error handlers already exist — the stale note that used to be here about both is removed as of the 2026-08-25 deployment-readiness pass. If you add more dashboard-display toggles to Notification Settings that should also affect the navbar, extend `nav_notification_prefs`/`DEFAULT_NAV_NOTIFICATION_PREFS` here rather than reading settings again from inside the template. Uses `get_notification_settings_cached()` (not the raw `get_notification_settings()`) specifically because `routes/dashboard.py` also needs the same admin's row on the same `/dashboard` request — the `_cached` wrapper memoizes on `flask.g` so that's one query, not two (fixed 2026-07-21, see [CHANGELOG.md](CHANGELOG.md)). If you add a third call site within a request, it gets the dedup for free; don't call the raw `get_notification_settings()` directly from route/context-processor code.

### `config.py`
- **Purpose:** Centralized environment configuration, selected by `APP_ENV` in `app.py`'s `create_app()` via `app.config.from_object(...)`. Also the app's single `load_dotenv()` call site — imported before any other module reads `os.environ`, so `.env` values are available process-wide from then on.
- **Responsibilities:** Load `.env` into the process environment; supply `SECRET_KEY`, `SESSION_COOKIE_SECURE`, `PERMANENT_SESSION_LIFETIME`, `MAX_CONTENT_LENGTH`, `CSRF_ENABLED`, `ENABLE_SELF_SERVICE_PASSWORD_RESET`, and `LOG_LEVEL` per environment.
- **Functions/Classes:** `Config` (base), `DevelopmentConfig(Config)`, `ProductionConfig(Config)`.
- **Depends on:** `os`, `python-dotenv` (`load_dotenv()`), `.env`.
- **Depended on by:** `app.py` (`from config import DevelopmentConfig, ProductionConfig`).
- **Future modification notes:** New env-driven settings belong here, as a `Config`/`DevelopmentConfig`/`ProductionConfig` attribute, not as an ad hoc `os.environ.get(...)` scattered in a route.

### `wsgi.py`
- **Purpose:** Production WSGI entry point. A one-line module that re-exports `create_app` so a WSGI server can build the app via the factory.
- **Responsibilities:** `from app import create_app` — nothing else. Used as `waitress-serve --call wsgi:create_app`.
- **Depends on:** `app.create_app`.
- **Depended on by:** the production start command only (not imported by application code). `render.yaml`'s `startCommand` names it.
- **Future modification notes:** Keep this free of side effects — it must stay importable without starting a server.

### `requirements.txt`
- **Purpose:** Pinned production dependency set (exact `==` versions), installed by `render.yaml`'s `buildCommand` and in local venvs.
- **Responsibilities:** Lists Flask/Werkzeug/Jinja, `supabase` + its transitive stack, `waitress` (prod WSGI server), `python-dotenv`, `cryptography`/`PyJWT`, and `pytest`. **As of 2026-08-28 (ADR-56):** `matplotlib`, `numpy`, `contourpy`, `cycler`, `fonttools`, `kiwisolver`, `pillow`, `pyparsing` were removed — charts render client-side with Chart.js now, and nothing else imported them.
- **Future modification notes:** **Must be saved as UTF-8** — it was UTF-16 LE until 2026-08-27, which parses fine on Windows but makes `pip install -r requirements.txt` fail on Linux (Render's build image). No dependency imposes a minimum Python version any more (`contourpy` left with matplotlib); [.python-version](../.python-version) is `3.12` (a bare `major.minor`, not a patch pin — 2026-08-28: Vercel's `@vercel/python` builder has no `3.11.9` interpreter and `uv sync --locked` fails hard on an exact patch it can't find; `3.12` resolves on both Vercel and Render).

### `render.yaml`
- **Purpose:** Render Blueprint (Infrastructure-as-Code) describing the one web service that runs this app. Added 2026-08-27.
- **Responsibilities:** Declares `runtime: python`, `buildCommand: pip install -r requirements.txt`, `startCommand: waitress-serve --host=0.0.0.0 --port=$PORT --call wsgi:create_app`, `healthCheckPath: /`, and the env vars — `APP_ENV=production`, `SESSION_COOKIE_SECURE=true`, `LOG_LEVEL=INFO`, `SECRET_KEY` (`generateValue: true`), and `SUPABASE_URL`/`SUPABASE_SECRET_KEY` (`sync: false`, so Render prompts and never stores them in the repo). Python version is not set here — it comes from [.python-version](../.python-version).
- **Depends on:** `requirements.txt`, `wsgi.py`, `.python-version`.
- **Depended on by:** Render only (read when you create a Blueprint service or on each push if `autoDeploy` is on).
- **Future modification notes:** This is one deployment for one library (ADR-53) — do not turn it into a multi-service file for multiple libraries. If you add a required env var to `config.py` or `database/supabase_client.py`, add it here too (as `sync: false` if it is a secret). As of 2026-08-28 nothing writes to local disk at runtime (backup streams from memory — ADR-56; branding images go to Supabase Storage — ADR-57), so **TD-73 is resolved** and no Render Disk is needed. `SUPABASE_STORAGE_BUCKET` is optional (defaults to `library-branding`, bucket auto-created) — add it here only if a deployment overrides the name.

## `database/`

### Removed files (SQLite infrastructure, deleted 2026-07-25, ADR-32, Phase 11)

The following files existed solely to create, connect to, or migrate the now-decommissioned SQLite database, and were deleted outright once the incremental table-by-table migration (ADR-16 through ADR-31) reached its last table: `database/db.py` (the `get_connection()` connection factory every route used to import), `database/schema.sql` (the SQLite DDL), `database/seed.py` and `database/init_db.py` (one-time schema-creation scripts), `database/migrate_to_supabase.py` (the one-time SQLite → Supabase bulk data copy, ADR-15 — its job is done and can't be safely re-run against a SQLite source that no longer exists), and all fourteen `database/migrate_*.py` incremental-schema scripts (`migrate.py`, `migrate_audit_log.py`, `migrate_cashbook_ledger.py`, `migrate_library_settings.py`, `migrate_settings_receipt_footer.py`, `migrate_membership_setting.py`, `migrate_receipt_settings.py`, `migrate_notification_settings.py`, `migrate_backup_log.py`, `migrate_security_settings.py`, `migrate_transactions.py`, `migrate_backfill_mirror_parity.py`, `migrate_backfill_settings_to_supabase.py`). See [DECISIONS.md](DECISIONS.md)'s ADR-32 for the full rationale and [04_DATABASE_SCHEMA.md](04_DATABASE_SCHEMA.md) for what each table looked like under SQLite, kept there as historical reference. The on-disk `database/library.db` data file itself is left in place, untouched (already `.gitignore`d, receives no further writes).

### `database/supabase_migration.sql`
- **Purpose:** Full DDL — the single, sole source of truth for the schema of every table in the app. Originally a hand-translated PostgreSQL equivalent of the now-deleted `schema.sql` (ADR-14); as of 2026-07-25 (ADR-32) it has no SQLite counterpart to stay in sync with anymore.
- **Responsibilities:** Define all 14 tables (`admins`, `settings`, `enquiries`, `students`, `memberships`, `payments`, `cashbook`, `expenses`, `transactions`, `audit_log`, `library_settings`, `membership_settings`, `backup_log`, `security_settings`) in PostgreSQL syntax, wrapped in `BEGIN;`/`COMMIT;`.
- **Functions/Classes:** N/A (pure SQL).
- **Depends on:** nothing (plain SQL file).
- **Depended on by:** nothing at the application level — applied by hand, once, in the Supabase SQL Editor; every `database/*_queries.py` module and route implicitly depends on the schema it defines.
- **Future modification notes:** See ADR-14 (original creation) and ADR-32 (became the sole schema source, TD-34 `Resolved`). Any future schema change is made here directly — there is no second file to keep in sync, and no migrations framework/runner (hand-apply any `ALTER TABLE` against Supabase directly, same as this file's own creation). **As of 2026-07-26 (Occupancy Analytics, Phase 3, ADR-38):** `library_settings` gained `morning_capacity`/`afternoon_capacity`/`evening_capacity` (`INTEGER DEFAULT 50` each) — merged into its `CREATE TABLE` per this file's own convention, plus a comment block with the exact `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...` an already-provisioned Supabase project's owner must run by hand in the SQL Editor (verified live: this app cannot execute DDL itself — no `exec_sql`/`run_sql`/DDL RPC exists, see ADR-38). `database/settings_queries.py` tolerates the columns not existing yet (see its own card). **As of 2026-08-21 (TD-30/TD-43 fix, ADR-53):** `payments` gained `idempotency_key TEXT UNIQUE` and `cashbook_synced BOOLEAN DEFAULT TRUE`; `memberships` gained `idempotency_key TEXT UNIQUE` — same "merged into `CREATE TABLE` plus an inline manual-`ALTER` comment block" convention as the capacity columns above. `database/membership_queries.py`/`database/payment_queries.py` tolerate all three columns not existing yet (silent degrade, not a hard failure — see TD-66).

### `database/supabase_client.py`
- **Purpose:** The single shared Supabase (PostgREST) client factory — as of 2026-07-25 (ADR-32), the app's **only** database access layer.
- **Responsibilities:** Read `SUPABASE_URL`/`SUPABASE_SECRET_KEY` from the environment (via `python-dotenv`'s `load_dotenv()`), raise `RuntimeError` if either is missing, and construct one `supabase.Client`, cached process-wide with `functools.lru_cache(maxsize=1)` since it's a plain HTTP client wrapper, not a stateful DB connection needing per-request open/close.
- **Functions/Classes:** `get_supabase_client()`.
- **Depends on:** `python-dotenv`, `supabase` (already in `requirements.txt`), `.env` (`SUPABASE_URL`/`SUPABASE_SECRET_KEY`).
- **Depended on by:** every route and `database/*_queries.py` module in the app — see [09_DEPENDENCY_MAP.md](09_DEPENDENCY_MAP.md) for the full per-file list.
- **Future modification notes:** This is the app's only database client — there is no SQLite equivalent left anywhere to keep in parity with. Any new table or query goes through this client, directly inline in a route or via a `database/*_queries.py` module, following whichever of the two established styles best fits (see [02_ARCHITECTURE.md](02_ARCHITECTURE.md)).

### `database/branding_storage.py`
- **Purpose:** Supabase Storage access layer for the three Library Profile branding images (logo/stamp/signature) — added 2026-08-28, ADR-57. Sibling to `supabase_client.py` (that is the Supabase-DB layer, this is the Supabase-Storage layer).
- **Responsibilities:** Upload a branding image to the `library-branding` bucket and return its full public URL; delete one (best-effort); create the bucket public on first use. The bucket name is `os.environ.get("SUPABASE_STORAGE_BUCKET", "library-branding")`.
- **Functions/Classes:** `BUCKET` (module constant), `_ensure_bucket()` (`@lru_cache(maxsize=1)` — `get_bucket()` then `create_bucket(..., options={"public": True, "file_size_limit": 5 MB, "allowed_mime_types": [png/jpeg/webp]})`, swallows a duplicate-bucket race; a raised exception is not cached so a transient failure retries), `upload_branding_image(object_path, data, content_type) -> public_url` (`_ensure_bucket()` → `from_(BUCKET).upload(..., {"content-type", "cache-control": "3600", "upsert": "true"})` → `get_public_url()`), `_object_path_from(url_or_path)` (the in-bucket path for a stored value, or `None` if it's a legacy relative path), `delete_branding_image(url_or_path)` (best-effort, never raises — `remove([path])` for a Storage URL, `os.remove` under `current_app.static_folder` for a legacy path).
- **Depends on:** `database.supabase_client.get_supabase_client` (uses `.storage`), `functools.lru_cache`, `os`; `flask.current_app` imported lazily inside `delete_branding_image()` only.
- **Depended on by:** `routes/setting.py` (`_save_upload`, `remove_library_logo`).
- **Future modification notes:** `create_bucket` works from Python with the service-role key even though raw SQL DDL does not (ADR-14 is about SQL, not the Storage REST API) — this is why no manual PROVISIONING step is needed. A deleted object can still be served from the Storage CDN until its `cache-control` max-age (3600 s) expires; that is harmless because the DB row is cleared immediately and the template's `{% if …_path %}` guard hides it. To switch to a private bucket later, change `_ensure_bucket()`'s `public` flag and have `upload_branding_image()` (or a new read helper) return a signed URL, and update `utils/branding.py`'s `branding_src()` to re-sign on render — no template or `library_settings` column change needed.

### `database/ai_center_queries.py`
- **Purpose:** Data access + rule-based retention-risk scoring for the AI Center — Phase 1 (Student Risk Analysis) as of 2026-07-27, ADR-39.
- **Responsibilities:** Compute a 0-100 retention score for one student from three signals already present in the schema (unpaid balance age, renewal/expiry timing, membership plan length), each weighted and blended into a single score, plus the ranked list of human-readable reasons (and their matched recommended action) that produced it. Not a trained model — there is no labeled churn outcome or attendance log anywhere in the schema to train one against (see ADR-39, TD-49). **As of 2026-07-27 (ADR-40):** has no hardcoded weight/threshold constants of its own — `compute_student_risk()` reads them from `database/ai_center_settings_queries.py` per admin.
- **Functions/Classes:** `REASON_THRESHOLD` (module constant — an internal reason-visibility sensitivity, not one of the admin-configurable weights/thresholds), `get_risk_level(score, high_risk_max, low_risk_min)` (as of ADR-40, thresholds are parameters, not module constants), `get_student_detail(admin_id, student_id)` (the tenant-scoping check every other function here relies on), `search_students(admin_id, query, limit=15)` — as of ADR-41, the JSON autocomplete's data source: matches on name/mobile (case-insensitive, partial) as before, but each match is now also enriched with `plan_name` (that student's latest membership's plan, or `None`), fetched via one extra `database.membership_queries.get_memberships_for_admin()` call rather than a per-match lookup; `_memberships_for_student(student_id)`/`_payments_for_student(student_id)` (student_id-only, same trust-boundary pattern as `database.membership_queries.get_active_membership()`), `_payment_delay_signal`/`_renewal_signal`/`_duration_signal` (each returns `(risk_fraction, reason, action)`), `_score_student_risk(student, settings, memberships, payments)` (added 2026-08-24 — the actual scoring math, factored out of `compute_student_risk()` so `compute_student_risk_batch()` below can reuse it against pre-batched data instead of duplicating the calculation), `compute_student_risk(admin_id, student_id)` — the public single-student entry point; as of ADR-40, its first step is `get_effective_settings(admin_id)`, whose weights/thresholds are threaded through every signal call and `get_risk_level()`; now a thin wrapper: fetch student/settings/memberships/payments, then `_score_student_risk()`. `compute_student_risk_batch(admin_id, students=None)` (added 2026-08-24, TD-60/latency fix) — same scoring for every student in one pass: settings fetched once (not per student), `database.membership_queries.get_memberships_for_admin()`/`database.payment_queries.get_payments_for_admin()` (both already-existing admin-wide batch reads) fetched once each and grouped by `student_id` in Python, instead of one Supabase call per student per table. Returns `{student_id: <same shape compute_student_risk() returns>}`.
- **Depends on:** `database.membership_queries` (`get_admin_students`, `get_days_left`, and as of ADR-41 also `get_memberships_for_admin`), `database.supabase_client.get_supabase_client`, `postgrest.exceptions.APIError`. **As of 2026-07-27 (ADR-40):** also `database.ai_center_settings_queries.get_effective_settings`. **As of 2026-08-24:** also `database.payment_queries.get_payments_for_admin` (for `compute_student_risk_batch()`).
- **Depended on by:** `routes/ai_center.py` (`compute_student_risk`, single-student page). **As of 2026-08-24:** `panda/insights.py`'s `get_top_risk_students()` calls `compute_student_risk_batch()` instead of looping `compute_student_risk()` — see that file's card and TD-60 in [11_FUTURE_WORK.md](11_FUTURE_WORK.md).
- **Future modification notes:** `purpose` (free text) is deliberately not scored — no verified correlation between purpose category and churn exists in this data yet (see ADR-39 and TD-52); don't add a purpose-based weight without first checking whether real outcome data supports it. `_payment_delay_signal()`'s "delay" is measured from the last actual payment on the membership, not a true due date (no due-date column exists — see TD-51). If Phase 2 (Prediction Dashboard aggregate view) is built, prefer `compute_student_risk_batch()` over looping `compute_student_risk()` — the batched version is now the source of truth for "score this admin's whole roster cheaply," and it already picks up each admin's own configured weights for free (one `get_effective_settings()` call, same as the single-student path). Don't reintroduce a hardcoded `DEFAULT_WEIGHTS`/`HIGH_RISK_MAX`/`LOW_RISK_MIN` here — `database/ai_center_settings_queries.py`'s `DEFAULTS` is the one place those fallback values live now (ADR-40). **As of 2026-07-27 (ADR-41):** `search_students()` is now `routes/ai_center.py`'s `student_suggestions()` JSON endpoint's only data source — if a new field needs to show up in the autocomplete dropdown, add it to the dict this function enriches each match with, not to a second query in the route. **As of 2026-08-24:** any new signal added to `_score_student_risk()` automatically applies to both `compute_student_risk()` and `compute_student_risk_batch()` — don't add signal logic directly inside either public function, it belongs in the shared core or in a new `_*_signal()` function called from it.

### `database/ai_center_settings_queries.py`
- **Purpose:** Get/save the per-admin weights and risk-level thresholds `database/ai_center_queries.py`'s scoring engine reads — AI Center Settings, added 2026-07-27, ADR-40 (Phase 3, pulled forward ahead of Phase 2).
- **Responsibilities:** One row per `admin_id`, same isolation pattern as `membership_settings`/`security_settings`. Always returns a usable dict even when nothing has been saved yet (or the table doesn't exist yet on this Supabase project) via `DEFAULTS`-overlay, so callers never special-case "no settings."
- **Functions/Classes:** `DEFAULTS` (module constant — `weight_payment_delay: 45, weight_renewal_history: 35, weight_membership_duration: 20, high_risk_max: 40, low_risk_min: 70`, the same values ADR-39 originally hardcoded), `get_ai_center_settings(admin_id)` (this admin's raw saved row, or `None`), `get_effective_settings(admin_id)` (`DEFAULTS` overlaid with whatever's actually saved — the one function every consumer should call), `save_ai_center_settings(admin_id, data)` (upsert via `.upsert(..., on_conflict="admin_id")`, same pattern as `database/membership_settings_queries.py`'s `save_membership_settings()`; validation is the caller's responsibility, not this function's).
- **Depends on:** `database.supabase_client.get_supabase_client`, `postgrest.exceptions.APIError`, `database.settings_queries._now_iso`.
- **Depended on by:** `database/ai_center_queries.py` (`get_effective_settings`), `routes/ai_center.py` (`get_effective_settings`, `save_ai_center_settings`).
- **Future modification notes:** `ai_center_settings` is a **brand-new table** this app cannot create on a live Supabase project itself (no DDL path — ADR-14/38/40) — see the `CREATE TABLE`'s comment in `database/supabase_migration.sql` and **TD-53**. Until it's applied by hand, `get_ai_center_settings()` returns `None` for every admin (verified live: PostgREST raises `PGRST205` "table not found," caught the same as any other read failure), so `get_effective_settings()` always falls back to `DEFAULTS` and scoring is unaffected; `save_ai_center_settings()` has no such fallback and raises, which `routes/ai_center.py`'s `settings()` catches to flash a clear message. Don't "fix" that by making `save_ai_center_settings()` swallow the error — a save that silently didn't persist would be worse than one that visibly failed.

### `database/panda_queries.py`

### `database/id_sequence.py`

- **Future modification notes:** Password change itself is handled inline in `routes/setting.py`'s `security_settings()` against the `admins` table, not through this module — this module only covers `session_timeout_minutes`/`remember_me_enabled`/`login_notifications_enabled`, none of which are currently enforced anywhere (TD-26). Returning `DEFAULTS` instead of `None` means callers don't need a "does a row exist" branch the way `get_notification_settings`/`get_receipt_settings` callers do — keep that contract if you add more security preferences.

### `database/migrate_normalize_input_data.py`
- **Purpose:** One-time, hand-run migration that applies `utils/normalization.py`'s rules to every row already in Supabase — added 2026-07-26 (Input Normalization) so pre-existing data matches what every route now writes going forward. Extended the same day (Normalization Audit) to also cover `admins`/`cashbook` once those write paths were found to have been bypassing normalization, and rewritten to fix two bugs its first two runs had (see "Fixed" below).
- **Responsibilities:** For `admins`, `enquiries`, `students`, `memberships`, `payments`, `library_settings`, `cashbook`, re-normalize each in-scope column (see `TABLE_RULES`) and write back only the rows whose normalized value actually differs from what's stored.
- **Functions/Classes:** `TABLE_RULES` (module constant — `{table: (primary_key_column, {column: normalizer})}`), `_fresh_client()` (a new, non-cached Supabase client — see below), `_with_retry(call)`, `_normalize_table(table, pk, field_rules)`, `run()`. Module constants `_PAGE_SIZE` (1000), `_MAX_ATTEMPTS` (4), `_REFRESH_EVERY` (300).
- **Depends on:** `database.supabase_client.get_supabase_client`, `utils.normalization` (all five normalizer functions), `postgrest.exceptions.APIError`, `time` (stdlib, retry backoff).
- **Depended on by:** nothing at the application level — run by hand, once (or re-run any time; fully idempotent), via `python -m database.migrate_normalize_input_data` (same "no migrations framework/runner, hand-apply" pattern the now-deleted `database/migrate_*.py` scripts used, ADR-32).
- **Fixed 2026-07-26 (Normalization Audit, same day):** the first two runs of this script each called `supabase.table(t).select("*").execute()` with no `.range()` — PostgREST silently caps an unranged select at its configured max-rows (1000 on this project), so both runs only ever scanned and normalized each table's *first* 1000 rows and silently ignored the rest, even though every table here has several thousand rows (`admins` alone reached ~11,000, mostly from repeated pytest runs each creating throwaway test admins). `_normalize_table()` now paginates via `.order(pk).range(offset, offset + _PAGE_SIZE - 1)` in a loop until a short page is returned. **Also fixed the same day:** an interim rewrite that batched each page's changed rows into one bulk `.upsert()` call (to cut network round trips versus one `.update()` per changed row) was tried and reverted after it corrupted a live test row — Postgres validates every `NOT NULL` column against an upsert's *tentative INSERT row* before `ON CONFLICT DO UPDATE` ever resolves, so any column not present in a given payload (i.e. any column of the table not listed in that table's `field_rules`, such as `cashbook.type`/`amount`) fails a not-null constraint even though the row already exists and only an `UPDATE` was ever intended (reproduced live: `null value in column "type" ... violates not-null constraint`; the failed statement rolled back atomically, no data was lost). Reverted to one targeted `.update(changes).eq(pk, ...)` per changed row (which has no such restriction, since it never constructs a candidate INSERT row), and added `_with_retry()` (a few attempts with backoff) plus `_fresh_client()` (periodically re-creates the Supabase client every `_REFRESH_EVERY` written rows) after the *original* per-row-update shape had its HTTP/2 connection terminated by the remote (`httpx.RemoteProtocolError: ConnectionTerminated`) after ~9,500 sequential requests scanning just the `admins` table. See [CHANGELOG.md](CHANGELOG.md) for this run's actual row counts.
- **Future modification notes:** Safe to re-run — normalizing an already-normalized value is a no-op, so a second run reports 0 rows updated everywhere and changes nothing (verified live). Deliberately does **not** touch `cashbook.category`/`cashbook.payment_method` — see ADR-36/TD-48 for why those two Cashbook fields are out of scope for this entire normalization pass, even though `cashbook.person`/`description` are now included. If a new category/name/location/free-text column is added to one of the tables above (or to a new table), add it to `TABLE_RULES` and re-run rather than writing a second one-off script — but if that table can hold more rows than `_PAGE_SIZE`, don't revert to an unranged `.select("*")`, and if the write volume is likely to be large, keep the per-row `.update()` shape (not a bulk `.upsert()`) unless every `NOT NULL` column of that table is included in the payload.

## `panda/`

A self-contained package (routes/services/prompts/intents/notifications/insights/forecasting all in one folder), deliberately not split across the top-level `routes/`/`database/` folders every other feature uses — see ADR-43 for why. Added 2026-07-27, Phase 1 (architecture + UI only, no real LLM). As of 2026-08-19 (ADR-47/48/49/50/51), `panda/intents.py` implements all five parts ("Ask"/"Analyze"/"Explain"/"Recommend"/"Forecast") of the Ask→Analyze→Explain→Recommend→Forecast progression — a real rule/keyword-based reply engine (Parts 1-4) plus a real plain-Python trend extrapolation (Part 5), still no LLM/ML. As of 2026-08-20 (ADR-52), two more topic-specific intents — student retention and cash management — extend Part 1's keyword coverage laterally; this is not a sixth part of the progression, which stays exactly as scoped above.

### `panda/routes.py`
- **Purpose:** HTTP surface for the floating Panda widget — every endpoint is JSON, called by `static/js/panda.js`.
- **Responsibilities:** Auth-guard every endpoint (401 JSON, not a redirect — these are `fetch()` calls from a widget, not page navigations, same shape as `routes/ai_center.py`'s `student_suggestions()`); translate `panda/services.py`'s return values and `database.panda_queries`'s two exception classes into the right HTTP status.
- **Functions/Classes:** `panda_bp` (Blueprint, `url_prefix="/panda"`), `_require_admin()`, `insights()` (`GET /panda/insights`), `suggested_questions()` (`GET /panda/suggested-questions`), `conversations()` (`GET`/`POST /panda/conversations`), `messages(conversation_id)` (`GET`/`POST /panda/conversations/<id>/messages`). Module constants `MAX_MESSAGE_LENGTH` (2000), `CHAT_UNAVAILABLE_RESPONSE`, `CHAT_TEMPORARILY_UNAVAILABLE_RESPONSE` (added 2026-08-24).
- **Depends on:** `panda.services`, `database.panda_queries.ChatStorageUnavailable`, `database.panda_queries.ChatStorageTemporarilyUnavailable` (added 2026-08-24).
- **Depended on by:** `app.py` (registers `panda_bp`); `templates/components/panda_widget.html` (reads its URLs via `url_for('panda.*')` into `data-*` attributes); `static/js/panda.js` (calls every endpoint via `fetch()`).
- **Future modification notes:** Empty-message/length/non-string validation runs early inside the `try/except` block, before any call that could actually raise either exception, so it still returns a clean 400 even when the chat tables don't exist yet — keep any new stateless validation just as early. `messages()` reads `message` via `.get("message")` (no string default) and only calls `.strip()` after an `isinstance(..., str)` check — a non-string JSON value (`null`/a number/a list/an object) must never reach `.strip()` directly, since that raised an unhandled `AttributeError` (500) before the 2026-08-19 QA audit fix (see CHANGELOG.md). A conversation-delete/rename endpoint would follow the same "check ownership inside the query, 404 on anything else" pattern `messages()` already uses. **A lapsed session behaves differently per HTTP method** and `static/js/panda.js` must keep handling both: a GET here reaches `_require_admin()` and returns a normal `401` JSON body; a POST never reaches this file at all when the session's CSRF token has gone stale, since `app.py`'s app-wide `enforce_request_security()` `before_request` hook rejects it first with `abort(400)` — an HTML error page, not JSON (see the 2026-08-20 CHANGELOG entry). Any new POST/PUT/PATCH/DELETE endpoint added here inherits that same HTML-on-CSRF-failure behavior; the frontend must not assume every non-2xx response is parseable JSON. **As of 2026-08-24 (TD-70, ADR-54):** every route now catches `ChatStorageTemporarilyUnavailable` alongside `ChatStorageUnavailable`, returning `CHAT_TEMPORARILY_UNAVAILABLE_RESPONSE` (still 503, but a distinct `error`/`message` telling the admin to try again — not the "ask your project owner to run CREATE TABLE statements" text, which would be wrong for a one-off network blip). Keep the two exception→response mappings separate if you add a third failure class later; don't collapse them back into one generic 503 body.

### `panda/services.py`
- **Purpose:** Orchestration layer between `routes.py` and everything else — the one place that decides how insights, suggested questions, and chat persistence fit together.
- **Responsibilities:** Keep routes thin; stay `request`/`session`-free so it's reusable from a future second entry point.
- **Functions/Classes:** `get_today_insights(admin_id)`, `get_suggested_questions(admin_id)`, `list_conversations(admin_id)`, `start_conversation(admin_id)`, `get_conversation_thread(admin_id, conversation_id)`, `send_message(admin_id, conversation_id, text)` (persists the user's message, then persists+returns Panda's real, rule-based reply — see `panda/intents.py`).
- **Depends on:** `database.panda_queries`, `panda.intents`, `panda.notifications`, `panda.prompts`.
- **Depended on by:** `panda/routes.py` (every function).
- **Future modification notes:** `send_message()` calls `intents.generate_reply()` (ADR-47) instead of `prompts.generate_placeholder_reply()` directly now — a future real LLM call most likely replaces `intents.py`'s handler bodies, not this file. Nothing else in this file needs to change for that swap.

### `panda/prompts.py`
- **Purpose:** Prompt/persona scaffolding for Panda's future LLM integration, plus the honest fallback reply generator for questions `panda/intents.py` doesn't recognize.
- **Responsibilities:** Hold the system persona and hard read-only constraints a future model/tool-calling layer must be given; hold the static Suggested Questions list; produce the fallback chat reply for an unrecognized question.
- **Functions/Classes:** `SYSTEM_PERSONA` (module constant, unused by any code path yet), `READ_ONLY_RULES` (module constant — a tuple of hard constraints, unused by any code path yet, see its own docstring), `SUGGESTED_QUESTIONS` (module constant, 9 static questions — as of 2026-08-20/ADR-52, includes one retention and one cash-management example alongside the original seven), `generate_placeholder_reply(user_message)` (ignores `user_message`'s content on purpose — returns the same honest "not connected to a real AI yet" string every time).
- **Depends on:** nothing beyond the stdlib.
- **Depended on by:** `panda/services.py` (`SUGGESTED_QUESTIONS`), `panda/intents.py` (`generate_placeholder_reply`, as its fallback).
- **Future modification notes:** `SYSTEM_PERSONA`/`READ_ONLY_RULES` are documentation for a future integration, not enforced anywhere today — see ADR-43 and PF-8 in `11_FUTURE_WORK.md` before assuming they do anything at runtime yet. `generate_placeholder_reply()` deliberately does not pattern-match `user_message` — that classification now lives in `panda/intents.py` (ADR-47); don't duplicate it here.

### `panda/intents.py`
- **Purpose:** Panda's real reply engine for all five parts of the progression — Part 1 ("Ask", ADR-47), Part 2 ("Analyze", ADR-48), Part 3 ("Explain", ADR-49), Part 4 ("Recommend", ADR-50), Part 5 ("Forecast", ADR-51) — plus four lateral topic-expansion intents, retention and cash management (ADR-52, 2026-08-20), expenses (ADR-54, 2026-08-24), and cash balance / profit-loss (ADR-55, 2026-08-25 — none a sixth part) — a rule/keyword-based intent classifier and reply composer, no external AI API and no machine learning model.
- **Responsibilities:** Classify a chat message into one of seventeen intents via word-bounded keyword matching on a punctuation-stripped copy of the text; every intent now composes a reply from `panda/insights.py`'s existing read-only wrappers (revenue, "why is revenue X", occupancy, renewals, admissions, purpose/course performance, student risk, retention, recommend, cash management, cash balance, profit/loss, expenses, forecast) — nothing is left as a placeholder. A genuinely unrecognized question still falls through to `prompts.generate_placeholder_reply()`. "Which batch should I promote?" is answered via purpose data with an explicit "not a real batch" disclaimer (no batch concept exists in this schema); "which locality gives the highest admissions" deliberately stays unrecognized (no locality data exists) rather than being caught by the admissions-trend keywords. "Why is revenue X" (Part 3) states the same current-vs-previous-month figures the plain revenue reply gives, then lists real, directionally-filtered contributing factors, or an honest "nothing stands out" line. A recommend question (Part 4) returns this admin's real, ranked action items straight from Business Intelligence's Action Center. A forecast question (Part 5) composes revenue/occupancy/churn trend projections, each independently reporting "not enough history yet" if that specific area doesn't have enough real data; as of 2026-08-24, a forward-looking occupancy question ("will occupancy increase?") also reaches this intent, not the present-state occupancy one. A retention question ("how can I retain students?", "how do I reduce churn?", ADR-52) composes the real retention ratio, churn-forecast trend, and top-risk-student list into one topic-focused reply; a cash-management question ("how can I manage cash?", "where is my cash going?", ADR-52) composes the real fee-collection rate, expense-category breakdown (labeled all-time as of 2026-08-24), and expense-health check. A dedicated expenses question ("how much are my expenses?", "what are my biggest expenses?", ADR-54) gets its own topic-focused reply (expense breakdown + expense health, no fee-collection section) instead of falling through to the placeholder; the admissions reply also now states this admin's total roster size and best admission month, not just the latest-vs-previous-month comparison. **Added 2026-08-25 (pre-pilot audit, ADR-55):** a cash-balance question ("how much cash do I have?", "what's my cash balance?", "what's in my cashbox?") answers with a single defined number — Cash-payment-method income minus Cash-payment-method expense, all-time — explicitly never called "bank balance"/"total money available"/"total collections"; a profit/loss question ("tell me about my profit or loss", "am I making a profit?", "is my business profitable?") answers with an explicit all-time net (every payment method, never a bare unscoped number) plus a recent-months breakdown that marks the current month as still in progress. The two are deliberately kept as separate intents/replies, never merged into one — a real library can have a positive cash balance and a negative overall profit at the same time (see ADR-55).
- **Functions/Classes:** `detect_intent(text)`, `generate_reply(admin_id, text)`, `_growth_direction_text(growth)` (shared by `_reply_revenue`/`_reply_explain_revenue`), `_is_retention_request(normalized)` (verb+noun combination, same shape as `_is_action_request`/`_is_explain_revenue_request`), `_is_future_occupancy_request(normalized)` (added 2026-08-24 — "will" + a direction word + an occupancy word, all three required; deliberately scoped to occupancy vocabulary, not a blanket "will X increase/decrease" pattern, to avoid hijacking other topics checked later in `detect_intent()`), `_is_cash_balance_request(normalized)` (added 2026-08-25 — bare "cashbox"/"cash box", OR the word "cash" AND a `_CASH_BALANCE_MARKERS` word both present; deliberately not a bare "cash" match, so a collection question like "how much cash did I collect?" isn't misrouted here), plus the `INTENT_*` constants (now including `INTENT_EXPENSES`, `INTENT_CASH_BALANCE`, `INTENT_PROFIT_LOSS`) and per-intent `_reply_*`/`_HANDLERS` internals (now including `_reply_expenses`, `_reply_cash_balance`, `_reply_profit_loss`).
- **Depends on:** `panda.insights` (`get_revenue_trend`, `get_expiring_memberships`, `get_shift_utilization`, `get_admissions_trend`, `get_student_count`, `get_purpose_performance`, `get_top_risk_students`, `get_revenue_explanation`, `get_recommended_actions`, `get_revenue_forecast`, `get_seat_demand_forecast`, `get_churn_forecast`, `get_retention_summary`, `get_risk_scoring_coverage`, `get_cash_collection_summary`, `get_expense_breakdown`, `get_expense_health`, and as of 2026-08-25 `get_cash_balance`, `get_profit_loss_summary`), `panda.prompts` (`generate_placeholder_reply`, as the unknown-intent fallback).
- **Depended on by:** `panda/services.py` (`send_message`, via `generate_reply`).
- **Future modification notes:** Action requests (deletion/pricing-change wording) are checked first and win over every other intent — misclassifying one as an answerable question would be a security-relevant mistake, not just a quality one. Forecast is checked next, before retention/risk, since `_RISK_PHRASES` includes the bare word "churn" (Part 2) and a message combining it with real forecast wording ("predict churn next month") should reach Part 5's real aggregate trend, the more specific answer (see ADR-51); as of 2026-08-24, `_is_future_occupancy_request()` is checked in this same branch (a forecast-flavored question containing "profit" but also "next month", e.g. "will I be profitable next month?", is caught here too, before ever reaching the new profit/loss check — see ADR-55). Retention (ADR-52) is checked right after forecast, before risk, for the identical collision reason: "how do I reduce churn?" also contains the bare word "churn" — checking retention first (its own verb+noun check, not a bare keyword) reaches the more specific retention-topic reply. Admissions/purpose-performance are checked before cash balance, cash management, expenses, and recommend since "which batch should I promote?" also contains "should i" (a recommend keyword) — the more specific, answerable intent must win. **As of 2026-08-25 (ADR-55):** cash balance is checked immediately before cash management (a more specific real answer must win — "what's my cash balance" vs. "how can I manage cash", no actual keyword overlap found); cash management (ADR-52) is checked before recommend for the same specificity precedent, and expenses (ADR-54) is checked right after cash management, before recommend, for the same reason — no actual keyword overlap between any of the three was found. Profit/loss (ADR-55) is checked immediately *after* recommend, before explain-revenue — deliberately after, not before: bare "profit" is a `_PROFIT_LOSS_PHRASES` word and `_RECOMMEND_PHRASES` already contains "increase profit"/"improve profit", so checking recommend first is what keeps "How can I increase profit?" resolving to Recommend rather than being shadowed by the newer bare-word match. `INTENT_EXPLAIN_REVENUE` (`_WHY_PHRASES` + `_REVENUE_PHRASES`, same verb+noun shape as the action-request check) is checked after profit/loss, before the plain revenue check. Adding a new answerable intent means adding a keyword tuple, a `_reply_*` function, and one `_HANDLERS` entry — no other file needs to change. `_reply_recommend()` deliberately doesn't map Part 3's `get_revenue_explanation()` factors to individual actions (one factor, admissions momentum, has no real matching action anywhere in the codebase) — see ADR-50 before changing that. `_reply_retention()` deliberately doesn't attempt a cross-student "why are students at risk" aggregate — see ADR-52 and **TD-65** before changing that; it does surface `get_top_risk_students()`'s existing 100-student cap (TD-60) honestly via `get_risk_scoring_coverage()` when actually hit. If `students` ever gains a real locality field, keep `_ADMISSIONS_PHRASES` narrow rather than widening it — a locality-aware answer belongs as its own new intent (see ADR-48). All five parts of the progression plus the retention/cash/expenses/cash-balance/profit-loss topic expansions are now real — a genuine LLM/ML integration (if ever pursued) is the only thing left to swap in, at these `_reply_*` handler bodies or `panda/forecasting.py`'s three functions, per ADR-47/51's "how to apply". **As of 2026-08-24 (ADR-54):** `_EXPENSE_PHRASES` is a flat bare-word list ("expense"/"expenses"/"spend"/"spent"/"spending"/"money going") deliberately unpaired with a verb, the same "unambiguous alone" treatment `_RETENTION_PHRASES` gives "retain"/"retention" — don't add a verb-pairing requirement to it without first checking it doesn't reintroduce the "how much did I spend" miss that treatment was chosen to avoid. `_is_future_occupancy_request()` is deliberately narrow (occupancy-only) — if a similar forward-looking gap is ever found for another topic (e.g. "will revenue increase" without "next month"), give it its own similarly-scoped check rather than widening this one to a blanket "will X" pattern, which would risk hijacking retention/cash/revenue questions checked later. **As of 2026-08-25 (ADR-55):** `_reply_cash_balance()`/`_reply_profit_loss()` must never be merged into one reply or into `_reply_cash_management()` — cash balance is Cash-payment-method transactions only, profit/loss spans every payment method, and a real library's roster can show both a positive cash balance and a negative overall profit at the same time; see ADR-55 before changing either's wording. `get_cash_balance()` has no monthly breakdown anywhere in this codebase (all-time only, same shape TD-61 already documents for expense categories) — see **TD-71**.

### `panda/notifications.py`
- **Purpose:** Turns `panda/insights.py`'s raw numbers into the "Today's AI Insights" cards shown in the widget and counted on the floating button's badge.
- **Responsibilities:** Three independent, rule-based checks (revenue trend, expiring memberships, shift under-utilization); a check that finds nothing returns no card — there is no manufactured "all good" filler card.
- **Functions/Classes:** `REVENUE_DROP_THRESHOLD_PCT` (-5), `UNDERUTILIZED_THRESHOLD_PCT` (50), `_check_revenue_trend(admin_id)`, `_check_expiring_memberships(admin_id)`, `_check_shift_utilization(admin_id)`, `_CHECKS` (module constant tuple of the three), `get_notifications(admin_id)`.
- **Depends on:** `panda.insights`.
- **Depended on by:** `panda/services.py` (`get_today_insights`).
- **Future modification notes:** A new insight is one more `_check_*` function (returning `None` or a `{id, type, severity, icon, title, message}` dict) appended to `_CHECKS` — nothing else in this package needs to change. Keep new checks wrapping an existing read-only query module wherever one already computes the number elsewhere (see `insights.py`'s own note on why).

### `panda/insights.py`

### `panda/forecasting.py`
- **Purpose:** Panda's real Part 5 ("Forecast", ADR-51) calculation engine — simple linear trend extrapolation over this admin's own historical data, no ML/LLM.
- **Responsibilities:** Fit an ordinary-least-squares straight line through up to 6 months of real monthly history and project one month ahead, for revenue, seat occupancy, and membership churn; return `None` instead of a number when fewer than `MIN_MONTHS_FOR_FORECAST` (3) real (nonzero, or for churn: has-any-expiring) months exist in the window.
- **Functions/Classes:** `forecast_revenue(admin_id, months_ahead=1)` (fits `database.cashbook_queries.get_monthly_income`), `forecast_seat_demand(admin_id)` (fits `database.bi_queries.get_monthly_occupancy_trend`, clamped to [0, 100]), `forecast_membership_churn(admin_id)` (computes a new monthly lapse-rate series from `database.membership_queries.get_memberships_for_admin` — the one genuinely new aggregation this module introduces — then applies the projected rate to `database.bi_queries.get_upcoming_expiries(days=30)`), `_linear_forecast(values, months_ahead=1)` (pure-Python OLS fit, no numpy/pandas), `_trend_direction(values)` ("up"/"down"/"flat", same `trend[0]` vs `trend[-1]` comparison `get_occupancy_insights()` already uses). Module constants `MIN_MONTHS_FOR_FORECAST` (3), `FORECAST_WINDOW_MONTHS` (6).
- **Depends on:** `database.bi_queries` (`last_n_months`, `get_monthly_occupancy_trend`, `get_upcoming_expiries`), `database.cashbook_queries.get_monthly_income`, `database.membership_queries.get_memberships_for_admin`.
- **Depended on by:** `panda/insights.py` (`get_revenue_forecast`, `get_seat_demand_forecast`, `get_churn_forecast`).
- **Future modification notes:** `forecast_membership_churn()`'s "did this student renew" test is the exact same one `database/ai_center_queries.py`'s `_renewal_signal()` uses (any later membership `joining_date` past this one's `end_date`) — keep them consistent if either changes. See **TD-62** in `11_FUTURE_WORK.md` for this module's known simple-linear-fit limitations (no seasonality, small-sample sensitivity, non-calendar-continuous churn indexing) before treating a forecast as more precise than it is. A real ML/LLM model, if ever pursued, is the intended replacement for these three function bodies (ADR-51's "how to apply") — callers (`panda/insights.py`) don't need to change for that swap as long as the `None`-when-uncertain contract is preserved.

- **Future modification notes:** `register()` hardcodes `role="Admin"` while the schema default is lowercase `'admin'` (Known Technical Debt item TD-13) — fix the casing before anything starts branching on `role`. As of 2026-07-23 (ADR-16), `admins` reads/writes for login/register/forgot-password primarily go through Supabase (`database.supabase_client.get_supabase_client()`), using `.eq()` filters (never raw string interpolation, so still immune to actual SQL injection) instead of parameterized `sqlite3` queries. Every Supabase call that carries user-controlled input is wrapped in `try/except APIError`, degrading to the same user-facing outcome as "no match found" (login/forgot-password) or a generic "Something went wrong" flash (register) — added because PostgREST encodes `.eq()`/`.select()` filter values into the request's GET query string, and Supabase's Cloudflare-fronted edge network was observed (live, via the test suite's SQL-injection-payload tests) to return an HTTP 403 WAF block for adversarial-looking query strings (e.g. containing `DROP TABLE`) before the request ever reaches Postgres — a new failure mode SQLite never had, since `sqlite3`'s bound parameters never touch a URL. Without the `try/except`, that 403 would surface as an unhandled `postgrest.exceptions.APIError` (500), a regression from SQLite's graceful "Invalid username" handling for the same adversarial input. **`register()` no longer touches SQLite at all (2026-07-25, ADR-31):** it used to mirror the new admin row — same `admin_id`, `full_name`, `username`, `mobile`, `email`, hashed `password`, `role` — into SQLite's `admins` table via `get_connection()` immediately after the Supabase insert, rolling back the Supabase insert if the SQLite insert raised `sqlite3.Error`. That existed solely because other tables still enforced real SQLite foreign keys back to `admins.admin_id`; as each of those dependents (`audit_log` — ADR-26, `students` — ADR-29, `enquiries` — ADR-30) stopped writing SQLite in turn, the bridge's reason for existing evaporated one table at a time until none were left. ADR-31 deleted the mirror-insert block outright (along with the `insert_response`/`new_admin_id` variables that only fed it) — this was the seventh and **final** mirror/bridge removed in Phase 10; see `docs/MIRROR_TRACKER.md` and `docs/DECISIONS.md`'s ADR-31 for the full history.

## `scripts/`

New directory, 2026-08-21 (one-deployment-per-library provisioning, ADR-53). Both files are standalone, read-only, dependency-free operator tools — not imported by the app itself, not covered by `pytest`. Each inserts the repository root onto `sys.path` itself (`sys.path.insert(0, str(Path(__file__).resolve().parent.parent))`) so they can be run directly (`python scripts/verify_schema.py`) from any working directory without needing `python -m scripts.verify_schema`.

### `scripts/verify_schema.py`
- **Purpose:** Pre-go-live check that every table this app needs actually exists on a given Supabase project — see [PROVISIONING.md](PROVISIONING.md) Step A.
- **Responsibilities:** For each of the 17 tables `database/supabase_migration.sql` defines, issues a read-only `select(..., count="exact", head=True).limit(1)` existence probe via the same `database.supabase_client.get_supabase_client()` the app itself uses, and reports `OK`/`MISSING`/`ERROR` per table.
- **Functions/Classes:** `ALL_TABLES` (module constant — every table name, in migration order), `KNOWN_MANUAL_STEP_TABLES` (module constant — `ai_center_settings`/`panda_conversations`/`panda_messages`, flagged with an extra hint since they're the ones most likely to be missing), `_probe_table(supabase, table_name)`, `main()`.
- **Depends on:** `database.supabase_client.get_supabase_client`, `postgrest.exceptions.APIError`.
- **Depended on by:** nothing in the app; run manually or from a deployment checklist. Referenced by `docs/PROVISIONING.md` and `docs/DEPLOYMENT.md`.
- **Future modification notes:** If a new table is added to `database/supabase_migration.sql`, add it to `ALL_TABLES` here in the same change — this list is intentionally not derived by parsing the SQL file (the SQL file has no stable machine-readable table list), so it can silently drift if forgotten. Exits non-zero on any problem — safe to use as a CI/go-live gate, not just interactively.

### `scripts/migrate_branding_to_storage.py`
- **Purpose:** One-off — move existing on-disk Library Profile branding images into Supabase Storage after the ADR-57 migration. Run once against a deployment (e.g. Render) that already had images under `static/uploads/settings/`.
- **Responsibilities:** For each `library_settings` row whose `logo_path`/`stamp_path`/`signature_path` is still a relative path and whose file exists on this machine, upload it via `database.branding_storage.upload_branding_image()` and rewrite the column to the public URL. Dry-run by default; `--apply` to write. Idempotent (rows already holding an `http(s)://` URL, or whose local file is missing, are skipped).
- **Functions/Classes:** `_FIELDS`/`_STATIC_ROOT` (constants), `_is_url(value)`, `main()` (argparse — `--apply`).
- **Depends on:** `database.branding_storage.upload_branding_image`, `database.supabase_client.get_supabase_client`, `mimetypes`, `argparse`.
- **Depended on by:** nothing in the app; run manually. Referenced by `docs/DECISIONS.md` (ADR-57) and the 2026-08-28 CHANGELOG entry.
- **Future modification notes:** Only needed while legacy relative-path rows still exist; once every deployment has been migrated (or its images re-uploaded through the app), this script and `utils/branding.py`'s legacy branch can both go.

### `scripts/verify_tenant_isolation.py`
- **Purpose:** Post-provisioning check that a freshly created Supabase project contains only one library's data — the direct mitigation for "operator pasted the wrong `SUPABASE_URL`/`SUPABASE_SECRET_KEY`" under the one-deployment-per-library model. See [PROVISIONING.md](PROVISIONING.md) Step D/E.
- **Responsibilities:** Before any admin has registered, asserts every relevant table is empty. After `--expected-admin-id <id>` (post first-admin-registration), asserts every row either belongs to that one `admin_id` directly, or — for tables with no `admin_id` column of their own (`memberships`, `payments`, `panda_messages`) — traces back to it through the same FK-ownership-chain pattern `database/payment_queries.py`'s `get_payments_for_admin()` already uses.
- **Functions/Classes:** `DIRECT_ADMIN_TABLES`/`FK_SCOPED_TABLES`/`UNSCOPED_LEGACY_TABLES` (module constants), `_fetch_all`, `_check_admins_table`, `_check_direct_table`, `_check_fk_scoped_table`, `main()` (argparse — `--expected-admin-id`).
- **Depends on:** `database.supabase_client.get_supabase_client`, `argparse`.
- **Depended on by:** nothing in the app; run manually or from a deployment checklist. Referenced by `docs/PROVISIONING.md` and `docs/DEPLOYMENT.md`. Exists specifically because `tests/conftest.py` has no mocking/teardown (see that file's card) — the real `pytest` suite is unsafe to run against a freshly provisioned, production-intended project, but this script is read-only and safe to run against one at any time.
- **Future modification notes:** If a new table gains its own `admin_id` column, add it to `DIRECT_ADMIN_TABLES`; if a new table is scoped only via a foreign key to an already-scoped table, add it to `FK_SCOPED_TABLES` (not `DIRECT_ADMIN_TABLES`) — the two are checked with genuinely different logic, and using the wrong one will either false-fail (missing column) or silently skip real ownership checking.

### `utils/normalization.py`
- **Purpose:** The single, shared input-normalization utility — added 2026-07-26 (Input Normalization) so every route stores category/name/location/free-text/phone fields in one consistent format instead of each route inventing its own `.upper()`/`.title()`/`.strip()` logic. See ADR-36 in [DECISIONS.md](DECISIONS.md).
- **Responsibilities:** Five pure string functions, no DB/Flask/request access — callers pass in a raw form value and get back the normalized value to store.
- **Functions/Classes:** `collapse_whitespace(value)` (trim + collapse internal whitespace runs, `None`-safe), `normalize_category(value)` (Category fields — Purpose, Shift, Membership Plan, Payment Mode — → UPPERCASE), `normalize_name(value)` (person name fields → Title Case, ASCII-letter-run-only so non-Latin scripts/emoji pass through untouched), `normalize_location(value)` (City/State → Title Case, same rule as `normalize_name`, kept as a distinct name for call-site clarity), `normalize_free_text(value)` (Address/Remarks/Notes/Descriptions — whitespace trimmed/collapsed only, casing untouched), `normalize_phone(value)` (phone numbers — whitespace trimmed/collapsed only), `clean_mobile(value)` (**added 2026-08-30, ADR-59** — strips non-digits, drops an optional leading `91`/`0` prefix, requires exactly 10 digits left; returns the bare 10-digit string or `""` if it can't be one).
- **Depends on:** `re` (stdlib) only.
- **Depended on by:** `routes/enquiries.py` (`normalize_name`/`normalize_category`/`normalize_free_text` for `full_name`/`purpose`/`preferred_shift`/`remarks`; **`clean_mobile` for `mobile` as of ADR-59** — `normalize_phone` no longer imported here), `routes/student.py` (`normalize_name`/`normalize_category`/`normalize_free_text` for `full_name`/`address`/`id_proof`/`purpose`/`shift`; **`clean_mobile` for `mobile` as of ADR-59** — `normalize_phone` no longer imported here), `routes/membership.py` (`plan_name`, `remarks`), `routes/payment.py` (`remarks`), `routes/setting.py` (`owner_name`, `phone` via `normalize_phone`, `city`, `state`, `address`, `receipt_footer`), `routes/auth.py` (`normalize_phone` for admin `mobile`, then its own `isdigit()/len==10` check), `database/payment_queries.py` (`record_payment()` — `payment_mode`, `payments` table only), `routes/membership_distribution.py` and `utils/chart_data.py` (`normalize_category`, when bucketing `plan_name` values into chart slices / mapping plan colours), `database/migrate_normalize_input_data.py` (the one-time backfill).
- **Future modification notes:** `clean_mobile()` is the single canonicalizer for a person's mobile (ADR-59) — call it, treat `""` as invalid, don't add a second bespoke phone check; a first-digit `[6-9]` rule could be folded into it without touching call sites. `routes/auth.py`/`routes/setting.py` deliberately keep their own phone handling (`normalize_phone` + local rules). `normalize_name`/`normalize_location` only re-case contiguous ASCII letter runs (`[A-Za-z]+`) — a name/city written in Devanagari, CJK, etc. is left byte-for-byte as typed, by design (there's no single "Title Case" rule that's meaningful across scripts). Cashbook's own `category`/`payment_method` fields (`database/cashbook_categories.py`) are deliberately **not** routed through this module — see ADR-36 for why. If a new person-name-like field is added anywhere in the app, call `normalize_name`, not a local `.title()` — Python's built-in `str.title()` mis-cases text after an apostrophe (e.g. `"o'brien".title()` → `"O'Brien"` is fine, but `"mcdonald's".title()` → `"Mcdonald'S"` is not) in a way this module's regex-based approach avoids for the simple space/hyphen-separated names this app actually stores.
